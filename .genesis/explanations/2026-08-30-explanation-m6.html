1Background: one outbound call, three ways to fail

Since M3, every accepted webhook goes through RedisJobQueue, which makes exactly two real network calls per request: an atomic SET key value NX EX ttl against Redis to check-and-record the delivery's idempotency key, and a hand-off of the parsed event to ARQ's queue (also a Redis operation, bridged across a background event-loop thread). Before M6, both of those calls were guarded by exactly one thing: a hardcoded future.result(timeout=10) on the ARQ hand-off, and nothing at all on the idempotency SET. If Redis was merely slow, the request blocked for up to ten seconds. If Redis was down outright, the call raised a raw redis.exceptions.ConnectionError straight out of RedisJobQueue.enqueue(), which FastAPI turned into an unhandled 500 — indistinguishable, from GitHub's point of view, from a genuine bug in this service, rather than "the dependency is temporarily down, please retry the delivery" (which GitHub's own redelivery mechanism already knows how to do).

M6's job is not to make Redis more reliable — it can't — but to make this service behave sanely around an unreliable dependency: bound how long a caller waits, stop hammering a dependency that has already shown it's down, and only retry the kind of failure retrying can actually fix.

Where this lives
Three new modules under backend/reliability/ (retry.py, circuit_breaker.py, timeout.py), wired into backend/job_queue/redis_arq.py's _call_reliably helper, which both of RedisJobQueue's real Redis calls go through. Six new Settings fields (RETRY_MAX_ATTEMPTS, RETRY_BASE_DELAY_SECONDS, RETRY_MAX_DELAY_SECONDS, RELIABILITY_TIMEOUT_SECONDS, CIRCUIT_BREAKER_FAILURE_THRESHOLD, CIRCUIT_BREAKER_RESET_TIMEOUT_SECONDS) make every knob configurable instead of a buried magic number.

2Intuition: what each primitive is actually for

Three different problems, three different tools. It helps to keep them separate before seeing how they nest:

retry

Handles a transient failure — one that might succeed if you just try again in a moment. A dropped TCP packet, a momentary connection blip. Retrying turns "this one attempt failed" into "this operation eventually succeeded," as long as the underlying problem was genuinely temporary.

timeout

Bounds how long you're willing to wait for any single attempt. Without it, "the dependency is slow" and "the dependency will never respond" look identical from the caller's seat — you just sit there. A timeout turns an unbounded wait into a bounded one, so the caller can move on (and, e.g., let a retry loop try again, or give up cleanly).

circuit breaker

Stops you from hammering something already known to be down. Retry and timeout both still cost something — a connection attempt, a wait — every single time. Once a dependency has failed enough times in a row, a breaker admits the obvious: the next call is very likely to fail too, so skip trying it at all and fail immediately instead. This is what turns "resilient" into "fail fast," not just "keep trying forever."

None of these three alone is "the reliability layer." A retry loop with no timeout can retry a call that hangs forever, one attempt at a time, for an unbounded total duration. A timeout with no breaker cuts each attempt short but still lets every single caller re-attempt a dependency that's been down for an hour. A breaker with no retry correctly stops calling a dead dependency, but never distinguishes "one unlucky blip" from "actually down" in the first place. They compose because each covers a gap the other two leave open.

3Composition order: retry(breaker(timeout(call)))

RedisJobQueue._call_reliably nests the three in exactly one order, outermost to innermost:

retry (outermost)
circuit breaker
timeout (innermost)
the actual Redis call (SET NX EX, or the ARQ enqueue)

Reading from the inside out: every real Redis call is individually bounded by a timeout first. That bounded call is what the breaker decides to count as a success or a failure. And the whole breaker-guarded, timeout-bounded call is what the retry loop repeats, with backoff, until it gives up or succeeds.

Why this order and not, say, breaker(retry(timeout(call)))? Putting retry inside the breaker would mean the breaker only ever sees one outcome per logical request — "the whole retry sequence eventually failed" — collapsing several real failures into a single recorded one. That breaks the breaker's own contract (failure_threshold consecutive failures trips it): with retry innermost, three real dependency failures inside one retry sequence would only count as one failure against the threshold, letting a genuinely dead dependency get hit several times per breaker-counted "failure" instead of stopping after the threshold is actually reached. Retry outermost means every individual attempt — each one separately timeout-bounded and breaker-guarded — is what gets counted, which is what lets the very next section's evidence (2 real calls trip a threshold of 2) come out exactly right.

4Retryable vs. non-retryable: a TypeError is not a flake

call_with_retry takes an explicit non_retryable_exceptions tuple and re-raises those immediately — no sleep, no further attempts. The default set is TypeError, ValueError, KeyError, AttributeError: the classic "the caller's code is wrong" family, not "the dependency is flaky" family.

Why this matters
A transient failure might succeed on the next attempt because the world changed between attempts (the network blip passed, the server came back). A TypeError from passing the wrong argument shape will fail identically on every attempt, because nothing about the call itself changes between retries — the bug is in the code, not the environment. Retrying it anyway doesn't add resilience; it just burns the entire retry budget (and the sleep time that comes with it) on a call that was never going to succeed, while making the failure take longer to surface and look, superficially, like "the system tried hard" instead of "the system has a bug."

This is also exactly why the pattern generalizes: whatever exceptions mean "this call itself is malformed" for a given dependency belong in that call site's own non_retryable_exceptions, extending the default set rather than replacing it. RedisJobQueue does exactly this — see next.

5Why CircuitOpenError must never be retried

RedisJobQueue extends the default non-retryable set with one more type: CircuitOpenError. This is the one addition the whole composition depends on. If a breaker being open were retryable, the retry loop would catch CircuitOpenError, sleep, and try again anyway — completely defeating the point of a breaker that exists specifically to skip attempts once a dependency is known to be down. Retry and breaker would be fighting each other: the breaker saying "don't bother," the retry loop saying "bother anyway."

This is provable, not just arguable. Configure retry_max_attempts=5 against a breaker with failure_threshold=2, point the call at something that always fails, and count how many times the real dependency is actually touched: 

real_call_count = 2 (retry_max_attempts was 5, breaker failure_threshold was 2)
breaker.state = open
CONFIRMED: exactly 2 real Redis-dependency calls happened, not 5.

Walking through why: attempt 1 fails (breaker still CLOSED, 1 consecutive failure < threshold of 2). Attempt 2 fails too — now 2 consecutive failures, so the breaker flips to OPEN as a result of that second failure. The retry loop, still under its 5-attempt budget, tries a third time — but this time breaker.call raises CircuitOpenError before the dependency is touched at all, and because that exception is non-retryable, the retry loop re-raises it immediately instead of sleeping and trying attempts 4 and 5. Two real calls, not five — the exact number the breaker's own threshold predicts, no more.

The same shape holds for the actual production settings (retry_max_attempts=2, breaker failure_threshold=2, used by tests/unit/test_reliability.py's wiring tests): driving a real webhook POST through the actual FastAPI route against a RedisJobQueue whose Redis connection was redirected to an unreachable address, with the circuit breaker and retry loop instrumented to count invocations, produces: 

response.status_code = 503
breaker_call_count = 2
retry_attempt_count (call_with_retry's own func() invocations) = 2
CONFIRMED: one real 503 webhook request made exactly 2 breaker calls and 2 retry attempts.

One real HTTP request, two breaker calls, two retry attempts — matched exactly, because both knobs are set to 2 in this project's own fast test settings.

6Half-open and the thundering herd

A breaker that opens forever would just convert "dependency is temporarily down" into "dependency is permanently unusable." So after reset_timeout_seconds elapses, the breaker transitions from OPEN to HALF_OPEN: the next call is treated as a probe. If it succeeds, the breaker closes fully — the dependency has recovered. If it fails, the breaker reopens immediately (not waiting for a fresh run of failure_threshold failures — one failed probe is already enough evidence the dependency is still down).

CLOSED
calls go through normally; a success resets the failure count
OPEN
every call rejected immediately, no dependency attempt at all
HALF_OPEN
exactly one probe allowed through

CLOSED → (≥failure_threshold consecutive failures) → OPEN → (≥reset_timeout_seconds elapsed) → HALF_OPEN → success → CLOSED  /  failure → OPEN

The dangerous version of this design is a thundering herd: the reset window elapses, and if every waiting caller were allowed through as its own "probe," they would all hit the just-maybe-recovered dependency simultaneously — potentially knocking it back down the moment it came up, the exact opposite of what a cautious recovery probe is for. CircuitBreaker prevents this with a _probe_in_flight flag, set and checked under the same lock that guards every other state read/mutation: the first caller to observe HALF_OPEN claims the probe and proceeds; every other caller that arrives while a probe is already in flight gets an immediate CircuitOpenError instead of a second concurrent attempt.

Thread safety for the breaker as a whole — not specifically the half-open probe race, but the general "many threads mutating shared state" hazard the milestone calls out by name — is proven under real load: TestCircuitBreakerThreadSafety starts 200 threads simultaneously, all calling a function that always fails, against one shared breaker with failure_threshold=10. The test asserts three things afterward: no thread saw an unexpected exception (the lock kept every read/mutation coherent), the breaker ended up OPEN (the threshold was reached), and — the interesting part — the dependency function was called somewhere between 10 and 199 times, not all 200: proof the OPEN check itself, not just the failure counter, is doing real work to stop callers once the breaker trips, mid-storm.

Scope note
The 200-thread test targets the CLOSED-to-OPEN transition under concurrent load, not a dedicated multi-thread race specifically against the HALF_OPEN _probe_in_flight guard. That guard's single-probe behavior is real production code, exercised by sequential tests (a successful probe closes the breaker; a failed one reopens it) — but this test suite does not additionally launch a concurrent herd of threads at the exact instant a breaker transitions to HALF_OPEN to prove only one of them wins the probe. Worth adding if a future milestone leans harder on the half-open path.

7The centerpiece: why this milestone exists at all

Here is the failure mode M6's own Definition-of-Done gate is written to catch, stated plainly: a reference implementation of this exact project wrote all three of these modules — retry, circuit breaker, timeout — unit-tested each one thoroughly in isolation, and never once called any of them from the live request path. Its /health endpoint reported an empty breaker list forever, because nothing ever registered a breaker outside of a test file. Every one of its unit tests passed. Its reliability layer did not exist in any way a real webhook request would ever notice.

This is why DONE.html's second M6 gate is phrased the way it is: "Every security and reliability module has a live call site in the request path, provable by grep — not merely a passing unit test." A plain grep -r "from backend.reliability import" would have found imports in the reference implementation too — it imported these modules into its own test files. Imports are not evidence of wiring; they're evidence that a human (or an agent) once typed the module's name somewhere.

L4 VERIFY's approach to this gate is the actual point worth internalizing, not just the result. It did not stop at "does redis_arq.py import backend.reliability" — that check alone would have passed the reference implementation's code too, if it had merely imported the modules without calling them. Instead it verified the wiring two independent ways:

Dynamic proof

Monkeypatched CircuitBreaker.call and call_with_retry with counting wrappers, then drove one real webhook POST through the actual FastAPI route (via TestClient) against a RedisJobQueue whose Redis connection was redirected to an unreachable address, and observed the counts directly: breaker_call_count = 2, retry_attempt_count = 2 (shown in full in Section 5). The primitives didn't just get imported — they executed, the correct number of times, during a request that looks exactly like something GitHub would send.

Falsification

Temporarily edited CircuitBreaker.call to bypass its own state machine entirely — call the wrapped function straight through, as if no breaker existed — and reran tests/unit/test_reliability.py: 

8 failed, 15 passed, 1 warning in 0.62s

Then reverted and confirmed the suite is green again:

23 passed, 1 warning in 0.61s

Exactly 8 of the 23 tests depend on the breaker's real state machine actually running: the six direct TestCircuitBreaker tests, the 200-thread concurrency test, the composition test that checks the breaker trips and then fails fast, and the wiring test that asserts the breaker ends up OPEN after a simulated Redis outage. Neutering the breaker doesn't make those tests merely weaker — it makes them fail outright, which is what distinguishes "this code path is actually exercised" from "this code path is merely imported somewhere." A reference implementation whose reliability layer is dead code would show 23 passes either way, because dead code has no failure mode when you break the thing it never called.

8The 503 fix, and why HMAC still wins

Before M6, a Redis outage during enqueue() raised a raw exception that FastAPI turned into an unhandled 500 — a tracked-but-deferred item since M3. M6 closes it: RedisJobQueue now translates both failure shapes (retries exhausted, or the breaker already open) into one shared QueueUnavailableError, and backend.webhook_receiver.router catches exactly that type and answers 503 instead.

Before M6

Redis unreachable → raw ConnectionError escapes enqueue() → unhandled exception → FastAPI's default 500, indistinguishable from a genuine bug in this service.

After M6

Redis unreachable → retry exhausted or breaker open → QueueUnavailableError → router catches it → 503, telling GitHub (correctly) that this is a transient condition worth retrying later.

The one detail worth being precise about: this fix does not touch, or weaken, the HMAC trust boundary from M2. The webhook route still verifies the request's signature over the raw body before anything else happens — including before the queue is ever touched. So with Redis down and a bad signature, the response is still 401, not 503: signature verification runs first regardless of the dependency's health, and a forged request never gets far enough to discover that Redis is unreachable. The order in backend.webhook_receiver.router.receive_webhook hasn't changed — verify, then parse, then enqueue — M6 only changed what happens when the last step fails.

9Known limits, stated honestly

  1. CircuitBreaker's registry has no reader yet. register()/all_breakers() maintain a real, thread-safe, process-wide registry of every breaker constructed — built because a future /health endpoint will need it — but no /health route exists in this codebase yet to call all_breakers(). This is forward-looking infrastructure, the same category as M4's WorkflowEngine Protocol or M5's InMemoryHitlQueue, not a gap in M6's own scope. Worth revisiting specifically once M8's LLM client and M11's GitHub client get wrapped in this same reliability layer: a non-idempotent call to either (an LLM completion with side effects, a real GitHub comment POST) would make an unread breaker registry a more expensive blind spot than it is today, guarding only the idempotent Redis operations.
  2. A timed-out call keeps running in the background, because Python cannot kill a thread. run_with_timeout submits the wrapped callable to a shared background thread pool and stops waiting for it once the configured bound elapses — but the worker thread itself keeps executing the original call until it eventually finishes or raises on its own; there is no portable way in Python to forcibly terminate a running thread. This is documented in backend/reliability/timeout.py's own module docstring as a known, accepted trade-off, not a hidden gap — safe today because the two calls it wraps (the idempotency SET, the ARQ enqueue) are idempotent or side-effect-tolerant. Measured overshoot past the configured timeout bound, across a small sample run, was 4–10ms — comfortably inside PLAN.md's own ±50ms tolerance, and consistent with the scheduling overhead of a real thread pool rather than a bare future.result() call.

10Quiz

Three questions. Click each one to reveal the answer.

1. A reference implementation of this project built retry.py, circuit_breaker.py, and timeout.py, unit-tested each one, and passed every test — yet its reliability layer never affected a single real request. Why does "the module is imported somewhere" not prove the opposite of that failure mode?

Because a unit test (or a `grep` for an import) can only tell you the code exists and runs in isolation — it says nothing about whether the live request path actually calls it. The reference implementation's own test files imported these modules; a plain import-grep would have passed its code too.

What actually distinguishes "wired in" from "merely present" is observing the primitive execute as a side effect of a real request — which is exactly what M6's L4 VERIFY did: monkeypatching the breaker and retry loop and watching a real webhook POST trigger exactly 2 calls to each, and separately, neutering the breaker and watching 8 of 23 tests fail because they depend on state the breaker actually maintains. "The module executed, with the effect a broken version of it would have missed" is strictly stronger evidence than "the module is imported," because the second is compatible with the module never running at all.

2. With retry_max_attempts=5 and a circuit breaker failure_threshold=2, an always-failing dependency call is measured to hit the real dependency exactly 2 times, not 5. What stops attempts 3 through 5 from happening?

CircuitOpenError is registered as a non-retryable exception. After the 2nd real failure trips the breaker to OPEN, the retry loop's 3rd attempt calls the breaker again, but the breaker now raises CircuitOpenError before touching the dependency at all — and because that's non-retryable, the retry loop re-raises it immediately instead of sleeping and trying attempts 4 and 5.

If CircuitOpenError were not marked non-retryable, the retry loop would treat it like any other failure — sleep, then try again — meaning attempts 3, 4, and 5 would each re-check the (still open) breaker, still never reach the real dependency, but burn the entire retry budget's sleep time doing so. Marking it non-retryable is what makes "fail fast while open" actually fast: the very next attempt after the breaker opens costs one cheap in-process exception, not a wasted retry cycle.

3. Composing the three primitives as retry(breaker(timeout(call))) puts retry outermost. Why not breaker(retry(timeout(call))), with retry innermost instead?

Because a breaker's failure_threshold counts consecutive failures it directly observes. If retry sat inside the breaker, one whole retry sequence (which might itself contain several real failed attempts) would register as only a single failure to the breaker — letting a genuinely dead dependency absorb several real hits per breaker-counted failure instead of tripping at the threshold the config actually names.

With retry outermost, every individual attempt is separately wrapped by the breaker (and, innermost, by the timeout), so each real call the retry loop makes is exactly one data point for the breaker's threshold. This is what makes the Section 5 evidence exact rather than approximate: a threshold of 2 trips after precisely 2 real calls, not some larger number diluted by nested retries the breaker never separately saw.
