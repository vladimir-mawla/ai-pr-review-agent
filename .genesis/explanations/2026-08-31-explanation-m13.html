Operator Dashboard + Evaluation/CI Gate

M13 gives this project two things it never had before: eyes (a dashboard an operator can actually look at) and a brake (CI that can block a bad merge before it lands). Both arrived with a real, instructive failure along the way — a cost page that briefly told an operator they'd spent $97,468.71 they hadn't, and an eval gate that ran on every push except the one moment it needed to: a pull request. This page covers why the dashboard reads through a JSON API instead of the database directly, why pr_cost_hourly doesn't exist and what stands in for it, the centerpiece cost-dashboard defect and its honest limits, the LLM-as-judge and what its own numbers do and don't prove, and why a green CI check that runs nothing is worse than no CI at all. 1Background: what a dashboard is for

Every prior milestone in this project made the pipeline itself more capable — a real specialist, real retrieval, a real GitHub round trip. None of them gave a human operator anywhere to look. If a review sat queued for human approval, the only way to find it was to query Postgres by hand. If spend crept toward the daily cap, the only warning was BudgetGuard throwing an exception mid-review. If something went wrong three specialist calls deep into a review, the only record was scattered log lines and whatever agent_events rows happened to exist. An operator dashboard exists to answer three concrete questions without a database client: what needs my attention right now, what is this costing me, and what actually happened on this one review.

None of that would be answerable without M7's events spine. Every specialist call, every routing decision, every span this project's orchestrator produces has been landing in the append-only agent_events table since M7 — not because M7 anticipated a dashboard, but because an audit trail was worth building on its own merits (compliance, debugging, cost accounting). M13 is the first milestone that actually reads that trail back out for a human, rather than only writing to it. The durable reviews table this milestone also added (outside its literal freeze boundary, disclosed in the M13 build report) exists for the same reason in miniature: agent_events' own decision event carries only an outcome and a confidence number, never the findings or the routing reason a human actually needs to see before approving or rejecting a queued review.

Why this matters before the centerpiece defect
Keep this in mind for later: a dashboard's entire value proposition is that an operator can trust the numbers on the screen without going and checking the database themselves. That trust is exactly what the centerpiece defect below broke, and exactly what the fix had to restore — not just quietly correct the number, but explain what got excluded and why.

2Three views, one JSON API

The dashboard (frontend/, Next.js 15) has three Client Component views, each answering one of the questions above:

/hitl

The HITL queue — every review currently awaiting human approval, with its findings, severities, confidence, and the exact reason route_review queued it instead of auto-posting.

/costs

Per-agent cost/latency — call count, total cost, average latency, and token usage, grouped by (agent, model). This is the centerpiece view below.

/trace/[reviewId]

Trace reconstruction — one review, end to end, in time order, from review_id alone: every span, LLM call, and routing decision recorded for it.

All three fetch from a single new backend module, backend/api/dashboard.py, rather than a Next.js server component querying Postgres directly. That choice was deliberate, not a default:

A Next server component reading Postgres directly would need a second, independent SQL client speaking TypeScript, duplicating exactly the schema knowledge backend/database/{repository,review_store}.py already encode — the two would drift the moment one side changed a column or a query without the other noticing. Every prior milestone in this project has kept the architecture inward-only (ADR-002: outer layers depend on inner ones, never the reverse, enforced by lint-imports); a second database client living in frontend/ would be a load-bearing exception to that rule for no real benefit, since a thin JSON API costs almost nothing to add and keeps exactly one component (EventRepository) responsible for knowing what a row in agent_events means.

3Why pr_cost_hourly doesn't exist

PLAN.md's original M13 text described the cost view as reading "from the continuous aggregates" — specifically a TimescaleDB materialized view named pr_cost_hourly, alongside agent_health_1m. Both are M12 (Tiger Cloud Migration) deliverables. M12 needs a real Tiger Cloud account this project does not have, and was disclosed as deliberately skipped when M13 was scoped — so pr_cost_hourly was never going to exist for M13 to read from, continuous aggregate or otherwise.

What stands in for it is plain SQL over the same rows a continuous aggregate would eventually pre-summarize: EventRepository.aggregate_llm_calls_by_agent, which groups real, unaggregated agent_events rows by (agent, model) — the same grouping key a TimescaleDB continuous aggregate over this data would use. The method's own docstring names this explicitly as an M12 swap point, and the swap really is narrow:

Now (M13, plain SQL)

FROM agent_events
WHERE event_type = 'llm.call'
  ...
GROUP BY agent, model

Later (M12, continuous aggregate)

FROM agent_health_1m   -- or
                       -- pr_cost_hourly
GROUP BY agent, model  -- (or SUM of
                       -- pre-summed buckets)

Only this one method's FROM/GROUP BY would change — the call site (backend.api.dashboard.get_agent_metrics) and the method's own return shape (AgentMetrics) stay exactly as they are, because a continuous aggregate grouped the same way produces rows shaped identically to what this query already returns. This is the same "structure the stand-in so the real swap is narrow" discipline this project has used before — M9's fixture embedder and M11's mock GitHub client were both built the same way, satisfying the same Protocol/shape the real implementation would.

4The centerpiece: $97,468.71

The plain-SQL query above is exactly correct at what it was written to do: sum every llm.call row's cost_usd, grouped by (agent, model). The defect wasn't in the arithmetic — it was in what the query was summing.

This project's own test suite has, since M8, occasionally written fixture rows carrying deliberately far-future timestamps directly into the real agent_events table — not a mistake, but a genuine test-isolation technique: pin a row to 2030 so it can never collide with "today"'s real spend window, prove BudgetGuard correctly ignores it, done. That technique works perfectly for the query it was designed against (sum_llm_cost_for_day, bounded to [day_start, day_start + 1 day)). Nobody had written a query that summed all time before M13's cost view did — and when they did, every one of those 2030-dated rows, still sitting in the append-only table years later, landed in the same bucket as a genuine call.

What an independent L4 VERIFY session actually found
19 rows dated in 2030, ~$40,261, at the exact same (agent='security', model='claude-haiku-4-5') key genuine calls use — no date filter, no test-prefix exclusion, no provenance flag anywhere in the query or the API layer. /costs rendered total_cost_usd: "97468.709561". The real number was $0.076917.

The reason this cleared $97,468 and not merely $40,261 matters: those 19 future-dated rows were not the only synthetic rows in the table. 170 total rows carried the budget-guard- prefix from this same fixture generator — only 19 of them future-dated (2030); the other 151 were past-dated, written to 2020-06-14/15 before this project's own M8 schema-isolation fix landed. A filter that only excluded future timestamps would have caught the 19 and silently missed the 151 sitting right alongside them, still masquerading as real spend from years ago:

Mechanism aloneCatchesMisses
Future-dated only (ts > now)19 rows (2030)151 rows (2020, same prefix)
Known prefix only (review_id LIKE ...)all 170 budget-guard-* rowsa future-dated row with an unrecognized prefix
Both, combined (what shipped)everything either alone catchesonly an unlisted, non-future-dated synthetic prefix — see the honest limit below

That's why the fix runs both mechanisms deliberately, not either one alone: the real production data contained cases only one alone would have missed. Neither mechanism is redundant with the other.

Why "reads a real table" wasn't enough to be honest

Before the fix, the homepage's own copy claimed "Nothing on these pages is fabricated" — and in one narrow, literal sense that was even true: /costs never invented a number, never rendered a placeholder, and every figure it showed came from a real SQL query against a real table. But "sourced from a real table" and "honest" are not the same claim. A query is only as honest as what it chooses to include, and this one included test fixtures a human operator had no way to distinguish from their own team's genuine Anthropic spend. An operator reading $97,468.71 on a Sunday morning would have no reason to doubt it — the page said, in as many words, that nothing on it was fabricated.

Why silently dropping the rows would have been its own honesty problem

The obvious-looking fix is "just filter the synthetic rows out and move on" — and the query-level filter is exactly what shipped. But a dashboard that silently drops 255 rows and says nothing about it has swapped one kind of dishonesty for another: an operator now sees a small, clean number with no way to know that ~$97,468 of activity in the underlying table was quietly excluded from what they're looking at. That's a real difference from "there was never anything to exclude." So the fix pairs the filter with an ExclusionSummary — row count and dollar total, broken down by which mechanism excluded each row — returned alongside the honest totals and rendered on /costs in its own disclosure card:

Exclusions (transparency, not silence)

255 rows excluded, $97,468.632644 total — 19 future-dated ($40,261-ish) + 151 past-dated test-fixture rows + overlap, broken out by mechanism. Not hidden; not mixed in.

The homepage's claim was rewritten to match: it now says every figure is a real query result while disclosing, in the same breath, that the underlying tables can (and did) contain synthetic rows the Cost & Latency view filters out and discloses — rather than either silently mixing them in (the original defect) or silently dropping them (the failure mode the disclosure card exists to avoid).

The honest limit: a denylist, not an allowlist

The second, independent L4 VERIFY session that ultimately APPROVEd M13 did not stop at re-checking the arithmetic. It classified every distinct review_id prefix present in the real database itself — not trusting the fix session's own list — and found no false negatives in the seven prefixes the fix excludes. Then it went further: it opened a transaction, inserted a today-dated row under a prefix not on the exclusion list, queried /costs, confirmed the row counted as real spend, and rolled the transaction back rather than leaving a stray row in the real database.

The ruling
The exclusion mechanism is a denylist — a best-effort, code-level list of known-synthetic prefixes — not an allowlist that could prove a row real. A row can be wrong in a way this filter cannot catch: today-dated, from a genuinely new (or renamed, or buggy) fixture generator nobody has grep-verified yet. Nothing about this makes the fix wrong to land now — the alternative, a hard allowlist that only counts rows carrying an explicit provenance flag, needs a schema change this milestone did not make. It is a real, disclosed limit, not a hidden one.

5The real root cause

The exclusion filter is the correct fix to land in this milestone — but it is a compensating control, not the fix for the actual defect. The actual defect is that this project's own tests write fixture rows directly into the real, production, append-only agent_events table at all, rather than into a disposable schema nothing downstream ever has to filter back out.

Two of this milestone's own test files already show what the correct pattern looks like: test_budget_guard_events.py and the new test_dashboard_api.py both use per-run disposable schemas — a real Postgres connection, but to a schema created fresh for that test run and torn down after, never the shared production table. test_events_spine.py, an M7 test file, was never migrated to that pattern: it still writes fixture rows (roughly 4 per run) directly into production agent_events on every free pytest run — and because the table is append-only by its own design (a database-level trigger this project built specifically to make deletion impossible even for a superuser), those rows are permanent. Every additional session that runs the free suite adds a few more rows a future query will need to know to exclude.

A filter that lists known-synthetic prefixes will always be chasing whatever new prefix the next un-migrated test file happens to invent. Migrating test_events_spine.py to a disposable schema would stop the bleeding at the source — the filter would then be a belt-and-braces safeguard against old, already-written rows rather than the only thing standing between a new test fixture and a future operator's real cost figure. This was judged correct to log as follow-up, not to fix inside this same session — see checkpoints/CURRENT.md's Deferred list.

6LLM-as-judge: who checks the checker

The regression gate needs something that can read a produced Review and decide, in the same way a human reviewer would, whether it's actually good — a judgment call, not a diffable assertion. backend/evaluation/judge.py's AnthropicJudge makes that call by asking a second LLM to score the candidate review against a golden case's expected findings.

Why the judge can't be the model that wrote the review
The four specialists all call claude-haiku-4-5. The judge deliberately calls claude-sonnet-5 instead — a different, stronger model in a different tier. A model judging its own family's blind spots is a weaker check than an independent model grading it: any systematic bias haiku-tier reviews share (a class of finding they're prone to miss, a phrasing they're prone to hallucinate) is exactly the kind of error a same-family judge is least likely to catch, because it may share the same blind spot.

The regression gate (backend/evaluation/regression_gate.py) averages the judge's score across the 4-case golden dataset and passes iff the mean is >= 0.700. That threshold is a deliberate middle, not a round number: the dataset mixes a hard must-catch case (missing a real SQL injection scores that case ≤ 0.4 under the judge's own rubric) with softer, nice-to-catch cases. Set the bar at 0.9, ordinary judge scoring noise would flip the gate on reruns with no real regression; set it at 0.5, a pipeline that silently stopped catching the SQL-injection case entirely could still pass by acing the softer cases. 0.700 requires catching essentially every must-detect finding while tolerating normal noise on the rest.

The honest measurement

An LLM judge is itself an unreliable instrument, and this project measured that rather than assuming it away. pytest -m live tests/eval/test_regression_gate.py -v made 9 real claude-sonnet-5 calls across this milestone's sessions, scoring the same golden case ("sqli-basic") repeatedly on both a genuinely correct review and a deliberately bad one. The result: zero within-group variance was measured — the judge gave the identical score to the identical input every time it was re-run — but across all 9 calls, no score ever landed inside the 0.65–0.75 band that would actually test the gate's threshold under realistic ambiguity. Zero variance on the cases actually measured is a real, reassuring data point; it is also not proof the judge is stable near the threshold that matters, because none of the 9 calls ever approached it.

The other honest limit sits in eval-gate.yml itself: the live-scored class, TestLiveJudgeDistinguishesGoodFromBadReviews, scores exactly one of the golden dataset's 4 cases on every trigger — including the weekly cron meant to catch silent drift. The other three golden cases (clean-code false-positive avoidance, docs/tests-soft-expectation cases) are exercised only by the free, canned-judge test classes, which prove the gate's own pass/fail arithmetic but never actually re-score those cases with a real model. A regression specific to those three case types — the pipeline starting to hallucinate findings on clean diffs, say — would not be caught by any currently-scheduled live run.

7CI: a green check that ran nothing

.genesis/DONE.html section 2 has carried a project-wide gate since M1: "Every CI job references test files that exist; CI is green on a clean checkout." It sat N/A for twelve milestones because this project had no CI workflow to check at all — a direct, deliberate reaction to the reference implementation this project studies, whose own CI workflow pointed at two test files that do not exist in that repository. A CI badge showing green tells a reader "nothing is currently broken." A CI badge that is green because the jobs it runs can't even find the files they're supposed to test is worse than having no badge at all — it actively asserts something false, with the specific authority a green checkmark carries.

.github/workflows/ci.yml is M13's answer: every run: step's referenced path was confirmed to exist before the workflow was committed, across 5 jobs — lint (ruff), typecheck (mypy --strict), imports (lint-imports), the free test suite (against real Postgres/Redis/pgvector service containers), and the frontend build. All 5 went green on the very first push to a real PR — not a claim taken on faith, but this milestone's own build report's first real-world test of the workflow file it had just written.

eval-gate.yml, the billable judge workflow, is deliberately a separate file from ci.yml — every ci.yml job is free by construction (pytest's own addopts deselects every live-marked test by default, and the workflow never sets an API key at all), so a contributor opening a routine documentation PR never spends anyone's money just by pushing. eval-gate.yml is where the real cost lives, and it is exactly the workflow M13's own L4 VERIFY REJECT centered on:

  1. L1 BUILD eval-gate.yml triggered on workflow_dispatch and a Monday 06:00 UTC cron only — reasoned, at the time, as keeping routine development free of charge. It never ran on a pull_request, so it structurally could not be wired up as a required status check.
  2. L4 VERIFY REJECT The milestone's own outcome text claimed the gate "blocks a merge that degrades review quality." An independent verifier pointed out that was false as written — nothing here could stop a quality-degrading PR from merging, no matter how badly it scored, because the gate never saw the PR at all.
  3. L2 DEBUG Added a pull_request trigger targeting main, kept workflow_dispatch/the weekly cron unchanged, and added a "Guard" step that fails loudly — with a message distinct from a missing-secret failure — when the run is on a fork PR, since GitHub Actions structurally withholds repository secrets from fork-PR pull_request runs; no amount of re-adding the secret fixes that, and a fork PR is not silently skipped or vacuously passed.
  4. L4 VERIFY APPROVE Confirmed the fix by inspection (actionlint and a real YAML parse clean, every referenced path confirmed to exist) — a real fork-PR run and a real required-status-check configuration could not be simulated locally, so those remain open items, not false claims.
Still open: running on every PR is not the same as blocking one
eval-gate.yml now genuinely runs on every pull request targeting main. But main currently has no branch protection at all — gh api repos/.../branches/main/protection returns a plain 404. A workflow that runs and fails does not stop a merge unless it is configured, on GitHub's side, as a required status check. That is a one-time, repo-admin setting this session did not have the standing to make unilaterally — logged as the sharpest open item in this milestone's Deferred list, not silently left implied.

8Quiz

Three questions. Click each one to reveal the answer.

1. `/costs`' fix could have shipped as "just filter the synthetic rows out of the SQL query" with no visible change to the page beyond a smaller number. Why did the actual fix add a whole "Exclusions" disclosure card instead of quietly filtering and saying nothing?

A dashboard that silently drops 255 rows worth ~$97,468 and shows a small clean number instead has traded one honesty problem for another — an operator has no way to know that activity was excluded from what they're looking at, only that the number looks trustworthy now.

The whole reason a dashboard exists is that an operator trusts the number on the screen without going to check the database themselves. Silent inclusion (the original bug) breaks that trust one way — a wildly wrong total. Silent exclusion would break it a different way — a plausible-looking total that hides how much was quietly removed to make it look that way. The ExclusionSummary/disclosure-card design gives the honest total AND tells the operator exactly what was excluded and why, so neither failure mode applies.

2. The fix excludes rows two ways at once: future-dated (`ts > now`) AND a list of known test-fixture `review_id` prefixes. Given that every future-dated row in the real database WAS a synthetic fixture row, why wasn't the future-dated check alone sufficient?

Of the 170 `budget-guard-*` fixture rows in the real database, only 19 were future-dated (2030); the other 151 were past-dated (2020-06-14/15), written before this project's own M8 schema-isolation fix landed. A future-date-only filter would have caught the 19 and silently missed the 151 sitting right next to them.

The two mechanisms cover different, non-overlapping gaps: a future timestamp alone proves a row can't be real (nothing in this system's real call path can produce a `ts` ahead of `now()`), regardless of its `review_id`; a known test prefix proves a row is synthetic regardless of its timestamp. Each catches real production cases the other alone would have missed — which is exactly why the fix runs both, not either.

3. The second, independent L4 VERIFY session ran a rolled-back-transaction probe: insert a today-dated row under an unlisted `review_id` prefix, check `/costs`, then roll back. What did that probe prove, and why did it not block APPROVE?

It proved the unlisted row still counted as real spend — the exclusion mechanism is a denylist (a best-effort list of known-synthetic prefixes), not an allowlist that could positively verify a row is genuine.

That's a structural, disclosed limit, not a defect the fix was supposed to close: a hard allowlist that only trusts rows carrying an explicit provenance flag would need a schema change this milestone didn't make. The verifier judged the shipped denylist the correct fix to land now — it closes the two real, concretely-triggered defects (the 19 future-dated and 151 past-dated rows) — while recording the allowlist-vs-denylist gap as exactly the kind of honest limit this project's own discipline requires disclosing rather than hiding.
