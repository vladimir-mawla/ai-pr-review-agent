Webhook Ingress: HMAC + Idempotency

1Background

M1 defined the shapes (Finding, Review, WebhookEvent) but built nothing that talks to the outside world. M2 is the first milestone where an actual HTTP request from an actual untrusted network reaches this codebase: a POST /webhook route that GitHub calls every time a pull request is opened, synchronized, or reopened on a repo this system watches.

The project's locked spec (DONE.html §1) states the trust boundary plainly: "Everything from GitHub is untrusted until its HMAC signature verifies." That is not a throwaway line — it is the entire reason M2 exists before M3's real queue or M4's orchestrator. /webhook is a public URL. Anyone who discovers it can craft a JSON body that looks exactly like a GitHub pull_request event and POST it. Without a signature check, that forged request would sail through parsing, get enqueued, and eventually trigger four LLM agents to review a "pull request" that was never actually opened on GitHub — at minimum a cost/DoS problem, at worst a way to feed poisoned diff content into whatever posts back to the real repo later.

GitHub's own mechanism for this is documented and specific: every webhook delivery carries an X-Hub-Signature-256 header, computed as hmac-sha256(secret, raw_request_body), plus an X-GitHub-Delivery header — a UUID unique to that one delivery attempt, repeated unchanged on a retry. M2's job is to use both correctly.

2The intuition: three steps, in order

backend/webhook_receiver/router.py opens with a comment that is also the entire design of the milestone: 

1. Verify the HMAC-SHA256 signature over the RAW request body — reject
   forgeries before any other work happens.
2. Check the X-GitHub-Delivery idempotency key so a retried delivery
   is not processed twice.
3. Enqueue the job (behind the JobQueue interface) and return 200
   immediately.

Nothing else. No parsing before step 1, no queue lookups before step 1, and critically, no actual review work happens in this request path at all — not even in M2, and not in M3 or beyond either. GitHub enforces a short response timeout on webhook deliveries and will mark the delivery failed (and retry it, repeatedly, on its own schedule) if the endpoint doesn't acknowledge quickly. A handler that tried to run the four specialist LLM agents synchronously, inline, before returning 200 would routinely time out — and worse, a slow-but-eventually- successful handler would still get retried by GitHub because the ack never arrived in time, causing duplicate work on top of the timeout.

Why "enqueue and return" is the whole contract
The webhook route's job is to turn an HTTP request into a reliably-recorded fact ("this delivery happened, do the work exactly once") as fast as possible, then get out of the way. Everything expensive — diff retrieval, four LLM calls, aggregation — belongs on the far side of a queue, in a worker that can take as long as it needs without an HTTP client (GitHub) waiting on it. M2 doesn't build that worker yet (that's M3); it builds the interface the worker will sit behind, so the request path never has to change shape once the queue is real.

The three steps also explain the milestone's name directly: HMAC is step 1, idempotency is step 2, and step 3 (enqueue) is what both of the first two exist to protect.

3HMAC over raw bytes, not re-parsed JSON

router.py calls await request.body() and passes those exact bytes into verify_signature before touching json.loads at all: 

raw_body = await request.body()

# Step 1: verify the signature over the RAW bytes, before anything else.
signature_header = request.headers.get(_SIGNATURE_HEADER)
verify_signature(raw_body, signature_header, settings.github_webhook_secret)

# Only now, with a verified signature, do we parse the body at all.
payload: Any = json.loads(raw_body)

This ordering is not a style choice. GitHub computes its signature over the literal bytes it sends on the wire — whatever whitespace, key ordering, and unicode escaping its JSON serializer happened to produce that day. If this codebase instead did payload = json.loads(raw_body) first and later re-serialized payload (say, with json.dumps(payload)) to compute the HMAC, the digest would almost certainly come out different — Python's json module does not promise to reproduce GitHub's exact byte sequence, and doesn't need to for the parsed data to be "the same." A correctly-signed, unmodified, genuine GitHub delivery would then fail verification, indistinguishable from a forgery.

Parse, then re-serialize, then hash

{"action":"opened","pr":1} on the wire becomes a Python dict, then json.dumps() might emit {"action": "opened", "pr": 1} — extra spaces, maybe different key order under some code paths. Different bytes, different HMAC. A genuine request now fails verification through no fault of the sender.

Hash the raw bytes first

raw_body is whatever arrived on the socket, untouched. hmac.new(secret, raw_body, sha256) reproduces exactly what GitHub computed on its side, because both sides are hashing the identical byte sequence — not two independent serializations of "the same" logical data.

This is also why verify_signature's own docstring calls this out explicitly as a precondition of the function, not an implementation detail: whatever calls it must pass the untouched wire bytes, or the whole verification is meaningless regardless of how carefully the comparison itself is done.

4Why hmac.compare_digest, not ==

Once both sides have a 64-character hex digest — the one GitHub sent, and the one this code computes from the raw body and the shared secret — validator.py compares them with: 

if not hmac.compare_digest(expected_hex, provided_hex.lower()):
    raise InvalidSignatureError("signature does not match computed HMAC")

Two strings that are equal in value can still be unequal in how long Python takes to notice. Python's == on strings compares byte by byte and stops at the first mismatch — that's a completely reasonable thing for a language to do, and normally invisible. But it means "abc123" == "abc999" and "zzz123" == "abc999" take measurably different amounts of time: the first mismatches at position 3, the second at position 0, so the first comparison does more work before giving up.

Now imagine an attacker who can submit a guessed signature and measure how long the server takes to respond "invalid" — over a network, with enough repeated samples to average out noise, this is a documented, practical attack. If this code used ==, an attacker could try a signature that's wrong everywhere, then change just the first hex character and try all 16 possibilities, keeping whichever one made the response take fractionally longer (because == got one character further before bailing out). Repeat for the second character, then the third, and so on — 64 rounds of roughly 16 guesses each (about 1,024 total attempts) recovers the entire correct signature, instead of needing to brute-force all 2256 possible digests at once.

Guess digest, measure response latency for each of 16 values at position 0
↓ keep the slowest-to-reject guess — it matched one more byte than the rest
Fix that byte, repeat for position 1, then 2, then 3 …
↓ after 64 rounds
Full 64-character signature recovered without knowing the secret

hmac.compare_digest defeats this specific attack by comparing every character before deciding on an answer, regardless of where — or whether — a mismatch occurred, so the function takes the same amount of time whether the first byte is wrong or the last one is. There's no early exit for an attacker's timing measurements to detect, so no partial "warmer/colder" signal ever leaks through response latency. This is the one line in the whole milestone that validator.py's own comment calls "the actual point of this module" — everything else (the prefix check, the length check, the hex check) is just getting two strings into a state where this comparison is meaningful.

5Three rejection cases, kept separate

validator.py defines three distinct exception types instead of one generic SignatureError, and the router maps each to a different HTTP status code:

CaseExceptionStatusMeaning
X-Hub-Signature-256 absent MissingSignatureError 401 No credential was presented at all — an auth failure.
Header present but not sha256=<64 hex chars> MalformedSignatureError 400 The request itself is garbled — wrong prefix, wrong length, non-hex characters. Not a security decision, a shape problem.
Well-formed header, digest doesn't match InvalidSignatureError 401 A credential was presented and it's wrong — the auth failure the whole module exists to catch.

Collapsing these into one generic "signature failed, return 401" would lose real diagnostic value and blur two very different situations. A 400 for a malformed header tells whoever configured the GitHub App (or a test writing a malformed fixture on purpose) that the request shape itself is broken — check the header format, not the secret. A 401 says the shape was fine but the credential was wrong — check the secret, or suspect a forgery. Keeping them as separate exception types in validator.py is also what makes the router's three-branch except block in receive_webhook possible at all: the module that knows why verification failed hands that reason to the module that knows which status code that reason deserves, instead of one function trying to do both jobs.

A known rough edge in this split
_is_hex currently checks hex-ness with int(value, 16), which is more permissive than "every character is 0-9/a-f/A-F" — Python's integer parser also accepts a leading +/- sign and underscore digit separators (e.g. int("dead_beef", 16) succeeds). A 64-character digest containing an underscore would currently pass this shape check and only get caught later by compare_digest rejecting it as a plain mismatch — surfacing as InvalidSignatureError (401) instead of MalformedSignatureError (400). Not a security hole (the request is still rejected either way), but it blurs exactly the distinction this section just described. Recorded as a deferred cleanup in checkpoints/CURRENT.md rather than fixed as a drive-by change during this bookkeeping pass.

6Idempotency: why it comes second

GitHub retries webhook deliveries it doesn't get a timely 200 for, resending the identical body with the identical X-GitHub-Delivery UUID. Processing that retry as a brand-new event would enqueue (and eventually review) the same pull request twice. The fix is what JobQueue.enqueue() guarantees: calling it twice with the same delivery_id is a no-op the second time.

But the order in router.py matters as much as the mechanism. Signature verification (step 1) runs to completion — including raising an HTTPException that returns 401 or 400 — before the delivery ID is even read off the request, let alone checked against the queue's seen-set (step 2). This isn't incidental; it's the only ordering that makes the idempotency guarantee mean anything.

Attacker sends unsigned/forged request with delivery_id = "real-future-uuid"
↓ if idempotency were checked before signature verification…
"real-future-uuid" gets marked seen in the queue's dedup set — for free, with no valid credential
↓ minutes later, GitHub sends the real delivery with that same UUID
Legitimate, correctly-signed delivery is silently treated as a duplicate and dropped

That is the concrete attack this ordering prevents: an idempotency store keyed on an attacker-controlled, unauthenticated header (X-GitHub-Delivery is just a request header — nothing about it is signed or verified on its own) would let anyone who can guess or predict a future delivery ID poison the dedup set ahead of time. The real event, when it eventually arrives with a valid signature, would look like "we've already seen this one" and get quietly discarded — a denial-of-service against one specific pull request's review, achievable without ever forging a valid signature.

Checking the signature first closes this off completely: an attacker who cannot produce a valid HMAC for any body never gets far enough into receive_webhook to touch the delivery ID or the queue at all — the request is rejected with 401/400 at step 1, before parse_pull_request_payload or queue.enqueue are even called. Only a request that has already proven it came from someone holding the shared secret gets to participate in the idempotency mechanism.

7The JobQueue interface, one milestone early

M3 is the milestone that adds a real, durable queue (Dockerized Redis + ARQ). M2 has no need for one — there's nothing to hand work off to yet, since M4's orchestrator doesn't exist. So why does M2 introduce backend/job_queue/interface.py (a Protocol) and backend/job_queue/in_memory.py (a concrete, process-local implementation) now, instead of waiting?

Because the router needs something to call in step 3, and the shape of that call — queue.enqueue(event) -> EnqueueResult, where a repeated delivery_id returns enqueued=False instead of raising — is exactly the idempotency contract the previous section depends on. Coding router.py against a concrete InMemoryJobQueue directly would work fine for M2's own tests, but it would mean M3 has to go back and edit the router, and every test that constructs it, just to swap in Redis. Coding against the JobQueue Protocol instead means M3's job is purely additive: write a new class that satisfies the same two methods (enqueue, size), and change one line in backend/api/main.py's create_app() default. The router, test_webhook_validator.py, and the idempotency guarantee itself don't move.

interface.py

JobQueue (a Protocol) plus EnqueueResult, a frozen dataclass carrying enqueued: bool and delivery_id: str. The idempotency contract — "twice with the same delivery_id must not double-enqueue" — is documented on the Protocol itself, not left implicit.

in_memory.py

InMemoryJobQueue: a set[str] of seen delivery IDs plus a list[WebhookEvent] of accepted jobs, both held in process memory. Explicitly not durable, not shared across processes, and not thread-safe under concurrent writers — acceptable for a single FastAPI instance in tests and a local demo, not for production.

This is the same "enforce the boundary in code, not in a comment" idea M1 used for backend/core's dependency direction, applied one layer up: the request path is written against an abstraction on purpose, before the concrete implementation on the other side of it is real.

8Known limits, stated honestly

L4 VERIFY approved M2 — the demo command passes, the four gates are green, and the milestone did what its plan entry committed to. It also flagged real limitations that are out of scope for what M2 promised, rather than treating them as blockers:

  1. InMemoryJobQueue's _seen_delivery_ids set grows unboundedly. Nothing ever removes an entry, so a long-running process accumulates one string per delivery forever. Fine for a test suite or a short local demo; not fine as a standalone production component. M3's real Redis/ARQ queue is expected to bring its own eviction (a TTL on dedup keys), which is exactly why this in-memory version wasn't over-engineered with one — it exists to unblock the router, not to be the long-term answer.
  2. No maximum request body size is configured. router.py calls await request.body() unconditionally, buffering and later hashing whatever arrives, however large. A local demo or a test suite never sends anything adversarial, so this doesn't show up yet — but M11 (real GitHub integration, exposed to the internet) is exactly the point where an unbounded body becomes a memory / CPU exhaustion vector and needs a hard limit before that milestone ships.
Why not just fix these now
Both are real, but neither is what M2's plan entry or the security gate in DONE.html actually asked for at this stage — M2's job was "HMAC verified and idempotency checked before any work is enqueued," which the demo command and the 23 webhook tests do prove. Recording the gaps in checkpoints/CURRENT.md keeps them visible for M3 and M11 respectively, instead of quietly forgetting them or scope-creeping this milestone to cover work two and nine milestones away.

9Quiz

Three questions. Click each one to reveal the answer.

1. Why does router.py call await request.body() and verify the signature before ever calling json.loads on it?

Because GitHub's signature is computed over the exact bytes it sent on the wire, and parsing-then-re-serializing would almost certainly produce different bytes.

hmac.new(secret, raw_body, sha256) only reproduces GitHub's digest if raw_body is the literal, untouched byte sequence GitHub hashed on its side. If the code parsed the JSON into a Python dict first and later re-serialized it to compute the HMAC, whitespace and key-ordering differences introduced by re-encoding would change the byte sequence and the digest — making even a genuine, unmodified GitHub delivery fail verification through no fault of the sender.

2. An attacker who cannot forge a valid signature sends a request with X-GitHub-Delivery: some-future-uuid. What stops them from poisoning the idempotency store for that UUID?

The router checks the signature (step 1) before it ever reads the delivery ID or touches the queue (step 2), so an unsigned/forged request never gets far enough to affect the dedup set.

If idempotency were checked first, an attacker could mark any UUID "seen" with no valid credential at all, so a legitimate delivery with that same X-GitHub-Delivery value would later be silently treated as a duplicate and dropped — a denial-of-service against a specific PR's review. Because verify_signature raises (and the router returns 401/400) before queue.enqueue is ever reached, only requests that already proved they hold the shared secret can influence what the queue considers "seen."

3. Why does M2 introduce a JobQueue Protocol and an in-memory implementation now, when the real Redis/ARQ queue isn't built until M3?

Because the router needs something to call in step 3 (enqueue), and coding it against an abstraction means M3 can swap in a real queue without touching the router, its tests, or the idempotency guarantee at all.

InMemoryJobQueue is a deliberately minimal stand-in — not durable, not shared across processes, with an unbounded dedup set — that exists purely so receive_webhook has a real, working target for queue.enqueue(event). Because the router is written against the JobQueue Protocol and not this concrete class, M3's job is purely additive: implement the same two methods against Redis/ARQ and change one default in create_app(), rather than rewriting the request path.
