First Real Specialist Agent (LLM-Backed)

Every milestone through M7 was deterministic: the same input always produced the same output, and every test could assert exact equality. M8 replaces the canned SECURITY stub with a real call to claude-haiku-4-5 — the first point in this system where that stops being true. This page covers the schema wall that keeps a non-deterministic response from reaching the rest of the pipeline unchecked, the empty-vs-invalid distinction that decides whether a clean diff is misrouted to human review, a centralized BudgetGuard that bit its own test suite twice before the query itself was fixed, a non-retryable-error bug that only a real (rejected) credential could have found, and — the actual point of all of it — what the model produced when it finally ran for real. 1Background: the last deterministic milestone was M7

By the end of M7, this system had a webhook receiver, a Redis-backed queue, a LangGraph orchestrator fanning out to four specialist "agents," an aggregator with a confidence-weighted human-in-the-loop (HITL) gate, a reliability layer (retry / circuit breaker / timeout), and an append-only Postgres events spine recording everything that happened. None of the four specialists — SECURITY, QUALITY, TESTS, DOCS — did any real analysis: each was a canned M4 stub returning a fixed Finding with a fixed confidence, so every review the system produced was a deterministic function of its inputs.

M8's outcome, verbatim from PLAN.md: "the security agent makes a real call to the driver model (claude-haiku-4-5) against a fixture diff, and its raw output is parsed through the Finding Pydantic schema before anything downstream sees it — the first point real model behavior enters the system." That sentence is doing a lot of work: it names both what changed (SECURITY becomes real) and the one thing that must exist around it before the change is safe (a schema wall between the model's raw text and everything downstream that assumes well-typed Finding objects).

2Why a real LLM call is a threshold, not just another feature

Every prior milestone's test suite could assert exact output: "this signed payload returns 200," "this job appears in the worker's log," "this collision keeps the CRITICAL finding." A real model call breaks that assumption at its root — the same diff sent twice can come back phrased differently, with a different confidence, in a different key order, or (rarely, but demonstrably, since it is what this milestone had to build defenses for) wrapped in markdown, or preceded by a sentence of commentary, or missing the wrapping object entirely. Nothing downstream of this call — the aggregator's dedupe, the HITL gate's threshold comparison, agent_events' NUMERIC(4,3) confidence column — was built to tolerate an arbitrary string. It was built to tolerate a Finding.

The threshold, stated plainly

Before M8: every code path from webhook to posted review is a pure function, replayable byte-for-byte. After M8: one call in that path talks to a system whose output is drawn from a distribution, not a lookup table. Everything this milestone built — the parser, the two forced-HITL fallbacks, BudgetGuard — exists to make that one non-deterministic call safe to have in an otherwise deterministic pipeline, not to make the pipeline non-deterministic everywhere.

3The schema wall: drift modes a real model actually produces

backend/agents/response_parsing.py's parse_findings_from_llm_response is that wall. It is told, in the prompt, to return exactly {"findings": [...]} — and then written as if it can't trust that at all:

1. Well-formed

{"findings": [...]} — the happy path.

2. Key drift

A different top-level key, e.g. {"issues": [...]}.

3. Markdown-fenced

The JSON arrives inside a ```json ... ``` fence anyway.

4. Prose-then-JSON

A sentence of commentary before the JSON object starts.

5. A bare list

The wrapping object is skipped: [{...}, {...}] directly.

6. Total garbage

No JSON at all, or every extracted item fails Finding validation.

Cases 1–5 all resolve to a real list[Finding] — the extraction logic tries a fenced block, then a bare JSON structure, then walks the alternate key list, then falls back to treating the whole payload as a list. Every recognized item is validated individually against the Finding Pydantic model; one malformed item (a hallucinated severity string, a missing field) is logged and dropped rather than discarding its valid siblings — "one bad item" and "the whole response is garbage" are different failure severities, and the parser distinguishes them instead of treating any error as total failure.

Case 6 — genuinely unrecoverable input — is where this module deliberately stops being tolerant and raises ResponseParseError, on purpose, rather than quietly returning []. What that exception means, and why an empty list would have been the wrong choice even here, is section 4.

4Empty vs. invalid: the distinction that decides HITL routing

This is the first of two real bugs the M8 L1 BUILD session caught in its own work, before any independent verifier ever looked at it. The original parser could not tell apart two situations that look identical at the Python level — an empty list — but mean opposite things:

Genuinely empty

{"findings": []} — the model looked at a clean diff and correctly found nothing to flag. This is a valid, confident result.

Every item invalid

The model returned a non-empty list, but every item failed Finding validation — the response is untrustworthy, not merely quiet.

Both cases produce the same Python value at the point the original code checked it: an empty findings list after validation. Collapsing them meant a clean diff — the common case — was misrouted through the forced-HITL CRITICAL fallback path (see section 5) every single time, defeating the entire point of an automated review: it would never auto-post anything.

The fix is a single extra condition, but it's the condition that matters: 

if not findings and items:
    raise ResponseParseError(
        "no valid Finding objects could be extracted from the LLM response"
    )
return findings

ResponseParseError is raised only when the pre-validation items list was non-empty yet nothing in it survived — that is Case 6. When items was empty to begin with, the function falls through and returns the empty list, exactly as a clean diff deserves. Two regression tests (test_empty_findings_list_is_valid_not_an_error, test_empty_findings_list_is_a_real_empty_list_not_a_fallback) pin this: both are proven to fail against the pre-fix collapsed logic and pass after the one-line fix.

Why conflating them is dangerous, not just wrong

A schema-valid Finding is not automatically a correct one — but an incorrectly-routed empty list is worse than either, because it corrupts the meaning of silence itself. If "nothing to report" and "I can't tell you anything trustworthy" produce the same downstream behavior, an operator loses the ability to distinguish "this specialist is confident and clean" from "this specialist's output should not be trusted" — exactly the ambiguity a security review pipeline exists to eliminate, not reproduce.

5The forced-HITL fallback and its collision-proof sentinel

When Case 6 does fire — or, separately, when the security specialist never got to attempt an analysis at all (a budget block, a bad credential, the provider unreachable) — this system does not crash the run and does not return an empty list. It returns exactly one synthetic Finding: CRITICAL severity, confidence 0.000, with a rationale explicitly stating this is not a real security claim.

CRITICAL is deliberate, not decorative. backend.hitl.queue.has_critical_finding — built back at M5 — forces any review containing a CRITICAL finding to human review, unconditionally, regardless of how confident the other three (still-stub) specialists are. A lower-confidence-but-non-CRITICAL fallback could, in principle, still average out above the auto-post threshold if the other specialists were confident enough; a forced CRITICAL cannot. M8 reuses this existing mechanism for two different failure classes instead of inventing a second signal shape:

BuilderFires whenfile_path sentinel
_parse_failure_fallback_findingThe model answered, but its answer was garbage (Case 6)<llm-response-unparseable>
infrastructure_failure_fallback_findingThe specialist couldn't even attempt analysis (BudgetExceededError, LLMConfigurationError, LLMCallFailedError)<security-specialist-unavailable>

Both sentinels use line_start=1, line_end=1. That matters because M5's aggregator dedupes findings by the key (file_path, line_start) — a real collision would mean one sentinel silently absorbing or being absorbed by an unrelated finding that happens to share a location. It can't happen here for two independent reasons: first, neither sentinel file_path can ever be produced by a real diff — angle brackets are not valid path characters a unified diff's +++/--- headers would ever emit, so no genuine Finding can share the key. Second, the two sentinels don't even collide with each other: they use two different literal file_path strings, so a run that (hypothetically) triggered both fallback paths would still keep both forced-CRITICAL findings distinct through dedupe, rather than one silently winning the collision and discarding the other's HITL signal.

6BudgetGuard: one check, one query, one bug that bit twice

backend/economics/budget.py's BudgetGuard hard-blocks — raises, never warns — once today's real spend meets a configured daily cap (default $20). Two design choices are worth isolating from the rest of the milestone:

The check lives inside the client, not inside each node

BudgetGuard.check_and_raise() is the first statement inside AnthropicLLMClient.complete/complete_async — before the underlying Anthropic client is even constructed. The original context-graph.json invariant described a per-node check instead; an independent L4 VERIFY session judged the built, centralized design better (no future caller of complete can forget the check; it covers every current and future call site uniformly, sync or async) and had the invariant text reworded to match reality rather than requiring the code to match a worse design retroactively. It is grep-verifiable: every real Anthropic( construction and every real messages.create call in backend/ resolves to exactly one call site, inside complete, reachable only after check_and_raise() has already run.

Spend is read from M7's events spine, never an in-memory counter

current_spend_usd() queries real agent_events rows, not a process-local variable — a counter would reset on every restart and disagree with any other process spending against the same budget. This is exactly the reason M7 built an append-only events spine with a real cost_usd column: so a later milestone (this one) would have a shared source of truth to query instead of inventing a second, parallel one.

The day-window bug that bit twice

The second bug the L1 BUILD session found in its own work: an integration test proving BudgetGuard reads real spend pinned its fixture rows to a far-future day (2030-06-15) "for test isolation." Because the original query, sum_llm_cost_since, only checked ts >= start_of_today with no upper bound, a row dated in 2030 is still >= today's midnight — it silently counted toward the live budget's real spend. Running the demo CLI immediately afterward raised a spurious BudgetExceededError: spent $2119.000446 of $20 cap, the sum of every future-pinned fixture row the test suite itself had written.

The first attempt at a fix re-pinned the fixture day to the past instead of touching the query — which relocated the symptom without touching the defect. An independent L4 VERIFY session proved this empirically by writing its own 2099-dated boundary-test rows and re-triggering the identical failure mode ($40.00 of a $20 cap). The real fix bounds the query itself to a genuine half-open window and renames it to say what it now does: 

-- before: WHERE event_type = 'llm.call' AND ts >= day_start
-- after:
WHERE event_type = %s AND ts >= %s AND ts < %s   -- [day_start, day_start + 1 day)

sum_llm_cost_since was renamed sum_llm_cost_for_day since the old name no longer described what it does. A future-dated row is now excluded from the day it doesn't belong to — a design decision, not an oversight: the hot-path check stays a single cheap bounded scan rather than growing a second "scan for anomalies" query nobody asked for yet.

Verified against this session's own real data

The two 2030-dated fixture rows ($2119.000446 each) are still sitting in the append-only agent_events table today — they can never be deleted, only excluded. Querying BudgetGuard.current_spend_usd() for real during this session's live-demo closeout returned $0.002408, exactly the sum of three real, same-day llm.call rows — proof the bounded window keeps working against the exact rows that broke the unbounded one.

7Reusing M6, disabling SDK retries, and the bug only a real key could find

AnthropicLLMClient.complete wraps the real anthropic.Anthropic().messages.create(...) call in the exact retry(breaker(timeout(call))) composition RedisJobQueue and EventRepository already use — reused, not reinvented, because a brand-new unprotected outbound call here would violate the same "every outbound call has a timeout / circuit-breaker" gate M6 and M7 were each held to.

The Anthropic SDK client is constructed with max_retries=0: this project's own retry/breaker/timeout stack is the single source of retry behavior. Leaving the SDK's own default (2 retries) enabled underneath it would silently double-retry every failure, confusing both real latency and the exact attempt counts this milestone's fault-injection tests assert on.

The bug: a rejected credential crashed the orchestrator; a missing one didn't

This was found the hard way — while trying to unblock the live demo with what was believed to be a real credential, Anthropic rejected it outright (a genuine 401 authentication_error, confirmed independently with a raw curl). A missing key was already handled correctly: it never reaches the SDK at all — LLMConfigurationError is raised earlier, inside _client(), before any network call is attempted, and security_node already turns that into a forced-HITL finding. An invalid key is a fundamentally similar situation — "the analysis did not happen" — but was not treated the same:

anthropic.AuthenticationError raised by messages.create
↓
call_with_retry: it's in _NON_RETRYABLE_EXCEPTIONS → re-raised immediately, uncaught, on attempt 1 (correct — a bad key must never be retried 3 times)
↓
complete()'s except (RetryExhaustedError, CircuitOpenError): never catches it — it was never wrapped into either
↓
propagates raw out of AnthropicLLMClient, through SecurityAgent.analyze (deliberately doesn't catch infrastructure failures), and crashes security_node

Widening security_node's own catch tuple to also recognize anthropic.AuthenticationError (fixing it at the node) was considered and rejected: it would either require importing the vendor SDK into backend/orchestrator/ — a layering violation this project has never had, since nodes.py has never imported anthropic — or duplicating the SDK's exception list a second time outside backend/tools/llm_client.py, the one module whose whole job is to be that vendor boundary.

The fix is at the boundary instead. complete now also catches anthropic.AnthropicError — the SDK's common base class, covering its entire exception family, not merely AuthenticationError — around the retry/breaker/timeout call, and re-raises it as this project's own LLMCallFailedError: 

except (RetryExhaustedError, CircuitOpenError) as exc:
    raise LLMCallFailedError(
        f"LLM call failed (retries exhausted or circuit breaker open): {exc}"
    ) from exc
except AnthropicError as exc:
    # re-raised immediately by call_with_retry, never wrapped in
    # RetryExhaustedError -- would otherwise escape all the way to
    # security_node, which only recognizes this project's own types.
    raise LLMCallFailedError(
        f"LLM call failed (non-retryable provider error): "
        f"{type(exc).__name__}: {exc}"
    ) from exc

This costs nothing at the already-correct fast-fail path (a bad key still fails on attempt 1, never retried) and means security_node's existing, unchanged catch — BudgetExceededError, LLMConfigurationError, LLMCallFailedError — now reaches it, producing exactly the same forced-HITL synthetic finding a budget block already produces. The non-retryable set also gained RequestTooLargeError (413 — the same "retrying the identical oversized body can never help" family, simply missed before). Transient failures — rate limits, overload, timeouts — stay deliberately retryable; this is not a blanket "never retry the vendor" change, only a fix for the family that can never succeed no matter how many times it's retried.

8What the real call actually produced

With a valid credential finally in place, PLAN.md's exact demo command was run for real: 

ANTHROPIC_API_KEY=... python -m backend.agents.security_agent --diff tests/fixtures/sqli_diff.patch

(run with the key sourced from .env via pydantic-settings, never typed literally on the command line). It exited 0 and printed two findings against a fixture diff containing two real, deliberately planted SQL-injection sinks — string concatenation in find_by_username, f-string interpolation in a new find_by_id_unsafe method:

CRITICAL · app/db.py:15-16 confidence 0.999

"The find_by_username method now uses string concatenation instead of parameterized queries, allowing direct SQL injection via the username parameter. An attacker can inject arbitrary SQL by providing input like "' OR '1'='1"."

CRITICAL · app/db.py:19-20 confidence 0.999

"The find_by_id_unsafe method uses f-string interpolation to build SQL queries directly, allowing SQL injection via the user_id parameter. An attacker can inject arbitrary SQL by providing input like "1; DROP TABLE users;--"."

Both findings validate against the Finding Pydantic schema (checked explicitly via Finding.model_validate on each, not merely by the fact that they printed without error).

Is it actually correct?

Judged against the fixture diff directly, not just against the schema: yes, substantively. Both real SQL-injection sinks were found, categorized correctly (sql_injection), scored CRITICAL with high confidence, and nothing was hallucinated — no third, invented vulnerability, no false claim about an unrelated part of the file. The line ranges are close but not pixel-perfect: the diff's new-file line numbering puts the actual vulnerable query = ... statement for find_by_username at line 16 (the model's reported range, 15–16, includes the preceding comment line rather than the following execute(query) call at line 17) — a one-line imprecision in which lines bound the issue, not a wrong location or a wrong diagnosis. The second finding's range (19–20) lines up exactly with the function definition and its vulnerable query line. A schema-valid finding is not automatically a correct one (see section 4's callout) — this is the case where it happens to be both.

A second, separate real call (passing review_id="m8-closeout-demo2", since the demo CLI itself never passes one — there is nothing to correlate an ad hoc CLI run's spend against) produced a real llm.call row:

modeltokens_intokens_outcost_usdlatency_ms
claude-haiku-4-57972730.0021622735

Hand-checked against backend/economics/pricing.py's table for claude-haiku-4-5 ($1.00 / $5.00 per million input/output tokens): 797 × ($1.00 / 1,000,000) + 273 × ($5.00 / 1,000,000) = $0.000797 + $0.001365 = $0.002162 — exact match.

9Honest limits

  1. No llm.call event on a failed call. AnthropicLLMClient.complete only calls emit_llm_call on success — a call that exhausts retries or hits an open circuit breaker records nothing in agent_events beyond whatever the caller's own error handling logs elsewhere. A future milestone building real alerting/dashboards off the events spine may want a failure-shaped event too; not built here since the outcome/token/cost fields don't have an obvious "this failed" shape without a schema change.
  2. Three specialists are still stubs. Only SECURITY is real. QUALITY, TESTS, and DOCS remain M4's canned findings, per this milestone's explicit scope — M10's job.
  3. complete_async has no live call site yet. The one live call this milestone built runs on a LangGraph worker thread, never an asyncio event loop, so the synchronous complete is correct there. The async path is directly tested (the offload mechanism is proven to work) but unused, forward-looking infrastructure — the same category as M7's own emit_tool_call.
  4. No per-model or per-agent budget breakdown. BudgetGuard sums all llm.call cost across every model/agent/review for the day against one global cap — there is no way today to ask "how much did QUALITY specifically spend."

10Quiz

Three questions. Click each one to reveal the answer.

1. A model response of {"findings": []} and a model response where every item in a non-empty findings list fails Finding validation both produce the same Python value at the point the original (buggy) parser checked it: an empty list. Why must these two cases never be treated the same way?

Because they mean opposite things: an empty findings list from a genuinely empty items list is a valid, confident "nothing to flag" result for a clean diff, while a non-empty items list where every item failed validation means the model's response was untrustworthy garbage. Collapsing them means "the model found nothing" and "the model's output could not be trusted" become indistinguishable.

The real-world consequence was concrete, not theoretical: the original parser routed every genuinely clean diff through the same forced-HITL CRITICAL fallback a total parse failure uses — because it could not tell the two cases apart, it treated the common case (a clean diff) as if it were the rare, alarming one (unparseable output). The fix checks whether the pre-validation items list was itself non-empty before deciding whether an empty result is a clean report or a real failure — if not findings and items: raise ResponseParseError(...) — so only "non-empty input, zero survivors" raises, not "empty input, zero survivors."

2. BudgetGuard.check_and_raise() reads spend via a query bounded to [day_start, day_start + 1 day). An earlier version of the query only checked "ts >= day_start" with no upper bound, and this was "fixed" once by re-pinning a test fixture's future-dated rows to the past instead of changing the query. Why did that first fix not actually work?

Because the defect was in the query, not in any one test's fixture data. An unbounded ">=" query counts any row timestamped today or later — including any future-dated row, from any source, that anyone ever inserts into the append-only table. Re-pinning one test's own fixture rows to a safely-past date only stopped THAT test from re-triggering the bug; it did nothing to stop a different future-dated row from causing the exact same failure.

That's exactly what happened: an independent verifier wrote its own far-future boundary-test rows to check the exact same query, and reproduced the identical class of failure (BudgetExceededError against inflated spend) with its own data. The real fix bounds the query itself to a genuine half-open window, ts >= day_start AND ts < day_start + 1 day, so any future-dated row — regardless of which test, session, or future bug produced it — is excluded from "today's" spend by construction, not by every test author remembering to avoid future dates.

3. anthropic.AuthenticationError was already listed in _NON_RETRYABLE_EXCEPTIONS before the fix in this milestone, so call_with_retry correctly re-raised it on attempt 1 without retrying 3 times. Given that the non-retryable behavior was already correct, why did a bad API key still crash the whole orchestrator run instead of forcing human review?

Because "re-raised without retrying" and "wrapped into this project's own exception type" are two different things, and only the first one was happening. call_with_retry re-raises a non-retryable exception immediately and uncaught -- it never becomes a RetryExhaustedError. complete()'s own exception handler only caught (RetryExhaustedError, CircuitOpenError), so the raw anthropic.AuthenticationError sailed straight past that handler untouched.

From there it propagated through SecurityAgent.analyze (which deliberately does not catch infrastructure failures) and reached security_node, whose catch tuple only recognizes this project's own exception types (BudgetExceededError, LLMConfigurationError, LLMCallFailedError) — never a vendor SDK type — so it crashed the node instead of routing to the forced-HITL fallback a missing key already triggers correctly. The fix adds a second except AnthropicError clause inside complete itself, wrapping the SDK's entire exception family into LLMCallFailedError at the one module whose job is to be the vendor boundary — so the fast-fail behavior stays identical, but the failure now arrives at security_node in a shape it already knows how to handle.
