1Background: why fan-in needs a real merge step

M4 built the fan-out: four specialist nodes (security, quality, tests, docs) run concurrently and each contributes its findings to GraphState.findings via an operator.add reducer — plain list concatenation. That solves the concurrency problem (nobody's write clobbers anybody else's), but it deliberately does nothing else. The join node aggregate_node was M4's last stub: a no-op that just handed the concatenated list onward.

A concatenated list is not a review. Four independent specialists looking at the same diff will often flag the same line for different reasons — security sees an injection risk exactly where docs sees a missing docstring — and a review that shows the human four redundant, uncoordinated comments about one line is worse than unhelpful; it actively erodes trust in the tool. M5's job is to turn "four lists of opinions" into "one coherent, confidence-scored, correctly-routed decision" — the aggregator's whole reason to exist. Concretely, that means three things landing in backend.orchestrator.nodes.aggregate_node for the first time as real logic instead of a stub:

4 specialists' findings
(concatenated, M4)
→
dedupe_findings
→
compute_overall_confidence
→
route_review
→
Review
(POSTED or QUEUED_FOR_HITL)

Every one of those three steps is pure Python over already-produced Finding objects — no LLM call, no I/O — which is exactly what makes the whole pipeline testable with plain fixtures (tests/unit/test_aggregator.py, tests/unit/test_hitl_gate.py) instead of needing a real model in the loop.

2The dedup key: what "duplicate" means here

dedupe_findings groups findings by the exact pair (file_path, line_start). Two findings collapse to one only if they name the identical file and the identical starting line; a finding on the same file at a different line, or the same line number in a different file, is never touched.

Why this key, and not something richer? Because "duplicate" here does not mean "two agents wrote the same sentence" — it means "two agents are both pointing at the same piece of code," which is the situation a human reviewer actually experiences as redundant. Four specialists each running independently over the same diff have no way to know about each other's output before the aggregator sees all four lists at once; the aggregator's whole job is to notice, after the fact, "these two entries are about the same line" and pick the one worth surfacing rather than showing the human all four.

Same file, same line_start

Collapse to one — this is the case the aggregator exists to handle.

Same file, different line

Kept separate — two genuinely different issues, even in the same file.

Different file, same line number

Kept separate — line 42 in app.py has nothing to do with line 42 in utils.py.

A known, deliberately accepted gap
The key is line_start only, not (line_start, line_end). A wide-span finding (say line_start=42, line_end=80) collapses into any other finding that merely shares line_start=42, even one whose own span is a completely unrelated single line. Widening the key to include line_end was considered during the rejection round below and deliberately rejected: it doesn't solve the real problem ("do these two findings' spans actually overlap"), since two spans can overlap without sharing either endpoint. A partial fix that looks complete is worse than an honestly incomplete one — this is recorded as a tracked gap for a future milestone's real interval-overlap logic, not silently dropped.

3Deterministic tie-breaking: not a nuisance, a bug class

Once two findings collide at the same key, dedupe_findings has to pick a survivor. Getting the ranking rule right (severity first — see the rejection below) is one problem; the other, easy to underrate, is making the whole comparison chain deterministic regardless of the order findings happen to arrive in.

That input order is not something the aggregator controls: findings arrive already merged by M4's operator.add reducer across four parallel LangGraph branches, and which branch's write lands first in the merged list is explicitly not guaranteed. A nondeterministic aggregator — one where the surviving finding depends on which specialist happened to finish first — is not merely untidy, it is a correctness bug: the same PR, re-reviewed with no code changes, could get a different verdict purely from scheduling noise. That would make every downstream promise (a CRITICAL finding always escalates, a threshold decision is reproducible) impossible to actually rely on.

The full comparison chain, applied only when two findings share a dedup key:

def _is_better(candidate: Finding, current: Finding) -> bool:
    if candidate.severity != current.severity:
        return _severity_rank(candidate) < _severity_rank(current)     # 1. severity
    if candidate.confidence != current.confidence:
        return candidate.confidence > current.confidence               # 2. confidence
    return _tie_break_key(candidate) < _tie_break_key(current)         # 3. agent -> category -> rationale

Steps 3 onward (agent precedence, then category, then rationale) exist purely so that once severity and confidence are both tied, the result still depends only on fields intrinsic to the findings themselves — never on "which one happened to arrive first in the list." This is why TestSeverityBeforeConfidenceDedupe's tests run each fixture through dedupe_findings in both orderings and assert identical output, and why the property test below goes further still: every one of the 120 permutations of a 5-finding collision (itertools.permutations over one CRITICAL finding plus four rivals) produces the same survivor.

4overall_confidence: an M1 debt that came due at M5

M1 shipped the Review model with an overall_confidence field and no relationship whatsoever to findings: a Review could be constructed with findings averaging 0.500 confidence and overall_confidence set to 0.000, and pydantic accepted it without complaint. M1's own L4 VERIFY flagged this and it was deliberately deferred rather than fixed — nothing in the system yet consumed the field, so a silent inconsistency had no way to cause a wrong decision. It sat quietly correct-by-vacuous-truth for three whole milestones.

Why M5, specifically, is where the debt came due
backend.hitl.queue.route_review is the first piece of code in the entire project that actually trusts overall_confidence to make a real routing decision — post automatically, or send to a human. A field nobody reads can be wrong for free; the moment something reads it to decide whether a human sees the review, "wrong" becomes "silently mis-routes real reviews." M1's deferred gap wasn't a latent bug waiting to fire on its own — it was inert until M5 built the first consumer, which is exactly the shape a lot of real technical debt takes: harmless until something starts relying on the thing that was never actually guaranteed.

The fix is compute_overall_confidence — one formula (mean of the deduped findings' confidence, rounded with ROUND_HALF_UP to 3 decimal places, 0.000 for an empty list) — paired with a Review model_validator(mode="after") that recomputes the expected value and raises ValidationError if the stored field disagrees: 

@model_validator(mode="after")
def _check_overall_confidence_matches_findings(self) -> "Review":
    expected = compute_overall_confidence(self.findings)
    if self.overall_confidence != expected:
        raise ValueError(
            f"overall_confidence ({self.overall_confidence}) does not match "
            f"compute_overall_confidence(findings) ({expected}); construct "
            "Review with overall_confidence=compute_overall_confidence(findings) "
            "rather than an independently-chosen value"
        )
    return self

Two designs were on the table: silently recompute the field from findings whenever they disagree (option A), or reject construction outright (option B, what was built). Option A is tempting — it never crashes — but it means a caller can pass an arbitrary, wrong overall_confidence and have the mistake quietly erased, which hides exactly the kind of bug this fix exists to surface. Option B fails loudly, at construction time, which is what lets a caller's bug be caught in a unit test instead of shipping silently — consistent with the project's stated fail-toward-doing-less philosophy: fail visibly rather than guess correctly by accident.

5The HITL gate: the 0.75 threshold and its boundary

route_review is the decision function: given the deduped findings and the computed overall_confidence, decide POSTED (auto-post) or QUEUED_FOR_HITL (human review), and produce the reason string explaining why. 

auto-post   iff  overall_confidence >= threshold  AND  no CRITICAL finding
human review otherwise

HITL_CONFIDENCE_THRESHOLD defaults to 0.750, a Settings field documented in .env.example. The boundary case — confidence exactly equal to the threshold — is deliberately on the auto-post side, not the human-review side. That reads as an arbitrary pick until you notice PLAN.md's own success criteria phrase it precisely: a review "below" the threshold routes to HITL, which places the threshold value itself outside that condition. test_exactly_at_threshold_auto_posts pins this down with a fixture at confidence 0.750 against a 0.750 threshold, alongside siblings one thousandth on either side, so the boundary can't silently drift to <= in a future edit without a test noticing.

A CRITICAL finding overrides all of this unconditionally — even at confidence 1.000 against a threshold of 0.000, a CRITICAL finding still forces human review (test_critical_finding_forces_human_review_even_with_low_threshold). This is the invariant the rejection below is about: the override only works if a CRITICAL finding actually survives long enough for the gate to see it.

6Anti-drift by construction: the reason string's real bug

DONE.html's M5 gate specifically calls out that "aggregator threshold in code matches the threshold in its user-facing message" — an oddly specific requirement until you know the concrete bug it is worded to prevent. A reference implementation of this exact milestone shape shipped code that checked critical_block_count >= 2 while its human-facing message claimed "3+ agents required" — the number in the comparison and the number in the sentence had drifted apart, silently, because they were two independent literals that someone updated only one of.

route_review's reason strings are built so that class of bug is structurally impossible, not just avoided by discipline: every string interpolates the same threshold parameter the comparison itself uses. There is no second, independently-typed number anywhere in this module's strings: 

if overall_confidence < threshold:
    reason = (
        f"queued for human review: overall_confidence {overall_confidence} is "
        f"below the configured HITL_CONFIDENCE_THRESHOLD of {threshold}"
    )
Verified, not just claimed
This build didn't just reason about the anti-drift design — it empirically reproduced the reference bug and confirmed the test would have caught it: temporarily hardcoded a stale number into the message (reproducing >= 2-in-code / "3+ agents required"-in-message exactly), confirmed test_reason_message_uses_the_configured_threshold_value failed against the tampered file, then restored the real file and confirmed the test passed again. A test that has never been observed to fail is a test whose ability to catch anything is still unproven.

7The rejection: a CRITICAL finding that vanished

This is the centerpiece of M5's history, and it is recorded here in full rather than smoothed into a footnote: M5's first build was rejected by an independent L4 VERIFY session for a real safety bug, not a style nitpick, and the fix that followed had to prove itself against a test shown to fail first.

The bug, concretely

The original dedupe_findings ranked colliding findings by confidence alone — severity played no role in the comparison at all. Two findings collided at app.py, line 42:

AgentSeverityConfidenceRationale
SECURITYCRITICAL0.751SQL injection via unsanitized query parameter
DOCSINFO0.752missing docstring

Under the old confidence-only rule, 0.752 > 0.751 — the INFO finding survives, the CRITICAL finding is discarded. The row struck through above is what the aggregator threw away.

Because has_critical_finding only ever inspects the post-dedupe list — by design, since the HITL gate should only ever see the findings a human would actually be shown — it found no CRITICAL finding at all. route_review then correctly followed its own logic given the (already corrupted) input: no CRITICAL finding, confidence 0.752 above the 0.750 threshold, so it returned POSTED. The review auto-posted, its reason string literally reading "no CRITICAL finding is present" — true of the surviving list, false of what the four specialists had actually found. A real SQL-injection finding was silently discarded and the system told the human everything was fine.

Why the 91-test suite missed it

This is the transferable lesson, and it is a test-design gap, not a test-coverage gap — the M5 L1 BUILD already shipped 91 passing tests. The bug lived exactly in the seam between two halves that were each, individually, thoroughly tested:

test_aggregator.py

Exercised dedupe_findings directly, with fixtures built to test dedup's own rules (agent precedence, category, rationale tie-breaks) — but no fixture happened to pit a lower-confidence CRITICAL finding against a higher-confidence non-CRITICAL one at the same key. The gap in the rule was never exercised because no test shape asked the question.

test_hitl_gate.py

Exercised route_review directly — but always against hand-built finding lists that never passed through dedupe_findings at all. Its CRITICAL-escalates tests constructed a list containing a CRITICAL finding and handed it straight to route_review, correctly proving the gate works given a CRITICAL finding — never proving one would still be there after dedup ran first.

Both halves passed because each one tested its own function in isolation with fixtures crafted for that function's own rules. Neither one tested the actual pipeline aggregate_node runs: dedupe's real output piped into route_review. The integration test in test_orchestrator_fanout.py didn't catch it either, because its four stub findings never collide on the same file+line — dedup is a no-op there by construction. The bug needed all three conditions at once (a real collision, a severity mismatch, dedupe's actual output feeding the gate) and no single existing test created that combination.

The fix and how it was verified

The approved fix reorders _is_better to compare severity first, via an explicit SEVERITY_RANK map added to backend.models.enums — deliberately not derived from the Severity enum's declaration order or member names, so a future reordering of the enum (say, alphabetizing it) can't silently flip the ranking. Confidence is demoted to a tie-break used only within the same severity. Finding.__lt__ was also pointed at the same map, closing a second place the ranking could have drifted from the fix.

  1. A true end-to-end regression test was added — TestDedupeAndRoutingInteraction::test_end_to_end_critical_survives_dedupe_and_forces_hitl — that builds the exact SECURITY/CRITICAL/0.751 vs. DOCS/INFO/0.752 collision, runs it through dedupe_findings then route_review, and asserts QUEUED_FOR_HITL with the CRITICAL finding surviving dedupe.
  2. That test was proven to fail against the old ordering before trusting it as a regression guard: temporarily reverting contracts.py to the pre-fix confidence-only version and re-running just that test reproduces the original bug exactly — AssertionError: assert [Finding(...DOCS...INFO...0.752...)] == [Finding(...SECURITY...CRITICAL...0.751...)] — then restoring the fix turns it back to a pass. A regression test that has never been seen to fail against the bug it names is unproven; this one now is.
  3. The test-design gap itself was closed, not just the one scenario: TestSeverityBeforeConfidenceDedupe parametrizes over every adjacent-and-non-adjacent severity pair where the higher-severity finding has the lower confidence, plus a permutation-based property test asserting a CRITICAL finding survives across every ordering of a 5-finding collision. TestDedupeAndRoutingInteraction now wires dedupe's real output into route_review the same way aggregate_node does, closing exactly the seam the original bug hid in.
Independently re-verified, not just re-run
A first independent L4 VERIFY session found and rejected this bug. A second, separately independent L4 VERIFY session then re-ran all four gates plus the exact demo command against the fixed code, and went further than re-running the unit-level regression test: it confirmed the CRITICAL-survives-dedupe guarantee holds through the actual compiled LangGraph — driving the collision through aggregate_node as the graph's real fan-in node, not only through dedupe_findings called directly — before approving M5.

    Independent session finds the CRITICAL/0.751 vs. INFO/0.752 collision, confirms the review auto-posts with a real CRITICAL finding silently discarded, and rejects M5's L1 BUILD.
  • L2 DEBUG

8The honest consequence of the fix

Severity-first dedupe is a fail-safe change, and fail-safe changes are not free — this one has a real, deliberate cost worth stating plainly rather than glossing over. Consider a HIGH finding at confidence 0.100 colliding with a MEDIUM finding at confidence 0.950. Under the old confidence-only rule, the MEDIUM/0.950 finding would have survived and (all else equal) likely kept the review's overall confidence above threshold. Under the fixed rule, the HIGH finding survives instead — correctly reflecting that it is the more severe issue — but its low confidence pulls the review's mean down, which can push a review from auto-post into human review that the old rule would have posted automatically.

Accepted, not a regression
This lowers the auto-post rate specifically for mixed-severity collisions where the more severe finding also happens to carry lower confidence. That is the correct direction to be wrong in: a system whose failure mode is "asks a human to look at slightly more reviews" is categorically safer than one whose failure mode is "silently discards a CRITICAL finding and tells everyone it's fine." Fewer auto-posts is the fail-safe consequence the fix exists to produce, not an accidental side effect.

9Known limits, stated honestly

L4 VERIFY approved M5 after the fix — all four gates are green, the demo command passes, and the CRITICAL-survives guarantee is now verified both at the unit level and through the compiled graph. Real, non-blocking limits remain on record rather than being quietly dropped:

  1. line_end is still not part of the dedup key (see Section 2) — a wide-span finding can still collapse into an unrelated narrow finding that merely shares line_start. Deliberately not fixed here; needs real interval-overlap logic in a future milestone.
  2. An empty findings list still routes to human review — route_review(Decimal("0.000"), [], threshold=...) returns QUEUED_FOR_HITL, since 0.000 is always below any sane threshold. This is a deliberate conservative decision, not a defect: "no findings" must never look indistinguishable from "confidently nothing to report" and silently auto-post. Covered by test_empty_findings_list_is_handled_sanely.
  3. Finding.__lt__ has no call site in backend/ production code. dedupe_findings compares findings through its own _is_better/_tie_break_key helpers, and its final sort orders dict keys, not Finding objects, so the dunder is never invoked in production today. It exists as correct, drift-proof, forward-looking code for a future direct caller (e.g. a dashboard listing).
  4. InMemoryHitlQueue is built and tested but not wired up. aggregate_node computes the correct Review.status and routing_reason and stops there — nothing pushes a QUEUED_FOR_HITL review into a live queue yet. Left for a later milestone, consistent with M4's own precedent of not wiring the orchestrator into the webhook/queue path.
  5. Models are still mutable post-construction — Finding and Review are not frozen and don't set validate_assignment, an M1-era gap M5 did not touch.

10Quiz

Three questions. Click each one to reveal the answer.

1. M5's original 91-test suite had dedicated tests for both dedupe_findings and route_review, and both passed. Why did neither one catch the CRITICAL-finding-dropped bug?

Because the bug lived in the seam between the two functions, not inside either one: test_aggregator.py's fixtures never happened to pit a lower-confidence CRITICAL finding against a higher-confidence non-CRITICAL one at the same key, and test_hitl_gate.py always fed route_review hand-built lists that never passed through dedupe_findings at all — so nothing ever tested dedupe's real output flowing into the gate.

Each half was well-tested for its own rules in isolation. The integration test in test_orchestrator_fanout.py also didn't catch it, because its four stub findings never collide on the same file+line — dedup is a no-op there. The fix explicitly closes this seam: TestDedupeAndRoutingInteraction now pipes dedupe's actual output into route_review, the same way aggregate_node does. The transferable lesson: two well-tested units composed together are not automatically a well-tested pipeline.

2. Why does Review's model_validator reject a mismatched overall_confidence outright, instead of silently recomputing it from findings so construction always succeeds?

Because silently recomputing would let a caller pass an arbitrary, wrong overall_confidence and have the mistake quietly erased — hiding exactly the kind of bug the M1 gap closure exists to surface. Rejecting fails loudly at construction time, catching a caller's error in a test instead of shipping a silently "corrected" wrong value.

This matters specifically because M5's HITL gate is the first code in the project that actually trusts overall_confidence to make a routing decision. A silent auto-correct would still produce a working Review object every time, which means a bug in whatever computed the original (wrong) value would never surface as a test failure — it would just quietly always get overwritten with the right answer, hiding that the caller's own computation was broken.

3. After the severity-first fix, a HIGH/0.100 finding can now survive a dedup collision over a MEDIUM/0.950 finding, and this can push a review into human review that the old rule would have auto-posted. Is this a new defect introduced by the fix?

No — it's a deliberate, accepted fail-safe consequence, not a regression. Lowering the auto-post rate for mixed-severity collisions is the correct direction to be wrong in: asking a human to look at slightly more reviews is categorically safer than the bug being fixed, which was a CRITICAL finding getting silently discarded while the system claimed everything was fine.

The fix's whole point is that severity should never lose to confidence in a dedup collision — that guarantee necessarily means a more-severe-but-less-confident finding sometimes displaces a less-severe-but-more-confident one, which can lower overall_confidence compared to the old rule. That's not a side effect to be minimized; it's the fail-safe behavior the rejection exists to produce.
