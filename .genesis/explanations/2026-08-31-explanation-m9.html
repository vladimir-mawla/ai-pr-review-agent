Hybrid Retrieval / Local Vector Memory

M9 gives this system a grounding layer: a local Postgres+pgvector store searchable by both vector similarity and full-text search, merged by reciprocal rank fusion (RRF). The interesting part of this milestone is not the plumbing — it's what happened when the team tried to make that fusion better and couldn't, and what a rigorous statistical test says about the improvement they kept instead. This page covers the two retrieval modes and why neither is sufficient alone, the exact arithmetic RRF uses and what it throws away to get there, the fixture embedder's honest collapse at real corpus scale, a 13-variant tuning investigation that failed its own held-out test (and was correctly discarded), and a McNemar test that turns a "73% vs 60%" headline into a much more careful claim. 1Grounding: why an agent needs retrieved context, not the whole repo

Every specialist agent this system runs (M8's real SecurityAgent, and M10's three more) answers a question about one diff: is this change safe, correct, well-tested, well-documented? Answering that well often requires more than the diff's own lines — does this function's caller already validate the input another way? Is there an existing helper that does the same thing? Does this touch a pattern the codebase has a documented convention for? That extra material is grounding: real, retrieved context from the surrounding codebase, handed to the model alongside the diff.

The obvious alternative — just send the whole repository — fails for reasons that compound rather than trade off against each other. A model's context window is finite and this repo alone is already hundreds of chunks; cost scales with tokens sent, so a whole-repo prompt on every review multiplies M8's already-metered BudgetGuard spend for no benefit on a diff that touches three functions; and — the subtler cost — a model asked to reason over everything at once has no signal for which of a thousand unrelated functions might matter, which measurably degrades relevance judgments compared to a short, targeted context. Grounding exists to solve exactly this: given a diff (or a query derived from it), retrieve a small number of genuinely relevant chunks from a pre-indexed store, and hand only those to the specialist.

What M9 actually builds

A local Postgres instance with the pgvector extension (a separate docker-compose service from M7's events Postgres, on its own host port 5434) stores code_chunks — this repo's own source, chunked and embedded — and HybridRetriever.hybrid_search is the one call a future specialist will make to get grounding context back: "find the chunks most relevant to this query," fused from two independent rankers rather than trusting either alone. M9 builds and proves this retrieval layer in isolation; wiring it into a specialist's actual prompt is later-milestone scope, the same staging M4's orchestrator and M8's LLM client followed before they were wired into the request path.

2Two retrieval modes, and what each is good at

backend/memory/context_retriever.py runs two independent searches over the same code_chunks table for every query, because each is good at exactly what the other is bad at.

Vector search (search_vector)

ANN search over embedding by cosine distance (pgvector's <=> operator, an HNSW index). Good at semantic matches — a query for "authenticate the request" can, in principle, find code that talks about "login" even though the two share no literal token. Bad at treating a rare, exact identifier as special: a single occurrence of a unique token gets averaged into whatever else is in that chunk's embedding, with no mechanism to say "this token appearing at all is a strong signal on its own."

Full-text search (search_fulltext)

Postgres's own ts_rank_cd over a generated, GIN-indexed content_tsv column, using plainto_tsquery. Good at exact and stemmed keyword matches — a query for the literal function name reciprocal_rank_fusion finds the chunk that defines it directly, no embedding noise involved. Bad at synonyms: it has no notion that "authenticate" and "login" are related unless both literal (stemmed) forms appear in the text.

This milestone's own fixture set has concrete examples of both failure/success modes, chosen from this repo's real code before ever being run against it (see tests/fixtures/ retrieval_queries.json's own rationale fields):

QueryWhat it testsWhich ranker wins
CircuitBreaker (id 3) An exact class name — full-text should nail this trivially Vector actually leads here (rank 2 of 387) — see section 3 for why full-text's own rank (18th) is deceptively bad
"authenticate the request" (id 4) Natural-language paraphrase with no literal keyword overlap — the vector-synonym case Depends entirely on embedding quality (section 4) — the deliberately riskiest query in the set
reciprocal_rank_fusion (id 1) Literal, corpus-unique identifier Full-text search's natural strength; used directly as this milestone's "known function name lands top-3" success criterion

Neither mode is sufficient alone across this whole query mix — which is precisely the justification for fusing them rather than picking one.

3Reciprocal rank fusion: the formula, k=60, and what it discards

reciprocal_rank_fusion (a pure function, no database dependency, directly unit-tested with known rank inputs) merges the two rankers' outputs with one formula: 

score(chunk) = sum over rankers r that surfaced chunk of  1 / (k + rank_r(chunk))

rank_r is 1-indexed — a ranker's top result has rank 1, never 0. A chunk that only one ranker surfaced still gets a score (from that one term); a chunk both rankers surfaced gets the sum of both terms, which is how a merely-decent showing on two rankers can outscore a brilliant showing on only one. k=60 is not an arbitrary constant this project invented — it's the commonly cited default from the RRF literature (Cormack, Clarke & Buettcher, 2009), chosen because it's large enough that a document's exact rank near the very top of one ranker doesn't completely dominate the fused score on its own; a second-place hit from one ranker and a first-place hit from another can still combine meaningfully rather than one ranker unilaterally deciding the result.

The real case that shows what this formula discards

Query id 3, CircuitBreaker, against the real, OpenAI-embedded corpus: the target chunk's true vector rank is 2nd of 387, at cosine similarity 0.4806 — genuinely the second-best match in the entire corpus, a confident, well-separated signal. Its full-text rank is 18th of 20 matched candidates, with ts_rank_cd = 0.1. On its face, "rank 18" looks like full-text search strongly disliked this document. Direct inspection of the full ranking shows that isn't what happened at all: ts_rank_cd for this query returns only a handful of coarse, quantized values (0.5, 0.3, 0.2, 0.1, ...), and this target's score of 0.1 is exactly tied with 11 other candidates — ranks 9 through 20 of the pool. Rank 18 doesn't mean "full-text meaningfully preferred the document at rank 9 over this one" — it means Postgres's own tie-break (row order) happened to place this one near the bottom of a 12-way tie carrying almost no discriminating information at all. 

RRF score = 1/(60+2) + 1/(60+18)
          = 0.016129 + 0.012821
          = 0.028950   -> fused rank 6 of the pool (a miss at top-5)

The fundamental cost of ignoring magnitude

RRF's formula only ever sees the two integers "rank 2" and "rank 18." It has no way to know that rank 2's cosine similarity (0.4806) reflects real, well-separated confidence, while rank 18's ts_rank_cd (0.1) reflects an arbitrary tie-break among 12 equally-scored candidates carrying almost no signal. A document one ranker is genuinely confident about is treated identically to one it barely, arbitrarily preferred — purely because both happen to land at the same ordinal position. Eight other candidates that scored only moderately on both rankers (e.g. vector rank 5 + full-text rank 1) out-accumulate this target's one very-strong-plus-one-weak combination, simply because RRF sums reciprocal ranks, not underlying scores. This is not a bug in the implementation — it's the structural trade-off any purely rank-based fusion makes in exchange for not needing the two rankers' scores to be on a comparable scale at all (cosine similarity and ts_rank_cd live in entirely different, incomparable ranges — RRF's whole appeal is sidestepping that problem, at the cost of exactly this kind of magnitude-blindness).

Section 5's tuning investigation tried a score-based fusion (min-max normalizing raw cosine similarity and ts_rank_cd within each pool) specifically to address this — it did not end up winning, but it was tried for exactly this reason, not omitted.

4The fixture embedder: why it exists, and where it collapses

DeterministicFixtureEmbedder exists because, for most of this milestone's build, there was no funded OpenAI credential available, and this project's own policy (mirroring AnthropicLLMClient's injectable fake client pattern from M8) is that nothing outside a real, credentialed live-demo path may depend on a network credential — every unit test, every integration test, and the demo command itself needed a no-network, fully-reproducible embedder. It tokenizes the input text, hashes each token to a deterministic unit vector, sums those vectors, and L2-normalizes the result — a real, inspectable mechanism, not a trained model, engineered specifically to make semantically related text (shared or canonicalized tokens) land near each other in vector space.

The honest finding, measured directly rather than assumed: this design collapses at real corpus scale. A summed-then-normalized bag of tokens dilutes a single occurrence of even an exact, corpus-unique identifier once the corpus has hundreds of chunks. The concrete, measured example — query id 7, route_review, against the real seeded corpus: the function's own definition chunk has a true vector rank of 117th of 378, at cosine similarity 0.032 — below the ~0.0625 magnitude two completely unrelated random 256-dimensional vectors correlate at by pure chance. The fixture embedder doesn't just rank the definition chunk low; on this metric alone it can no longer distinguish "this chunk is about route_review" from "these two vectors share no relationship at all." Meanwhile, chunks that merely call the function several times (mostly test files) repeat the exact identifier token repeatedly and outrank the actual definition, in both full-text cover-density and vector token-sum weight.

This is a fixture-embedder limitation, not a retriever bug

HybridRetriever's SQL and reciprocal_rank_fusion's arithmetic were verified directly to do exactly what they are specified to do. A larger candidate pool was tried experimentally (up to 100 candidates, over a quarter of the corpus) and only recovered 2 of 6 misses on the original 10-query set — a partial fix that defeats the pool's own documented purpose, correctly rejected rather than shipped. Once a funded OpenAI credential existed, the same 10 queries were re-measured on real text-embedding-3-large embeddings: recall@5 rose from 4/10 to 7/10, rescuing 3 of the fixture embedder's 6 misses and losing none of its hits — direct evidence the collapse above is a property of the hashed bag-of-tokens design, not of the retrieval architecture around it.

5The centrepiece: tuning on the same 10 queries is fitting noise

With fusion and vector-alone tied at 7/10 on the original 10-query set, the obvious next move looks like: try a few fusion variants, keep whichever scores highest on those same 10 queries. That move is a methodological trap, and this milestone's investigation is worth walking through precisely because it demonstrates the trap being avoided on purpose, not stumbled past.

Ten queries is a small enough sample that a variant can score higher purely by luck — by fitting whatever idiosyncrasies happen to exist in those specific 10 items, rather than by being genuinely better at retrieval in general. If the winner is then judged only against the same 10 queries it was selected on, there is no way to tell the difference between "this variant is actually better" and "this variant happened to fit this particular sample's noise." The fix applied here is the standard one from any discipline that takes overfitting seriously: hold out a second, independent sample, commit it before it is ever used, and touch it exactly once, after the selection is already locked in.

  1. The held-out set was written and git-committed before any tuning happened. tests/fixtures/ retrieval_queries_holdout.json — 15 queries, chosen blind from this repo's own source the same way the original 10 were — exists in git history from before the first of the 13 variants was ever tried. This ordering matters: a held-out set built or edited after seeing which variant looks best is not held-out at all, it's just a second chance to cherry-pick.
  2. Every tuning step used only the original 10. 13 variants — weighted RRF at vector:fts ratios of 2:1, 3:1, and 1:2; candidate pools of 50, 100, and the full 387-chunk corpus; RRF's own k at 10, 20, and 120; three score-based fusion weightings; one best-rank fusion — were all scored exclusively against the 10-query tuning set. Best result: 8/10, achieved by three separate variants, never 9/10 or 10/10.
  3. The selection rule was written down before the held-out set was touched. Highest recall@5; tie-break on recall@3; tie-break on upweighting the already-stronger vector ranker; tie-break on the smallest parameter deviation from current defaults. Applying it mechanically picked weighted RRF at vector:fts = 3:1 (k=60, pool=20).
  4. The held-out set was queried exactly once, with the winner, the untuned current default, and vector-alone all measured together for a fair three-way comparison.
MethodOriginal 10 (tuning set)Held-out 15 (recall@5)Held-out 15 (recall@10)
Vector alone7/109/15 (60%)10/15 (67%)
Current RRF (k=60, pool=20, untuned)7/1011/15 (73%)13/15 (87%)
Tuned winner (vec:fts=3:1)8/1011/15 (73%, tied)12/15 (80%, worse)

The tuned winner's edge on the tuning set (8/10 vs 7/10) evaporated on the held-out set — it merely tied the untuned default at recall@5, and was outright worse at recall@10. This is the overfitting risk the whole methodology exists to catch, caught for real.

Why NOT shipping the tuned variant is the correct engineering outcome

It would have been easy to ship the 3:1 weighting anyway — it did score better on some evidence, and a less careful process might have stopped at "8/10 beats 7/10, ship it." The held-out test exists specifically to prevent that: a change justified only by the same data used to find it is not justified at all, and shipping it here would have meant a real, worse-at-recall@10 change to a live retrieval system, sold on evidence that had already been shown not to generalize. HybridRetriever/reciprocal_rank_fusion are unchanged from before this investigation began — the correct response to "13 variants, none of which beat the shipped default on held-out data" is not to force one through anyway, but to conclude the current configuration isn't leaving obvious, cheap, generalizable recall on the table, which is itself a useful, if less exciting, result.

673% vs 60% sounds decisive. McNemar says otherwise.

The held-out numbers above — 11/15 vs 9/15 at recall@5 (73% vs 60%), 13/15 vs 10/15 at recall@10 (87% vs 67%) — read like a clear win for fusion. This milestone's own PLAN.md, in its first pass at recording this result, said as much: fusion "clearly beats" vector-alone, by a margin "large enough to not be noise." An independent verification session later ran the actual statistical test this claim implies, and the picture it produced is narrower.

McNemar's test is the right tool here because recall@5 and vector-alone-recall@5 aren't two independent samples — they're two scores on the same 15 queries. What matters for "is method A really better than method B" isn't the raw counts, it's the queries where the two methods disagree — the discordant pairs. A query both methods get right, or both get wrong, provides no information about which method is better; only the disagreements do.

MetricDiscordant pairsRRF right / vector wrongVector right / RRF wrongMcNemar p-value
recall@5220p = 0.5
recall@10330p = 0.25

Neither p-value clears any conventional significance threshold (e.g. p < 0.05) — and with only 2 or 3 discordant pairs total, no test could. What the data does show, precisely: at both recall@5 and recall@10, every single discordant pair went RRF's way and none went the other way. The direction is perfectly one-sided everywhere it was formally tested. What it does not show: that this one-sidedness is anything more than what you'd expect to see some of the time from a coin that isn't actually biased, given how few discordant pairs there are to work with.

Direction consistent. Significance absent. These are different claims.

For someone deciding whether to trust this benchmark, the distinction matters concretely: "no evidence fusion hurts" is fully supported (RRF lost zero discordant pairs at either k on the held-out set); "suggestive evidence fusion helps" is a fair characterization (the one-sidedness is a real pattern, not nothing); "fusion clearly beats vector-alone" is not supported by this sample size, however the raw percentages look. A benchmark can be honestly reported and still not be decisive — the two are not the same claim, and collapsing them is exactly the kind of overclaim this closeout session's fix to PLAN.md exists to correct. Settling the question for real would need enough discordant pairs — realistically a substantially larger, blindly-chosen query set (30 or more) — for McNemar to have a chance of reaching significance even if the true effect is real.

One more nuance the original "clearly beats" framing omitted entirely: on the small original 10-query set, fusion doesn't uniformly win at every k — at recall@3 specifically, vector-alone actually leads, 6/10 to fusion's 5/10. That's the one place in either query set where the direction runs against fusion outright, not merely short of statistical significance.

7Honest limits

  1. The success criterion was amended after the numbers were already measured. PLAN.md's original M9 criterion — a literal "recall@5 = 100% on a 10-query fixture" — was written before any real measurement existed. It was retired only after the honest 40%/70%/tied-then-not-significant results were already on record, with the original wording and every intermediate status kept verbatim above the correction, not rewritten. This is the right order of operations (measure, then decide whether the bar was realistic) but it does mean the bar this milestone is ultimately judged against was not fixed in advance the way the held-out query set discipline (section 5) insists tuning decisions should be.
  2. n=15 is small. The held-out set is large enough to be a real, blind, single-use test — the discipline that matters most for avoiding overfitting — but it is not large enough to make a statistically confident claim about the size of fusion's benefit, as section 6 shows directly. A 30+-query set is the tracked next step, not yet built.
  3. The corpus vanishes on every container recreate. The pgvector service has no volume, by design — a docker compose down && up starts code_chunks empty every time. A host-side marker file that survives the recreate can still claim a corpus is already seeded, which has already cost two separate verification sessions a surprise re-seed and real API spend. The test fixtures guard against this correctly (comparing the marker's claimed count against a live row count before trusting it); a human running the demo command by hand is not automatically protected — see README.md's local development notes and the pgvector service comment in docker-compose.yml, both updated in this closeout session.

8Quiz

Three questions. Click each one to reveal the answer.

1. Thirteen fusion variants were tuned and scored using only the original 10-query set, and a held-out 15-query set — written and committed before any tuning began — was queried exactly once, after a winner was already selected. Why does the order of these two steps matter, and what would go wrong if the held-out set had instead been built or adjusted after seeing how the 13 variants performed?

Because a held-out set only tells you anything if it is genuinely independent of the selection process it's meant to check. If the held-out set were built or adjusted after seeing the 13 variants' results, it would no longer be an independent test -- it would just be a second opportunity to pick queries (consciously or not) that happen to favor whichever variant already looked best, defeating the entire purpose.

This is exactly the failure mode the pre-registered selection rule and the committed-before-queried held-out set were built to prevent: the tuned winner (weighted RRF, vector:fts=3:1) scored 8/10 on the original 10 -- a real, measured edge -- but then tied the untuned default at recall@5 and lost at recall@10 on the held-out 15, revealing that its tuning-set edge had fit noise specific to those 10 queries rather than reflecting a genuine improvement. Querying the held-out set only once, after the winner was locked in, is what makes that a trustworthy negative result rather than something that could itself have been cherry-picked.

2. Query id 3 (CircuitBreaker) has a true vector rank of 2nd (cosine 0.4806) but a full-text rank of 18th (ts_rank_cd 0.1) -- direct inspection shows that 0.1 score is exactly tied with 11 other candidates. Why does RRF's formula, score = 1/(k+rank), treat this rank-18 result as meaningfully worse than a rank-9 result with the identical tied score, and what does that reveal about what rank-based fusion discards?

Because RRF's formula only ever looks at the ordinal rank number, never the underlying score that produced it. It has no way to represent "these 12 candidates are actually tied and this rank ordering among them is arbitrary" -- rank 9 and rank 18 get different, fixed contributions (1/(60+9) vs 1/(60+18)) regardless of whether the scores behind them are meaningfully different or an arbitrary tie-break among equals.

This is the fundamental cost of ignoring magnitude: a ranker's genuine confidence (vector rank 2 at a strong, well-separated cosine similarity of 0.4806) is fused using the exact same mechanism as a ranker's arbitrary, low-information tie-break (full-text rank 18, tied with 11 others at a score that barely discriminates between any of them). A rank-based fusion like RRF sidesteps the real problem of putting cosine similarity and ts_rank_cd on a comparable scale -- but the price is that it cannot tell a confident rank from a coin-flip rank once both happen to land at the same ordinal position.

3. The held-out 15-query results show current RRF beating vector-alone 11/15 to 9/15 at recall@5 (73% vs 60%) -- but a McNemar test on the underlying discordant pairs (2 pairs, both favoring RRF, 0 the other way) gives p=0.5, nowhere near significant. Which of these is the accurate way to describe what this evidence actually supports?

"No evidence fusion hurts, and suggestive but statistically unproven evidence that it helps" -- not "fusion clearly beats vector-alone." The direction is genuinely one-sided (every discordant pair favored RRF, none favored vector-alone, at both recall@5 and recall@10), which is real information -- but with only 2-3 discordant pairs total, that one-sidedness is exactly the kind of pattern a fair coin would also produce some of the time by chance, so it cannot be called statistically significant.

This is precisely the gap between the raw percentages (73% vs 60% looks decisive) and what a formal significance test on the same underlying data actually supports. PLAN.md's own M9 success criteria originally said fusion "clearly beats" vector-alone with a margin "large enough to not be noise" -- this closeout session corrected that wording on top of (not instead of) the original, specifically because "direction consistent" and "statistically significant" are different claims, and only the first one is currently earned. Settling the second would need a larger, blindly-chosen query set (30+) to generate enough discordant pairs for McNemar to have a real chance at significance.
