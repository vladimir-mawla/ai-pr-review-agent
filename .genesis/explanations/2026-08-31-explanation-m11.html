Real GitHub Integration

M11 swaps M10's mocked github_client for a real GitHub App: a real RS256 JWT, a real cached installation token, real REST calls, all still wrapped in M6's retry/breaker/timeout composition with GitHub-specific error classification. The centerpiece is not the auth handshake — it's what happens when an LLM's reported line number doesn't actually correspond to a line GitHub will accept a comment on, and why that must never take the whole review down. This page covers the App-vs-PAT auth model; why an installation on one throwaway repo is the actual safety boundary, not the App's permission set; the diff-position mapping problem and its degradation path; a real, re-provable idempotency check; a contract test built to avoid mock/reality drift; and the honest limits an independent L4 VERIFY session found and judged non-blocking. 1Background: from a PAT to a GitHub App

Anyone who has scripted against GitHub with a personal access token (PAT) has used the simplest possible auth model: one long-lived string, generated once by a human in a settings page, sent as a bearer token on every request, valid until the human revokes it. It authenticates as that human, with whatever scopes they granted it, for as long as they choose to leave it alive.

A GitHub App is a different actor entirely — it authenticates as itself, not as any one person, and it does so through two separate credentials with two separate lifetimes instead of one:

Step one — mint_app_jwt in backend/integrations/github_auth.py — signs a JWT asserting only "I am App <app_id>" (the iss claim), using RS256 so the signature can only be produced by the holder of the App's private key. This JWT is good for exactly two things: app-level endpoints like GET /app, and exchanging itself for an installation token. It cannot fetch a diff or post a comment directly.

Why the JWT must live under 10 minutes. This is GitHub's own hard rule, not a local choice: a JWT whose exp claim is more than 10 minutes past iat is rejected outright. The reasoning is the same reason short-lived credentials exist anywhere — a JWT is signed with the App's most sensitive secret (the private key itself), so the App's own code goes out of its way to mint a fresh one for essentially every use rather than caching one for hours the way a PAT effectively is. This project clamps to a conservative 9 minutes (_MAX_JWT_TTL_SECONDS = 9 * 60), not the literal ceiling, specifically so a token minted right at the boundary is never rejected by a few seconds of clock rounding. It also backdates iat by 60 seconds (CLOCK_SKEW_TOLERANCE_SECONDS) because GitHub rejects a JWT whose iat appears to be in GitHub's own future — a JWT minted at this machine's honest current time can still look "not yet valid" to a GitHub server whose clock runs a few seconds behind. 

current = now if now is not None else datetime.now(UTC)
issued_at = current - timedelta(seconds=CLOCK_SKEW_TOLERANCE_SECONDS)   # backdated 60s
expires_at = issued_at + timedelta(seconds=_MAX_JWT_TTL_SECONDS)        # +9min from there

payload = {"iat": int(issued_at.timestamp()), "exp": int(expires_at.timestamp()), "iss": app_id}
encoded = jwt.encode(payload, private_key_pem, algorithm="RS256")

Step two exchanges that JWT for an installation access token via POST /app/installations/{id}/access_tokens. This token — not the JWT — is what actually authenticates a real diff fetch or a real review post, and it authenticates as the installation (this App, as installed on this specific account's chosen repositories), never as the App in the abstract and never as any human. It lives roughly an hour, which is long enough that minting a fresh one before every one of a review's several outbound calls (metadata, diff, changed files, the post itself) would be wasteful and would needlessly hammer GitHub's own rate limit on the token-exchange endpoint — so InstallationTokenCache holds one token per installation id and only re-mints when the cached one is within _REFRESH_MARGIN_SECONDS (5 minutes) of its real, GitHub-reported expiry.

Why the installation id is discovered, not configured. A naive integration might put an installation id in .env next to the App id. This project deliberately does not: discover_installation_id calls GET /repos/{owner}/{repo}/installation for real, every time a new (owner, repo) pair is seen, and GitHub's own answer — 200 with an id, or 404 — is the fact being asked about. A hardcoded id could go stale the moment someone uninstalls and reinstalls the App, or could simply be typed wrong with no mechanism to catch it; the discovery call cannot be wrong about whether the App is actually installed, because it is GitHub's own installation registry answering directly. The same call also becomes the authorization gate — see the next section.

2One throwaway repo: install scope is the safety boundary

This project's GitHub App is installed on exactly one repository: vladimir-mawla/pr-review-agent-testbed, a disposable repo created specifically to receive real, live reviews. It would be easy to assume the safety boundary here is the App's permission set — the specific scopes granted on the App's settings page (pull_requests: write, contents: read, and so on). That's not quite right. Permissions say what kinds of actions the App could take if it were installed somewhere; they say nothing about where.

Permission set alone

Answers "can this App write pull-request reviews at all?" — a yes/no that is the same everywhere the App happens to be installed. It cannot answer "should this App be allowed to touch this specific repository" — that's not a question permissions are shaped to ask.

Install scope (what actually gates M11)

RepositoryAuthorizer.authorize calls GET /repos/{owner}/{repo}/installation before any real action. A 404 — this App is simply not installed on that repo — refuses the action outright, regardless of what the App's permission set would otherwise allow. With the App installed on exactly one throwaway repo, this call 404s for literally every other repository on GitHub.

Put concretely: even if a bug elsewhere in this codebase somehow passed an arbitrary (owner, repo) through to RealGitHubClient — a real programming error, not a hypothetical attacker — the App's write permission would be structurally unable to reach anywhere except the one repo it is actually installed on. GitHub itself enforces this, not application logic this project could get wrong; rbac.py's RepositoryAuthorizer is a thin, testable wrapper around that real, external fact, not a second, locally-maintained allowlist that could quietly drift out of sync with what's actually installed.

Why this beats a local allowlist A hand-maintained list of "repos we're allowed to touch" living in this codebase would be a second source of truth that could drift from reality — someone uninstalls the App and forgets to update the list, or updates the list without actually installing anywhere. The real installation record IS the list; asking GitHub is asking the one place that can't be stale relative to itself.

3The centerpiece: diff-position mapping

A GitHub pull request review can attach a comment to a specific line, but "line 47 of app.py" is not, by itself, enough information for GitHub to accept it. An inline review comment must anchor to a line the diff itself actually shows — a line that was added, removed, or is part of a context window GitHub chose to render around a change. A line that exists in the file but falls outside every hunk of this particular diff has no anchor GitHub will accept a comment against, full stop.

This matters because an LLM-reported line number is exactly the kind of number that can miss. A specialist agent reads a diff as text and reports "line 47" from its own reading of that text — but the model can be off by a line, can report a line number from the full file rather than the diff's own numbering, or can name a line that got shifted between when the diff was fetched and when the review is posted. None of that is a parsing bug; it's an inherent gap between "a number an LLM wrote down" and "a number GitHub's diff renderer actually produced a comment slot for."

Why one bad anchor is catastrophic, not just wrong GitHub's review-creation endpoint takes one comments array for the whole review. If even one entry in that array anchors to a line GitHub's diff doesn't recognize, the ENTIRE POST fails with HTTP 422 — not just that one comment. A review with five solid, well-anchored findings and one bad line number does not post four good comments and skip the bad one; it posts nothing at all, and every other finding in that review is lost along with it.

Two schemes, one choice

GitHub's REST API has historically supported two ways to anchor an inline comment:

SchemeHow it addresses a lineWhy it's fragile / why it isn't
position (legacy) An integer offset counted from the first line of the unified diff for that file — every hunk header and context line counts, not just changed ones. Brittle by construction: it silently shifts if GitHub ever changes hunk-splitting or context-line heuristics between when a diff is fetched and when the review posts, and it has no natural relationship to "line 47 of the file" — translating one into the other needs extra bookkeeping this project's domain model doesn't otherwise carry.
line + side (current, chosen here) The real line number in the file — new-file numbering when side="RIGHT", old-file numbering when side="LEFT" — the same addressing the GitHub web UI itself uses when a human leaves an inline comment. Matches what a Finding already carries (file_path + line_start) with zero translation, and is GitHub's own currently-documented, recommended mechanism rather than an older, less-documented one.

backend/integrations/diff_mapping.py builds one DiffIndex per PR by walking every changed file's unified-diff patch text once, tracking the running old-file and new-file line counters through each hunk: 

marker = raw_line[0] if raw_line else ""
if marker == "+":
    index.right_lines.add(new_line); new_line += 1
elif marker == "-":
    index.left_lines.add(old_line); old_line += 1
elif marker == " ":
    # a context line is the SAME source line on both sides
    index.right_lines.add(new_line); index.left_lines.add(old_line)
    old_line += 1; new_line += 1

map_finding_to_anchor then looks up (file_path, line_start) against that index — RIGHT first (an added or context line, the overwhelming common case), then LEFT (a genuinely removed line — a real, valid thing to comment on: "this validation you just deleted was load-bearing"). If neither set contains the line, it returns None. It never raises.

The degradation path

None is not treated as a failure to recover from — it's a routing decision. RealGitHubClient.post_review_comment classifies every finding independently: a mappable finding becomes one entry in the review's real comments array; an unmappable one is rendered, in full, into the review's summary body instead.

Finding from a specialist agent
↓
map_finding_to_anchor(file_path, line_start)
↓
Anchor found → real inline comment,
line+side
No anchor → folded into the review's
summary body, clearly labeled
↓
One POST .../reviews call, every finding accounted for, never a 422 from a mapping miss

This is what makes one bad line number harmless instead of catastrophic: the review still posts, still contains every finding the pipeline produced, and a reader can immediately see which findings got a precise inline anchor and which are listed in the summary because their reported line didn't correspond to anything the diff shows.

The reference implementation's choice, and why it's worse The project this system is measured against (ayush488-glitch/ai-pr-review-agent) gave up on this problem entirely: it posts summary-only, for every review, regardless of whether that specific review's findings would have mapped cleanly or not. That trades a rare failure (one bad anchor) for a permanent one (no inline comments, ever) — the reviewer loses GitHub's native "comment attached to the exact line" experience on every single review, including the overwhelming majority that would have mapped perfectly fine, just to avoid the possibility that one review in a hundred might have had a bad line number. Independent classification plus degradation gets the precise, inline experience for the common case and a safe, informative fallback for the rare miss — without sacrificing one to avoid the other.

4Idempotency: the review_id marker

GitHub retries webhook deliveries — a slow or momentarily-erroring receiver can see the same delivery arrive twice, and separately, this project's own ARQ job queue can retry a job that raised after it successfully posted but before it finished cleanly. Either path risks the same real-world outcome: the same review posted to the same PR twice.

The fix does not need a database table, a distributed lock, or a new piece of infrastructure — it needs one fact GitHub is already willing to store: post_review_comment writes a hidden HTML comment into every review body it posts, keyed by this project's own review_id: 

_IDEMPOTENCY_MARKER_PREFIX = "<!-- pr-review-agent:review_id="
_IDEMPOTENCY_MARKER_SUFFIX = " -->"

def _find_existing_review_id_marker(self, *, owner, repo, pr_number, headers, review_id):
    marker = f"{_IDEMPOTENCY_MARKER_PREFIX}{review_id}{_IDEMPOTENCY_MARKER_SUFFIX}"
    response = self._call_reliably(lambda: self._http_client.get(
        f"/repos/{owner}/{repo}/pulls/{pr_number}/reviews", headers=headers,
        params={"per_page": _FILES_PAGE_SIZE},
    ))
    existing = [ExistingReview.model_validate(e) for e in response.json()]
    return any(marker in review.body for review in existing)

Before doing any real work — before even fetching the diff — post_review_comment checks whether a review carrying this exact review_id's marker is already on the PR. If so, it logs and returns without calling GitHub's write endpoint at all. A job retried from the top after a successful first post finds its own marker already there and becomes a safe no-op on its second execution, regardless of ARQ's max_tries setting.

This was proven for real, not asserted from reading the code: the live integration test was run twice against the real testbed PR, and the review count on the PR was confirmed unchanged between the two runs — the second run found the marker and skipped.

The limitation this session's closeout found The GET above fetches exactly one page of reviews (per_page, no follow-the-next-link loop). On a PR with more than 100 reviews, a marker sitting on an earlier page would go unseen, and a retried job could post a genuine duplicate. Not a risk for how this project actually uses a throwaway testbed PR today, but a real correctness gap on a busier PR — see Honest limits.

5The contract test: why a mock needs a leash

MockGitHubClient has stood in for GitHub since M10, and every unit test that exercises the review-posting path runs against it, never the real network. That's the right default for speed and determinism — but it creates a specific risk: the mock encodes assumptions about what GitHub's real API returns (field names, nesting, types), and nothing stops those assumptions from quietly drifting away from what GitHub actually sends, e.g. if a future change to github_models.py renames a field the real API never renamed. A test suite built entirely against a mock that has drifted from reality stays green while testing nothing real — false confidence is worse than an obviously-broken build, because nothing signals the problem until a real call fails in production.

tests/contract/test_github_client_contract.py exists specifically to catch that drift, and it was built to avoid being circular — a contract test that only checks the mock against itself, or against a fixture the same session invented by hand, proves nothing. Instead it's split into two halves:

TestFixtureMatchesRealShape

Default, no marker, no credential needed. Loads tests/fixtures/github_api_contract.json — JSON captured from real, live calls against vladimir-mawla/pr-review-agent-testbed#1 during this milestone's own build session — and asserts every github_models.py model parses it without error, with the exact field values GitHub itself returned. THIS is the actual drift guard: it fails the moment a model change stops agreeing with what GitHub really sends, without a network call.

TestLiveCaptureReproducesTheFixtureShape

@pytest.mark.live, skipped without a credential. Re-runs the SAME calls against the REAL API right now and asserts the response still parses under the same models — proving the fixture isn't stale or fabricated, and would catch GitHub itself changing a response shape out from under this project.

The independence is what makes this non-circular: the fixture was captured from a real API response once, checked into the repo, and is separately re-pullable from the real API on demand — it is neither hand-written nor validated only against itself. The fixture's own _captured_from field records exactly where it came from (https://github.com/vladimir-mawla/pr-review-agent-testbed/pull/1, 2026-08-31), and its _note field records that the token field is deliberately redacted — no credential material rides along with the shape being pinned.

6Honest limits

The ngrok webhook-tunnel leg was never exercised PLAN.md's own M11 demo command opens with ngrok http 8000 & python scripts/register_webhook.py ... — ngrok is not installed on this build machine, and scripts/register_webhook.py does not exist at all (confirmed directly: ls scripts/register_webhook.py fails with "no such file"). No real inbound GitHub webhook was ever received by this system. Everything downstream of a webhook delivery — auth, real diff fetch, the real four-agent pipeline, diff-position mapping, real posting — was proven end to end via direct calls instead. This is judged non-blocking because the webhook → queue → orchestrator path a real delivery would drive was already independently proven real at M10; only the inbound-delivery leg itself remains unexercised.
The live demo bypassed the M5 HITL gate — on purpose, and it cannot recur in production The real four-agent pipeline, run against the real testbed PR, correctly found a genuine CRITICAL SQL-injection defect and correctly routed to QUEUED_FOR_HITL — the safety gate working exactly as designed. To still satisfy this milestone's own "post a real review to a real PR" requirement, post_review_comment was called directly instead of through post_or_queue, a disclosed, demo-only bypass. This cannot happen by accident in the real system: both production call sites — backend/job_queue/arq_worker.py and backend/cli/review_local.py — call only post_or_queue, never post_review_comment directly (grep-verified). A CRITICAL finding routes to a human in every real path this project actually runs.
The LLM's own line attribution was off by two lines The diff-position mapping mechanism worked correctly for the real demo review — both findings resolved to valid anchors, no 422, nothing degraded. But the underlying line number the specialist agent reported for the SQL-injection finding was itself two lines off from the actual vulnerable statement in app.py. This is a distinct failure mode from what the centerpiece section covers: mapping answers "does GitHub have an anchor for the line I was given," not "is the line I was given actually correct." A precisely mapped comment on the wrong line is still a wrong comment — a reminder that solving the anchoring problem does not, by itself, solve the separate problem of an LLM's own line-counting accuracy.
Two smaller, code-level gaps found in this closeout's own review RealGitHubClient.__init__ raises a raw FileNotFoundError — not the documented GitHubAuthError — when the configured private-key path doesn't exist, because the open(...) call at construction isn't wrapped in a try/except. And RepositoryAuthorizer.authorize distinguishes "not installed" from other auth failures by checking whether the literal substring "HTTP 404" appears in an exception's string form, rather than checking a typed status code — fragile if that message format ever changes upstream.

7Quiz

Three questions. Click each one to reveal the answer.

1. A review has five findings. Four map cleanly to real diff lines; one specialist reported a stale line number that the diff doesn't show at all. If this project posted all five as inline comments anyway, what would actually happen — and how does the real degradation path avoid it?

GitHub's review-creation endpoint takes one `comments` array for the entire review — if even one entry anchors to a line GitHub's diff doesn't recognize, the WHOLE POST fails with HTTP 422. All five findings would be lost, not just the one bad one.

`map_finding_to_anchor` classifies every finding independently before anything is posted: the four that resolve against the PR's real `DiffIndex` become real inline `line`+`side` comments; the one that resolves to `None` is instead rendered into the review's summary body by `_format_summary_body`, clearly labeled as unable to be anchored. The review still posts, with all five findings represented — just four inline and one in the summary — instead of a 422 that would have silently destroyed all five.

2. `RepositoryAuthorizer.authorize` calls the real GitHub API on every new `(owner, repo)` pair rather than checking a hardcoded installation id from `.env`. Given that the App's permission set (`pull_requests: write`, etc.) is configured once on GitHub's own App settings page regardless of where it's installed, why is the *installation scope* — not the permission set — actually what keeps this system from touching an arbitrary repository?

The permission set only answers "what KINDS of actions could this App take if installed somewhere" — it says nothing about WHERE. `GET /repos/{owner}/{repo}/installation` returning 404 for every repo except the one throwaway testbed repo is what actually makes an arbitrary target unreachable, regardless of what the App's permissions would otherwise allow there.

Even a real bug elsewhere that passed an arbitrary `(owner, repo)` through to `RealGitHubClient` would hit this same real, external check — GitHub itself enforces "not installed here" before any write permission could ever be exercised against that repository. A hardcoded id or a local allowlist would be a second, driftable source of truth that could go stale the moment the App is uninstalled or reinstalled elsewhere; asking GitHub's own installation registry directly cannot be stale relative to itself.

3. `_find_existing_review_id_marker` fetches only page 1 of a PR's existing reviews (`per_page`, no pagination loop) before deciding whether `review_id` has already been posted. Under what real circumstance does this stop being a safe idempotency check, and why doesn't this affect the M11 live demo itself?

On a PR with more than 100 reviews, a marker sitting on an earlier page (page 2 or beyond) would never be seen by a single-page GET — a retried job could then post a genuine duplicate review, the exact failure this check exists to prevent.

The M11 live demo itself isn't affected because the testbed PR (`vladimir-mawla/pr-review-agent-testbed#1`) has a tiny number of reviews — nowhere close to the page boundary — so the idempotency re-run that proved "review count unchanged on a second run" never exercised the pagination edge at all. This is exactly why it's logged as an open item rather than something the live demo already ruled out: proving the mechanism works on a small PR is not the same as proving it works on a busy one.
