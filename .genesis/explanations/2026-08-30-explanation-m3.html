1Background

M2 built the webhook route: verify the HMAC signature, check the delivery id against an idempotency store, then call queue.enqueue(event) and return 200. But M2's queue, InMemoryJobQueue, was explicitly a stand-in — a Python set of seen delivery ids and a list of accepted events, both living only in the current process's memory. Nothing dequeues from it. Nothing else can see it. It exists purely so the router has something real to call.

M3's job is to replace that stand-in with the real thing: a durable queue (Redis) and a real ARQ worker process that actually dequeues and does something with each job — the async hand-off the whole system design depends on, since GitHub's webhook can't wait around for four LLM agents to finish reviewing a pull request before it gets an HTTP response.

2The intuition: a swap, not a rewrite

M2 didn't just build InMemoryJobQueue; it built backend/job_queue/interface.py first — a Protocol named JobQueue with exactly two methods, enqueue() and size() — and coded backend/webhook_receiver/router.py against that Protocol, never against the concrete InMemoryJobQueue class. That is the single decision that makes M3 additive instead of invasive: M3's job becomes "write a new class satisfying the same two methods," not "rewrite the request path."

Verified, not just claimed
The M3 diff (git diff --stat 3e24fb4^..74ba8f0) touches ten files — redis_arq.py, arq_worker.py, docker-compose.yml, settings.py, main.py, .env.example, pyproject.toml, the new test file, and two genesis bookkeeping files — and backend/webhook_receiver/router.py is not among them. tests/integration/test_queue_roundtrip.py makes this a tested claim rather than an assertion in a docstring: its TestJobQueueContract class runs the exact same three tests (first enqueue succeeds, a repeat is a no-op, size() reflects distinct jobs) against both InMemoryJobQueue and RedisJobQueue via a single parameterized fixture — proving both implementations satisfy one contract, which is exactly what lets the router stay untouched.

Only one line in backend/api/main.py actually decides which implementation a real (non-test) app gets, and it reads a setting rather than hardcoding a choice: 

def _default_job_queue(settings: Settings) -> JobQueue:
    """Build the JobQueue a real (non-test) app uses, per settings.job_queue_backend."""
    if settings.job_queue_backend == "redis":
        return RedisJobQueue(settings)
    return InMemoryJobQueue()

JOB_QUEUE_BACKEND=in_memory is still the default in .env.example, so existing webhook tests and a Docker-free local run are unaffected; setting it to redis (and running docker compose up -d redis) is what turns on the real queue this milestone built.

3Why enqueue-and-return-200 matters

GitHub enforces a short response timeout on webhook deliveries. If the endpoint doesn't acknowledge quickly, GitHub marks the delivery failed and retries it — repeatedly, on its own schedule, with the same X-GitHub-Delivery id. A handler that tried to run the review pipeline synchronously before returning 200 would routinely time out, and a slow-but-eventually-successful handler would still get retried because the acknowledgment never arrived in time — causing duplicate work stacked on top of the timeout.

GitHub POSTs a webhook, starts its response-timeout clock
↓
Router verifies signature, checks idempotency, calls queue.enqueue(event) — a bounded Redis round trip, not the review itself
↓ typically well under a second
Router returns 200. GitHub is satisfied; the delivery is done from its point of view
↓ asynchronously, on its own schedule
The ARQ worker (a separate OS process) dequeues the job and does the actual (eventually: four-agent) work, with no HTTP client waiting on it

This is why M3 exists as its own milestone rather than being folded into M4's orchestrator: the queue is the boundary between "must respond fast" and "can take as long as it needs." RedisJobQueue.enqueue() does two bounded Redis operations (the idempotency SET and handing the job to ARQ) and returns — heavy work stays entirely on the worker's side of that boundary.

4The atomic idempotency key, and the race it avoids

RedisJobQueue.enqueue() checks and claims a delivery id in a single Redis command: 

key = f"{_IDEMPOTENCY_KEY_PREFIX}{event.delivery_id}"
was_newly_set = self._redis_sync.set(
    key, _IDEMPOTENCY_VALUE, nx=True, ex=self._ttl_seconds
)
if not was_newly_set:
    return EnqueueResult(enqueued=False, delivery_id=event.delivery_id)

SET key value NX EX ttl means "set this key, with this expiry, but only if it doesn't already exist" — and Redis executes the whole thing as one indivisible operation. The alternative — call EXISTS key, and if it comes back false, call SET key value EX ttl — looks equivalent for a single caller, but it is a classic check-then-act race the moment two callers can run concurrently, which a webhook endpoint under real traffic absolutely can (GitHub's own retries, or two nearly-simultaneous legitimate deliveries racing a slow network).

Concretely, with two threads/requests handling the same retried delivery:

Request A: EXISTS key → false (not seen yet)
↓ before A gets to SET, the scheduler switches to B
Request B: EXISTS key → also false — A hasn't written anything yet
↓ both now believe they are first
A calls SET, then B calls SET — both proceed to enqueue_job, and the delivery is processed twice

The gap between EXISTS returning and the corresponding SET running is exactly where two callers can both observe "not present." SET ... NX EX ... collapses that gap to zero: Redis is single-threaded for command execution, so of any number of concurrent SET ... NX calls for the same key, exactly one can ever return "I set it" — there is no window in which two callers both get the affirmative answer. redis_arq.py's own docstring calls this out as the reason the method is written this way, not as an incidental implementation detail.

5Why the TTL exists, and why 7 days

M2's InMemoryJobQueue kept every delivery id it had ever seen in a set, forever — flagged at M2's own L4 VERIFY as an unbounded-growth finding: a long-running process accumulates one string per delivery with no eviction. RedisJobQueue fixes this by construction: every idempotency key it writes carries an expiry (the ex= argument above), so Redis itself reclaims the memory once the key is no longer plausibly useful — no separate cleanup job, no unbounded structure.

The default, _DEFAULT_IDEMPOTENCY_TTL_SECONDS = 7 * 24 * 60 * 60 (one week), is sized against a specific external fact: GitHub retries a failed webhook delivery for roughly 24 hours before giving up. The TTL has to comfortably outlive that window, or a legitimate late retry could arrive after its idempotency key has already expired and get treated as a brand-new delivery — silently defeating the entire mechanism this milestone exists to build. Seven days is not "24 hours plus a little" — it's roughly 7× GitHub's own retry window, a wide margin over clock skew, a delayed retry queue on GitHub's side, or simply an unusually late redelivery, while still bounding memory growth to "a week's worth of delivery ids," not "forever."

tests/integration/test_queue_roundtrip.py's TestIdempotencyTtl doesn't just trust that ex= was passed correctly — it constructs a queue with a short 30-second TTL, enqueues one event, then reads the TTL back from Redis directly via TTL key (exposed as RedisJobQueue.ttl_for()) and asserts it's positive and ≤ 30, ruling out both "no expiry was actually set" and "the wrong value was passed."

6The sync/async bridge

JobQueue.enqueue() is a synchronous method — a deliberate M2 design choice, since router.py calls it as a plain, non-awaited call from inside an async def route, and M3 is not allowed to change that router. But ARQ's client, arq.connections.ArqRedis, is async-only: there is no synchronous enqueue_job. Something has to bridge the two.

The tempting-but-hazardous option

Call asyncio.run() (or a fresh loop.run_until_complete()) directly inside enqueue(). This works in a plain script, but enqueue() is invoked from inside a route handler that is itself already running on uvicorn's event loop, on uvicorn's thread. Trying to start (or drive) a second event loop on a thread that already has one running is the well-known "this event loop is already running" class of failure — sometimes an outright exception, sometimes silent corruption of scheduling, depending on exactly how it's invoked.

What RedisJobQueue actually does

At construction, it starts a dedicated background thread running its own private event loop forever (asyncio.new_event_loop() + loop.run_forever()). enqueue() then hands work to that loop from the caller's thread via asyncio.run_coroutine_threadsafe(coro, self._loop) and blocks on future.result(timeout=...) — a real thread-to-thread handoff, never a second loop competing for the same thread. 

self._loop = asyncio.new_event_loop()
self._loop_thread = threading.Thread(
    target=self._run_loop, name="redis-job-queue-loop", daemon=True
)
self._loop_thread.start()
...
future = asyncio.run_coroutine_threadsafe(
    self._arq_pool.enqueue_job(ARQ_JOB_FUNCTION_NAME, event.model_dump(mode="json")),
    self._loop,
)
future.result(timeout=_ENQUEUE_TIMEOUT_SECONDS)

Two consequences follow directly from this design. First, enqueue() genuinely blocks the calling (request) thread while it waits for future.result() — it's not free concurrency, just safe concurrency; recorded in checkpoints/CURRENT.md as worth revisiting only if request-path latency ever becomes a problem at real traffic volume. Second, because the job actually goes through ARQ's real wire format (its queue zset, msgpack-encoded payload) rather than some hand-rolled shortcut, the ARQ worker in arq_worker.py needs no special-casing to consume it — it's a completely ordinary ARQ job as far as the worker is concerned.

7Known limits, stated honestly

L4 VERIFY approved M3 — the demo command passes, all four gates are green, and the milestone did what its plan entry committed to. It also flagged real, non-blocking limitations:

  1. Nothing calls RedisJobQueue.close() at shutdown. close() exists and correctly releases the ARQ pool, stops the background loop, and joins its thread — but no FastAPI lifespan hook actually calls it, so the background thread is simply abandoned when the process exits. Harmless in practice (it's a daemon thread; the process is exiting anyway regardless), but untidy — a lifespan hook should call it for a clean shutdown.
  2. A Redis-down enqueue() surfaces as an unhandled 500, not a graceful 503. Neither the synchronous SET nor the cross-thread ARQ hand-off currently catches a connection failure and translates it into a deliberate "service unavailable, retry later" response — acceptable for M3's local-dev scope, worth revisiting before this endpoint carries real traffic.
  3. Idempotency state is lost whenever the Redis container is recreated. docker-compose.yml's redis service has no volume, so docker compose down && up always starts it empty — confirmed empirically (DBSIZE drops to 0). An empty queue after a clean restart is exactly M3's own success criterion ("no orphaned jobs"), but the corollary is that replay protection resets too: a delivery this process already saw looks brand new again after a recreate. Now documented in docker-compose.yml's comment and README.md, not fixed — adding a volume is a design decision nobody has asked for yet.
Why these aren't blockers
None of the three contradicts what M3's plan entry or DONE.html's DoD gates asked for: a validated webhook enqueues to Redis, a separate worker dequeues and logs it, and a clean restart leaves no orphaned jobs. The demo command and all 9 new integration tests prove exactly that. Recording the gaps keeps them visible for whichever later milestone needs to close them, instead of quietly forgetting them or scope-creeping M3 to cover work — lifespan wiring, graceful degradation, persistence — that was never this milestone's job.

8Quiz

Three questions. Click each one to reveal the answer.

1. Why did swapping in a real Redis/ARQ queue require zero changes to backend/webhook_receiver/router.py?

Because M2 coded the router against the JobQueue Protocol, not the concrete InMemoryJobQueue class, so any implementation satisfying the same two methods (enqueue, size) is a drop-in replacement.

RedisJobQueue implements the exact same Protocol InMemoryJobQueue does. The only thing that changes is one function in backend/api/main.py, _default_job_queue(), which picks the concrete class based on settings.job_queue_backend. tests/integration/test_queue_roundtrip.py's TestJobQueueContract proves this by running the identical three contract tests against both implementations via one parameterized fixture.

2. Why is the idempotency check one atomic SET key value NX EX ttl instead of an EXISTS check followed by a separate SET?

Because two concurrent callers for the same delivery id could both observe "not present" from EXISTS before either one writes, and both would then proceed to enqueue — a classic check-then-act race. A single atomic SET...NX guarantees only one caller ever gets the affirmative "I set it" result.

Redis executes SET ... NX EX ... as one indivisible command, so there's no window between "check" and "act" for a second caller to slip through. With a separate EXISTS then SET, a retried GitHub delivery arriving as two near-simultaneous requests could both read "key doesn't exist" before either writes it, resulting in the same delivery being enqueued twice — exactly the bug idempotency exists to prevent.

3. JobQueue.enqueue() is a synchronous method, but ARQ's client is async-only. Why doesn't RedisJobQueue just call asyncio.run() inside enqueue() to bridge the two?

enqueue() is called from inside an async route handler that is already running on uvicorn's own event loop and thread; starting or driving a second event loop on that same thread is the well-known "event loop already running" hazard. Instead, RedisJobQueue runs ARQ's async client on a dedicated background thread with its own private loop, and bridges to it via asyncio.run_coroutine_threadsafe.

The background-thread approach means the caller's thread never tries to nest a loop inside one that's already executing — it just blocks on future.result(timeout=...) waiting for a real cross-thread handoff to finish. The trade-off, recorded as an open item in checkpoints/CURRENT.md, is that every enqueue() call genuinely blocks the calling thread on that round trip — acceptable at M3's scale, worth revisiting only if request volume ever makes that latency matter.
