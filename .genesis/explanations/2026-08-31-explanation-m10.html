Full Local Dry-Run Review

M10 is where this project stops being four separate pieces of machinery and becomes one pipeline: four real LLM-backed specialists, retrieval grounding, the ARQ worker finally driving the orchestrator graph it has been queueing jobs for since M4, a mocked GitHub dispatch with a structural "never both" guarantee, and a CLI that writes one schema-valid Review to disk. 1Background: what existed before M10

By M9, this project had every piece except the piece that connects them. M8 gave it one real specialist (SECURITY) calling a real Anthropic model; QUALITY, TESTS, and DOCS were still M4's canned, no-network stub findings. M9 gave it a local retrieval store (HybridRetriever, pgvector + full-text search fused by reciprocal rank fusion) that nothing yet queried from inside a real agent call. And the orchestrator itself — a real LangGraph StateGraph that fans out to four nodes concurrently, checkpoints to disk, and resumes across a process boundary — had been sitting unwired since M4: the ARQ worker dequeued a verified webhook event and did nothing more than record that it arrived.

M10's job was not to invent new capability so much as to finish wiring the capability that already existed: make the other three specialists real, ground all four in retrieval, and — the item every milestone since M4 had deferred and re-deferred — make the queue actually drive the graph.

2Four specialists, not one broader prompt

A single prompt asking one model call to check security, code quality, test coverage, and documentation all at once would cost a quarter of what four separate calls cost, and it would never produce two agents flagging the same line from different angles. M10 chose four narrow specialists anyway, and the honest cost showed up immediately in the real numbers: PLAN.md's own M10 demo run (backend/cli/review_local.py against tests/fixtures/sample_pr_diff.patch) made four real, billable Anthropic calls for one review, and its 14 findings contained two confirmed cross-agent duplicate clusters — TESTS separately flagging the same hardcoded-credential issue SECURITY already covered (through a "this should be validated by a test" framing, a mild bleed into SECURITY's own territory), and SECURITY and QUALITY each independently flagging the same bare-except/uninitialized-variable bug from their own distinct angles.

One broad prompt

1 call, 1 bill. No cross-agent duplicates, because there is only one agent. But nothing separates a security concern from a docs concern in the model's own reasoning — a single pass has to divide its attention across four different kinds of scrutiny in one shot, with no way to give any one of them a dedicated system prompt tuned to what THAT kind of review actually looks for.

Four narrow specialists (M10's choice)

4 calls, 4x the bill. Each agent gets a system prompt written for exactly one remit, run independently and concurrently (LangGraph's Send API, unchanged since M4). The real cost: two of the real demo's 14 findings are duplicates from different agents converging on the same real defect — not a hypothetical, a directly measured consequence, disclosed rather than hidden.

Neither of the two duplicate clusters is actually wrong — SECURITY and QUALITY flagging the same bare-except bug are both right, from genuinely different angles (it is both a defensive-programming problem and a data-integrity problem) — but it is real, disclosed overlap, not zero, and it is the direct, honest price of specialist narrowness over one broad prompt. See Honest limits for why the current dedupe pass does not catch it.

3Remit separation is prompt-only, not structural

All four specialists share one implementation (backend/agents/base_agent.py's run_specialist_analysis): load a versioned prompt, ground it with retrieval, call the LLM, parse the response, fall back to a forced-HITL finding on a parse failure. Nothing in that shared body — or anywhere else in the pipeline — prevents SECURITY's prompt from answering a documentation question, or DOCS's prompt from flagging a SQL injection. The only thing keeping SecurityAgent on-topic is the text of its own system prompt (backend/prompts/templates/security/v1.md) and the fact that agent_type=AgentType.SECURITY is what the response parser attaches to every finding it returns, not a claim the model itself is forced to justify.

SecurityAgent

Own system prompt, own AgentType.SECURITY tag. Nothing stops it from noticing a docs gap; nothing routes that observation anywhere special if it does.

QualityAgent

Same shared plumbing, different prompt file, different tag.

TestsAgent

Same shared plumbing, different prompt file, different tag.

DocsAgent

Same shared plumbing, different prompt file, different tag.

Consequence "Remit" is a convention each prompt is written to follow, enforced by how well the model follows instructions on a given call — not a constraint the code checks or enforces. The real demo run's two duplicate clusters are exactly what this looks like in practice: two agents each doing their own job correctly, converging on the same line because nothing structurally scoped either of them away from it.

4Grounding by symbol name, not raw diff text

Every specialist's prompt is grounded in retrieved repository context via M9's HybridRetriever — but the retrieval query is not the diff itself. extract_retrieval_query (backend/agents/base_agent.py) pulls the names of symbols the diff actually defines on an added line (a def/class/const declaration, matched by a small set of simple regexes) and joins up to 12 of them into the query, falling back to the first 500 characters of raw diff text only when no declaration is found at all. 

def extract_retrieval_query(diff: str) -> str:
    symbols: list[str] = []
    for line in diff.splitlines():
        if not line.startswith("+") or line.startswith("+++"):
            continue
        for pattern in _DEFINITION_PATTERNS:
            match = pattern.search(line)
            if match:
                name = match.group(1)
                if name not in symbols:
                    symbols.append(name)
                break
    if symbols:
        return " ".join(symbols[:_MAX_QUERY_SYMBOLS])
    return diff[:500]

This is a direct, learned consequence of M9's own investigation, not a fresh design guess. M9's checkpoint measured directly that a single occurrence of even an exact, corpus-unique identifier gets diluted below the corpus's own incidental noise floor once the corpus has hundreds of chunks — a real function's true vector rank landed 117th of 378 candidates, at a cosine similarity below the magnitude two unrelated random vectors correlate at by pure chance. A long, free-text query (the whole diff, hundreds of tokens of prose and code mixed together) makes this worse, not better: it dilutes a distinctive identifier's vector weight even further and gives full-text search a weaker, noisier match too. A short query built from the actual symbol names the diff introduces is both a stronger full-text match (the compound identifier, as written) and a less-diluted vector query — fewer, more distinctive tokens, closer to the shape of query M9's own test_known_function_name_in_top_ three_fused_results already proved works well.

The retrieval call is bounded on both ends: top_k=5 results, and format_retrieved_context caps the injected text at 6000 characters total, adding whole chunks only — never a chunk cut mid-way, which would inject a misleadingly truncated fragment. And a retrieval failure (the pgvector store briefly unreachable, a malformed query) is swallowed, not propagated: the call proceeds on the diff alone rather than treating a grounding hiccup as if the LLM provider itself were down. See Honest limits for the consequence of that choice.

5The shared infrastructure-failure path

M8 built this mechanism for SECURITY alone: when a specialist cannot even attempt its analysis — a budget block, a missing or rejected credential, a provider that stayed unreachable after retries — the right response is not an empty findings list. An empty list is indistinguishable from "I looked, and found nothing" — exactly the shape a clean, confident review has. M10 generalizes that fix (previously only security_node's own bespoke handling) into one shared body every specialist node now shares, backend/orchestrator/nodes.py's _specialist_node: 

_INFRASTRUCTURE_FAILURE_EXCEPTIONS = (
    BudgetExceededError,
    LLMConfigurationError,
    LLMCallFailedError,
)

def _specialist_node(agent_type, state, config):
    ...
    try:
        findings = _run_specialist(node_name, agent_type, config, diff)
    except SimulatedNodeCrashError:
        raise
    except AgentExecutionError as exc:
        return {"findings": [], "node_errors": {node_name: str(exc)}}
    except _INFRASTRUCTURE_FAILURE_EXCEPTIONS as exc:
        fallback = infrastructure_failure_fallback_finding(agent_type, exc)
        return {"findings": [fallback], "node_errors": {node_name: str(exc)}}
    return {"findings": findings, "node_errors": {}}

The fallback is one synthetic Finding: severity CRITICAL, confidence 0.000, a rationale naming the real exception. That specific combination is what makes it work — backend.hitl.queue.has_critical_finding forces QUEUED_FOR_HITL unconditionally the moment any CRITICAL finding exists, regardless of what the other three specialists reported. A merely-low-confidence finding would not guarantee that; a bare empty list guarantees the opposite of what is needed.

Why this mattered more at M10 than at M8 Before M10, only SECURITY was real — QUALITY, TESTS, and DOCS were M4's stub nodes, which never call an LLM and so could never hit a budget block or a provider outage in the first place. A budget block on one of those three stubs was structurally impossible, so the gap in their infrastructure-failure handling was invisible — there was nothing yet that could trigger it. The moment M10 made all four real, every one of them gained the exact same failure surface SECURITY already had, and M8's own L4 VERIFY had already flagged this exact gap as something that would bite "once M10 wires up the other three real agents" (checkpoints/CURRENT.md's M9 Deferred entry, written before M10 started). Generalizing the fix here closes it before it was ever exploitable, not after.

Note the narrower except AgentExecutionError branch above returns a genuinely empty list, not a fallback finding — that path is reserved for this test suite's own simulated-crash machinery, a deliberately different case from a real infrastructure failure. And anything outside that named tuple — a real TypeError, a real bug in this project's own code — is not caught here at all; it propagates out of the node uncaught, the same way it always did, because silently reinterpreting a genuine programming bug as "the specialist is unavailable" would hide it rather than surface it.

6Mid-review budget exhaustion

There is no review-scoped "budget already spent this review" fast path. Each of the four specialist calls independently starts with AnthropicLLMClient.complete calling BudgetGuard.check_and_raise() — the same M8 mechanism, unchanged — and each one reads the same real, shared spend from agent_events and decides for itself whether today's cap is already exceeded. That means a cap crossed partway through one review (say, by the first two agents' own real spend) blocks whichever of the remaining calls happen to run afterward, and leaves the review "2 of 4 successful, 2 of 4 budget-blocked."

Agent 1 — SECURITY

Calls succeed. Real findings returned.

Agent 2 — QUALITY

Calls succeed. Real findings returned.

Agent 3 — TESTS

BudgetExceededError — cap already crossed. Forced-HITL CRITICAL fallback finding instead.

Agent 4 — DOCS

BudgetExceededError — same cap, same fallback.

Because each blocked agent contributes its own forced CRITICAL/confidence-0.000 finding (the same mechanism the previous section describes) rather than an empty list, and because a single CRITICAL finding forces QUEUED_FOR_HITL unconditionally, a half-blocked review can never silently look like a complete, confident, auto-postable one — the gate routes it to a human exactly as it would a review with two real CRITICAL security findings. tests/integration/test_budget_guard_across_four_agents.py proves this through the real compiled graph (a shared fake LLM client that deterministically blocks calls after the first allow_count succeed, independently counting how many calls were actually attempted — proving the guard is hit per call, not merely configured to be).

7Closing the M4 gap: the queue finally drives the graph

Since M4, this project's own Deferred list carried the same item forward, milestone after milestone: "the orchestrator built at M4 is not yet wired into the webhook/queue path." M3 built the ARQ worker; M4 built the compiled LangGraph; from M5 through M9, the worker's job handler did nothing but record that a webhook job had arrived. M10 is the milestone that finally connects them — backend/job_queue/arq_worker.py's process_webhook_event now runs a real review through the same LangGraphWorkflowEngine instance backend.cli.review_local drives, then dispatches the resulting Review through the same post_or_queue function the CLI uses.

The interesting part is not that it calls engine.run — it's how it calls it. graph.invoke makes four real, synchronous, network-bound LLM calls; that is a long, blocking operation. ARQ's worker process is itself asyncio-based (so it can run many jobs concurrently within one process), so calling that blocking review directly inside the async def job handler would stall the worker's own event loop for the whole review's duration — serializing every other concurrently-queued job behind it. This is the identical defect class this project has now fixed three times before, on three different event loops:

MilestoneWhat blocked the loopFix
M6/M7 follow-upA synchronous Redis enqueue call on uvicorn's webhook-ingress loopenqueue_async via asyncio.to_thread
M7A synchronous Postgres events write on the same uvicorn loopemit_decision_async via asyncio.to_thread
M8(Forward-looking) a real Anthropic call from an async callercomplete_async via asyncio.to_thread, built ahead of its first real caller
M10The blocking graph.invoke review on ARQ's own worker event loopasyncio.to_thread, same pattern
 
def _run_review_blocking(engine, review_id, initial_state):
    return engine.run(thread_id=review_id, initial_state=initial_state)

async def process_webhook_event(ctx, event):
    ...
    result = await asyncio.to_thread(
        _run_review_blocking, engine, review_id, initial_state
    )

The webhook ingress itself is untouched — receive_webhook still only enqueues and returns immediately, exactly as it has since M3/M6/M7. The review runs entirely inside the ARQ worker's own separate OS process, offloaded onto that process's own thread pool so one slow review does not stall the worker's ability to pick up other queued jobs concurrently.

8Exactly one of post or queue

PLAN.md's own M10 success criteria name this directly: "the mocked GitHub client records exactly one 'post' or one 'queue_for_hitl' call, never both." The guarantee is structural, not merely tested — backend/integrations/github_client.py's post_or_queue is the single, shared decision point both real call sites (backend.cli.review_local and backend.job_queue.arq_worker) use instead of each re-implementing its own status check: 

def post_or_queue(client: GitHubClient, review: Review) -> None:
    if review.status == ReviewStatus.POSTED:
        client.post_review_comment(review)
    else:
        client.queue_for_hitl(review)

A plain if/else over one method call each makes "both" unreachable by construction — there is no code path through this function that calls both, or neither. The MockGitHubClient's own dispatch_count() helper (posted + queued call counts summed) exists specifically so a test can assert this as one number rather than checking two list lengths separately.

"Verified in both directions" means verified at both of the two real call sites that route through this shared function, not just one: tests/e2e/test_full_local_review.py's test_the_mock_github_client_records_exactly_one_call_never_both proves it through the CLI path end to end, and tests/integration/test_queue_to_orchestrator.py's test_enqueued_event_is_processed_into_a_review proves the identical invariant through the ARQ worker path — a real enqueued webhook event, processed by a real worker job handler, through the real graph, to a real dispatch decision.

9Honest limits

Adjacent-line duplicates escape dedupe dedupe_findings' key is an exact match on (file_path, line_start) — a gap M5 already deferred for one agent's own wide-span findings, and now confirmed to also let two DIFFERENT agents' findings on adjacent-but-not-identical lines both survive as separate findings instead of colliding. The real demo run's two duplicate clusters (see Four specialists) are exactly this: real, correctly-identified defects, reported twice, that a wider or interval-aware key would need to actually catch — not something this milestone attempted to fix.
An ungrounded review looks identical to a grounded one build_user_message silently falls back to the diff alone when retrieval fails — a deliberate availability/thoroughness trade-off (see Grounding), not a bug. But nothing in the resulting Review records which case happened. A review whose four specialists were all genuinely grounded in real repository context and one whose grounding silently failed four times over produce structurally identical output — there is no grounded flag, per finding or per review, to tell them apart after the fact.
The pipeline is now non-deterministic The builder session's own real demo run produced 14 findings at overall_confidence=0.896. An independent L4 VERIFY session's own real run of the identical demo command against the identical fixture diff produced 15 findings, not 14 — the same real defects, plus one additional real finding surfaced by the model's own run-to-run variance. This is the first milestone whose real, headline output number cannot be reproduced exactly twice — expected of a genuine LLM call, and now explicitly recorded rather than treated as a fluke to chase down.

10Quiz

Three questions. Click each one to reveal the answer.

1. A specialist agent hits a `BudgetExceededError` mid-review. Why must `_specialist_node` return one synthetic CRITICAL/confidence-0.000 finding instead of an empty findings list — and what would actually break if it returned `[]` instead?

Because an empty findings list is indistinguishable from a clean, confident "I looked and found nothing" review. If a budget-blocked agent returned `[]`, a review where 2 of 4 specialists never even ran could still pass `route_review`'s confidence/CRITICAL checks and auto-post as if it were a genuinely thorough pass.

The forced CRITICAL/confidence-0.000 fallback works specifically because backend.hitl.queue.has_critical_finding forces QUEUED_FOR_HITL unconditionally the moment ANY CRITICAL finding exists — so a half-blocked review is guaranteed to route to a human, the same way a review with two real CRITICAL security findings would. This was M8's original fix for SECURITY alone; M10 generalizes it to all four specialists specifically because M8's own L4 VERIFY had already predicted the gap would bite once QUALITY/TESTS/DOCS stopped being no-op stubs that could never hit this exception in the first place.

2. `extract_retrieval_query` builds a specialist's retrieval query from the diff's own changed symbol names, falling back to the first 500 characters of raw diff text only when no declaration is found. Why not just always use the raw diff text as the query — it contains strictly more information?

Because more text is not more signal here — M9's own investigation measured directly that a single occurrence of even an exact, corpus-unique identifier gets diluted below the corpus's own incidental noise floor once the corpus reaches real scale (one real function's true vector rank landed 117th of 378, at a cosine similarity BELOW what two unrelated random vectors correlate at by chance).

A long, free-text query made of the whole diff's prose and code mixed together dilutes a distinctive identifier's vector weight even further than a single mention already does, and gives full-text search a noisier match too. A short query built from the actual symbol names the diff introduces is both a stronger full-text match (the exact compound identifier, as written) and a less-diluted vector query — fewer, more distinctive tokens. This is a direct, learned consequence of M9's own findings, not a fresh guess made at M10.

3. `post_or_queue` is a plain `if review.status == ReviewStatus.POSTED: ... else: ...` — no locking, no transaction, no retry. Why is this enough to structurally guarantee "exactly one of post or queue, never both," and what would a test actually need to prove to falsify that guarantee?

Because a single, unconditional if/else over two method calls makes "both" or "neither" unreachable by construction, for any single `Review` passed through it — every possible value of `review.status` takes exactly one of the two branches, not zero and not two. There is no code path through this function that calls both `post_review_comment` and `queue_for_hitl`.

A test could only falsify this by finding a `Review` value that takes neither branch (impossible, since `if`/`else` is exhaustive) or by finding a caller that invokes post_review_comment/queue_for_hitl directly instead of going through post_or_queue — which is exactly why both real call sites (backend.cli.review_local and backend.job_queue.arq_worker) route through this one shared function rather than each re-implementing its own status check. The tests (test_the_mock_github_client_records_exactly_one_call_ never_both for the CLI path, test_enqueued_event_is_processed_into_a_review for the ARQ worker path) exist to confirm both real call sites actually go through it, not to prove the if/else logic itself, which is exhaustive by construction.
