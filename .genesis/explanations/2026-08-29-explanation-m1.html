1Background

This repository is a from-scratch build of a multi-agent PR review system: a webhook receiver, a queue, a LangGraph orchestrator fanning out to four specialist agents (security, quality, tests, docs), an aggregator with a human-in-the-loop gate, and a Tiger Cloud-backed memory/events store. None of that exists yet. M1's job was narrower and more foundational: stand up the package skeleton the rest of the plan will be built into, and define the three data contracts — Finding, Review, WebhookEvent — that every later milestone passes around.

This is a contracts-first milestone by design. The project's ADR-0001 (local-simulation-first build order) commits to building the real architecture against local fixtures rather than a throwaway prototype, specifically so that later milestones swap in real integrations (GitHub, Tiger Cloud, an LLM) behind interfaces that were designed deliberately, not improvised under integration pressure. That only works if the shapes flowing through the system are nailed down before the behavior is. If Finding's confidence field, or WebhookEvent's idempotency key, changes shape in M8 because nobody thought it through in M1, every consumer written in between has to be revisited. Pydantic models with real field constraints (bounds, lengths, patterns) — validated at construction time rather than trusted by convention — are the mechanism for "nailed down."

The other half of M1 is architectural: ADR-002 commits to a modular monolith where dependencies only point inward, toward backend/core. M1 stands up the empty package tree for that (19 subpackages under backend/) and wires up a tool, import-linter, to check the rule mechanically rather than relying on every future contributor reading and remembering ADR-002.

2The intuition: enforce, don't document

A codebase with clean layering degrades one import at a time. Nobody ever decides "let's make core depend on the API layer" — someone just needs a type from backend.api inside backend/core/ to fix a bug at 6pm, adds the import, the tests still pass, and the rule is now silently false. Six months later nobody can extract core into its own package, or reason about it in isolation, because it quietly depends on everything.

Why mechanical enforcement, not a docs page
A rule that lives only in a wiki page or an ADR is a rule that has to be remembered, every time, by every person (or agent) touching the code. A rule enforced by a linter that runs as part of the demo command is a rule that cannot regress silently — the CI-equivalent gate goes red the moment someone adds the forbidden import, in the same commit, before it ever reaches a reviewer.

Concretely, ADR-002's inward-only rule says: backend/core may be imported by anything, but it must import nothing else in backend/. backend/models is one layer out from that — it may depend on core, but nothing above it (agents, orchestrator, API, etc.) may be depended on by it either. Two import-linter "forbidden" contracts encode exactly that:

backend.core
↑ everything else may depend on core; core depends on nothing
backend.models
↑ everything above may depend on models; models depends on nothing above it
backend.agents · orchestrator · api · database · webhook_receiver · job_queue · integrations · reliability · observability · memory · tools · security · hitl · economics · evaluation · cli · prompts

A toy example: if someone later writes from backend.api import respond inside backend/core/engine.py to reuse a helper, that one line breaks the "Core layer independence" contract. Running the demo command's second half, lint-imports --config .importlinter, would report that contract as BROKEN and exit non-zero — before the PR merges, not after someone notices the module graph has become a hairball.

3Implementation walkthrough

M1 landed four files under backend/models/, each owning one contract, plus the 19 empty subpackages (backend/{core,models,agents,api,cli,database,economics, evaluation,hitl,integrations,job_queue,memory,observability,orchestrator,prompts, reliability,security,tools,webhook_receiver}) and 24 unit tests in tests/unit/test_models.py.

enums.py

Severity (CRITICAL→INFO), AgentType (SECURITY/QUALITY/TESTS/DOCS), ReviewStatus (POSTED/QUEUED_FOR_HITL/REJECTED/ERROR). All three are StrEnum, so they serialize as plain strings in JSON while still being type-checked and exhaustively matchable in Python.

findings.py

Finding: one issue found by one agent. Owns confidence as a Decimal bounded to [0.000, 1.000] with exactly 3 decimal places (avoids float-precision drift when confidences get averaged later), and line_start/line_end as positive ints. Also defines __lt__ so a list of findings sorts by severity then confidence without a separate sort key function at every call site.

review.py

Review: the top-level result for one PR. Owns the full findings list, an overall_confidence (same bounded-Decimal shape as Finding.confidence), and the ReviewStatus that downstream consumers (the API, the dashboard, the HITL queue) branch on. This is the object every later milestone that "produces a review" will construct.

webhook.py

WebhookEvent: the parsed, minimal shape extracted from GitHub's pull_request payload — action, PR number, repo owner/name, 40-hex-char head SHA, and a delivery_id for idempotency dedup in M2. Also defines WebhookPullRequest/WebhookRepository as intermediate shapes, though nothing in the current tree actually constructs them yet (see the gaps below).

The demo command is two commands chained with &&, and both halves were run for real to write this page:

4The import-linter config bug

The first pass at .importlinter used the section header [importlinter:settings]. That header is documented in some import-linter examples floating around, but it is not what the version actually pinned in this project (import-linter 1.8.x / 1.12.1 installed) looks for. Its INI reader, IniFileUserOptionReader, matches on a section literally named [importlinter].

Before — silently broken

[importlinter:settings]
root_package = backend

[importlinter:contract:1]
name = "No forbidden imports"
type = "forbidden"
source_modules =
    backend.models
forbidden_modules =
    backend.api

After — fixed

[importlinter]
root_package = backend

[importlinter:contract:core-independence]
name = Core layer independence
type = forbidden
source_modules =
    backend.core
forbidden_modules =
    backend.models
    backend.api
    ...

[importlinter:contract:models-independence]
name = Models layer independence
type = forbidden
source_modules =
    backend.models
forbidden_modules =
    backend.api
    ...
Why this failed loudly instead of quietly
With the wrong section header, every reader (.importlinter and a duplicate copy in setup.cfg) returned None from read_options(), and use_cases.read_user_options() raised "Could not read any configuration." — a hard crash, not a false "0 broken." That's the good version of this bug: a third copy of the contracts also existed under [tool.import-linter] in pyproject.toml, which is not even the key the TOML reader looks for (it wants [tool.importlinter]) and was unreachable anyway because the demo command passes --config .importlinter, which forces the INI-only reader path. Three different broken config locations, one real fix: keep .importlinter as the single source of truth, since that's the file the demo command names explicitly, and delete the other two.

The fix also widened the contracts. The original single contract only checked that backend.models doesn't import backend.api — a narrow, partial encoding of ADR-002. The corrected config adds a second contract for backend.core against every other subpackage, and expands backend.models's forbidden list to all 17 outer subpackages, so both innermost layers are actually checked, not just one edge of the graph.

Non-vacuousness was verified by hand: a throwaway from backend.api import x was added to backend/core/__init__.py, lint-imports was re-run and printed Core layer independence BROKEN with a non-zero exit, then the line was reverted and the contract went back to KEPT. A passing linter that has never been observed to fail is not proof the gate works — it might just mean nothing sets it off.

5Python 3.11 → 3.12, and the unbounded pin

pyproject.toml was originally written against Python 3.11 (the highest version documented as available at the time), with requires-python = ">=3.11" and matching mypy/ruff target versions. Once Homebrew's python@3.12 (3.12.14) became the project's approved runtime, three fields were bumped together — requires-python, tool.mypy.python_version, and tool.ruff.target-version — so the interpreter actually running the venv, the type checker, and the linter all agree on one language version. Skewed versions here are a quiet source of false-negative type checks (mypy checking 3.11 syntax rules against code that a 3.12 interpreter runs).

Separately, the dev dependency import-linter>=2.0 (later corrected to import-linter>=1.8,<2.0) was an unbounded lower pin — the kind of thing that looks harmless in a diff because it installs fine on the machine that wrote it.

pin: import-linter>=2.0
→
fresh pip install resolves to latest 2.x (2.14)
→
config validated against 1.8 syntax breaks

.importlinter's contract syntax (the unquoted type = forbidden form, the section-name conventions fixed in the previous section) was validated against 1.8.0 specifically. An unbounded >=2.0 pin means anyone cloning this repo today — or CI running a fresh install tomorrow — gets whatever the newest 2.x release is, which is a different major version with its own config expectations. The project would pass on the original author's machine (whatever was already installed locally) and fail on a clean clone, which is close to the worst kind of bug: invisible until someone else tries to reproduce the build. The final commit narrows the pin to >=1.8,<2.0, matching the version the contracts were actually written and verified against, so a fresh clone reproducibly gets the same behavior.

6Known gaps, deliberately deferred

L4 VERIFY ran a separate, independent session against M1's demo command and success criteria and returned APPROVE — the tests pass, the linter contracts hold, and backend/core has zero sibling imports, which is everything M1's plan entry actually committed to. That verification pass also surfaced five model-validation gaps that are real, but out of scope for what M1 promised. They're recorded here, and in checkpoints/CURRENT.md, rather than fixed silently, so a later milestone (or the user) makes an explicit call on each one instead of the gap being forgotten.

  1. Finding.line_end >= line_start is not enforced. Both fields are independently validated as positive ints, but nothing stops line_start=42, line_end=10 from constructing successfully — it would need a cross-field @model_validator.
  2. Review.overall_confidence is not cross-checked against the actual mean of findings[].confidence. A Review can be constructed with findings that average to 0.30 and an overall_confidence of 0.99 — the two fields are validated independently, not against each other.
  3. WebhookEvent.delivery_id is validated only by length (exactly 36 characters), not by actual UUID format — a 36-character string of arbitrary characters passes.
  4. Models are mutable after construction. None of the four contracts set model_config["frozen"] = True or validate_assignment = True, so a Finding or Review instance can have its fields reassigned post-construction without re-running validation.
  5. WebhookPullRequest and WebhookRepository are dead code. Both are defined in backend/models/webhook.py, but nothing in the current tree constructs or imports either one — only WebhookEvent is actually used.
Why not just fix these now
Fixing validation gaps changes the contract's runtime behavior for every future consumer, and the deferral is deliberate: it's a decision for the user (or a later, explicitly-scoped milestone) to make, not something to slip in as a side effect of a documentation and bookkeeping pass. None of the five gaps affect what M1's own demo command or success criteria checked.

7Quiz

Three questions. Click each one to reveal the answer.

1. Why did lint-imports --config .importlinter raise a hard "Could not read any configuration" error instead of quietly reporting zero broken contracts?

Because the section header didn't match what the installed tool looks for.

The config used [importlinter:settings], but import-linter 1.8.x's IniFileUserOptionReader matches only a section literally named [importlinter]. Every reader (the .importlinter file and a duplicate in setup.cfg) returned None, so read_user_options() had nothing to work with and raised outright — which, while alarming, was actually the safer failure mode: it forced a fix rather than letting the gate silently pass with zero contracts checked.

2. Why is backend/core forbidden from importing backend/models, when backend/models is one layer further from the edges of the system?

Because ADR-002's rule is inward-only in one specific direction: everything points toward core, and core depends on nothing in the tree.

backend/models is allowed to depend on backend/core (one layer further in), but not the reverse. If core could import models, and some outer package (say backend/api) already depends on both, the dependency graph stops being a clean tree pointing toward core and starts having cycles — which is exactly what the two forbidden-import contracts in .importlinter exist to catch mechanically.

3. Why does an unbounded pin like import-linter>=2.0 count as a real bug even though it worked when M1 was originally built?

Because "works on this machine" and "reproducible" are different claims, and the pin only guaranteed the first one.

The .importlinter contract syntax in this repo was written and verified against import-linter 1.8.0 specifically. A >=2.0 lower bound with no upper bound means a fresh pip install — on a clean clone, in CI, or on a teammate's machine — resolves to whatever the newest 2.x release is (2.14 at the time), a different major version with different config expectations. The fix pins to >=1.8,<2.0 so every fresh install lands on the version the config was actually validated against.
