1Background

The system this project is building reviews a pull request with four independent specialist reasoners — security, quality, tests, docs — then merges what they find into one review. M1 through M3 built everything up to the point where a validated webhook sits on a Redis queue, waiting to be picked up. Nothing yet decides what happens to that job once a worker dequeues it: which agents run, in what order, what happens if one of them fails, and — because a worker process is not guaranteed to live forever — what happens if the whole thing dies halfway through.

M4's job is to build that missing piece: an orchestrator. Concretely, it uses LangGraph, a library purpose-built for exactly this shape of problem — a graph of steps with shared state, some of which can run in parallel, all of which needs to survive a crash. M4 does not yet wire in real agents (that's M8/M10) or real aggregation logic (M5); it proves the orchestration mechanism itself works, using four fast, deterministic stub nodes that each return one canned Finding.

2Typed state: why a graph needs a schema

A StateGraph is LangGraph's core abstraction: a directed graph of named nodes (plain functions) that all read from and write to one shared, typed state object as execution moves through the graph. "Typed" is doing real work in that sentence — it's not a mutable global dict; it's a schema (backend/orchestrator/state.py's GraphState, a TypedDict) that says exactly which keys exist, what type each holds, and — critically for this milestone — how to combine two nodes' writes to the same key.

An orchestrator needs this structure for a reason a simple function call doesn't: multiple independent pieces of work (four specialists) need to contribute to one shared result, and some of them run at the same time. If state were just "whatever the last function returned," two things break at once — there is no defined shape a downstream node (the aggregator) can rely on, and concurrent writers would silently stomp on each other. A typed schema with per-field merge rules is what makes "four things happen in parallel and all four results end up in the final answer" possible to state as a guarantee rather than an accident of scheduling.

review_id, pr_number, repository_owner, repository_name, head_sha

Carried through unchanged by every node — identifying context for the run, not yet acted on until a later milestone needs it.

findings: Annotated[list[Finding], operator.add]

Every specialist's contribution, combined via operator.add (list concatenation) rather than overwritten.

node_errors: Annotated[dict[str, str], _merge_dicts]

Maps a failed specialist's name to its error message, combined via a shallow dict merge.

3Fan-out via the Send API

backend/orchestrator/graph.py routes START through a dispatcher function that returns four langgraph.types.Send objects, one per specialist: 

def _dispatch(state: GraphState) -> list[Send]:
    return [Send(node_name, state) for node_name in _SPECIALIST_NODES]

builder.add_conditional_edges(START, _dispatch, _SPECIALIST_NODES)

A plain add_edge(START, node) per specialist would technically also fan out to four nodes in the same super-step, but Send is the API PLAN.md's M4 outcome names explicitly, and — more importantly — it generalizes: Send lets the number of fanned-out tasks depend on runtime data (imagine a future milestone with a variable number of specialists), where a hardcoded set of add_edge calls cannot.

Why run the four specialists concurrently instead of one after another at all? Because they are independent: security's read of the diff doesn't need quality's answer first, and vice versa. Chained sequentially, four specialists each taking real LLM latency (M4's stubs sleep 0.2s to simulate this) would add up: run one after another and total wall time is roughly the sum of all four. Run them concurrently and wall time is roughly the slowest single one — the whole point of an orchestrator that fans out rather than just calling four functions in a row.

Verified, not just claimed
test_fanout_runs_nodes_in_parallel doesn't just eyeball a duration — it asserts wall time for all four nodes stays under half the sum of their four individual sleeps (a sequential chain would blow past that bound), and separately asserts every pair of nodes' recorded (start, end) execution windows actually overlaps in time. The real measured numbers logged during this build: ~0.31s wall time for all four nodes vs. 1.2s (four × 0.3s) a sequential chain would need.

4The reducer: operator.add, and life without it

Here is the concrete problem four parallel writers create. All four specialist nodes run in the same LangGraph super-step, and each one returns a partial state update — {"findings": [finding], "node_errors": {}}. LangGraph has to fold all four of those partial updates into one new state before the next super-step (the aggregator) runs. Without a merge rule, the only sane default for "four things wrote to the same key" is last write wins — whichever node's update LangGraph applies last simply overwrites the other three. Four specialists would collapse into one surviving Finding, with no error and no indication that three-quarters of the review's findings quietly vanished.

Annotated[list[Finding], operator.add] on the findings field is what tells LangGraph's Pregel engine to use a different rule for this key specifically: instead of replacing the old value with the new one, call operator.add(old, new) — for two lists, that's concatenation. Four branches each contributing a one-element list combine into a four-element list, in whatever order the merges happen to land in (order across branches is explicitly not guaranteed — M5's aggregator, not M4, owns sorting). node_errors gets its own reducer, _merge_dicts, doing a shallow {**left, **right} union — safe here because each node only ever writes its own key, so there's no ambiguity about which value wins on a real collision.

What LangGraph does without a reducer
This is the detail worth being precise about: LangGraph does not silently pick last-write-wins as some kind of safe default for every case. For a channel with no declared reducer, if more than one node in the same super-step tries to write a new value to it, LangGraph raises InvalidUpdateError and the run fails loudly. In other words: the "silently drop three specialists' work" scenario above isn't actually what an un-reduced findings: list[Finding] field would do — that exact case is what forces you to add a reducer in the first place, because LangGraph refuses to guess how to combine concurrent writes to a bare field and fails the run instead. operator.add is what tells it "concatenation is the correct way to combine these," turning an error into defined, correct behavior.
Verified, not just claimed
test_fanout_state_merges_across_parallel_branches asserts all four findings survive as four independently valid Finding objects (not a partially-merged fragment) and that node_errors merged to an empty map when nothing failed — proving the reducers actually combine branches correctly, not just that the graph runs without raising.

5Checkpointing: what, when, and why resume skips

A checkpoint is a durable snapshot of GraphState plus which nodes have completed, written after each super-step — not just once at the very end of a run. build_graph() requires a checkpointer as a mandatory parameter with no default, specifically so it is structurally impossible to compile this graph without one: 

def build_graph(
    checkpointer: BaseCheckpointSaver[str],
) -> CompiledStateGraph[GraphState, None, GraphState, GraphState]:
    ...
    return builder.compile(checkpointer=checkpointer)

Every call is scoped by a thread_id — the identifier the checkpointer uses to correlate all state for one run (one PR review, in the target design). LangGraphWorkflowEngine.run(thread_id, state) starts a new run; if a node raises partway through, LangGraph's checkpointer has already durably recorded whichever sibling branches in that same super-step did complete, as "pending writes" against the last good checkpoint, before the exception propagates out of run(). resume(thread_id) — called with no fresh initial state, just the same thread_id — tells LangGraph to continue that persisted run from its last checkpoint.

Why must resume skip completed nodes rather than replay them, concretely? Two reasons converge here. First, correctness: three of the four specialists in M4's fan-out already succeeded and their findings are durably recorded — re-running them would be wasted work at best, and for a real LLM-backed specialist in a later milestone, an unnecessary paid API call and a chance of a different (possibly worse) answer replacing a good one. Second, this is the entire reason checkpointing exists in the first place: a worker process can die at any point (an OOM kill, a deploy, a crash), and a review pipeline that restarted every specialist from zero after every transient crash would never make forward progress reliably at scale. LangGraph's checkpointer tracks "pending writes" per super-step precisely so resume can look at what's already durably committed and only re-invoke the tasks that never finished.

6Proving resume is real, not theater

A checkpointing claim is easy to state and easy to fake — "compiled with a checkpointer" proves almost nothing on its own if nothing actually exercises the resume path against a genuinely new process. This is exactly the gap DONE.html's M4 gate calls out by name: "LangGraph checkpoints actually resume after a simulated worker crash (compiled with a checkpointer, not without)."

Why this gate exists
A prior reference implementation of this same milestone shape claimed Redis-backed crash-resume in its comments and documentation, but the graph it actually shipped was compiled with no checkpointer at all — the claim and the code silently disagreed, and nothing in that codebase would have caught it, because no test exercised resume across a real process boundary. That gap is exactly why this project's DONE.html gate is worded the way it is, and why this build treats "compiled with a checkpointer" as the necessary-but-not-sufficient first step, not the finish line.

This build's central test, test_checkpoint_resume_skips_completed_nodes, is deliberately built to make faking the result hard:

  1. Arm a simulated crash in the docs node, run the graph — it raises. The other three specialists already committed a successful result.
  2. Build a brand-new LangGraphWorkflowEngine instance, pointed at the same on-disk SQLite checkpoint file, and call resume(thread_id) — modeling an actual new worker process picking up a dead one's work, not a retry against the same in-memory Python objects.
  3. Assert the three already-completed nodes' call counts are still exactly 1 (never re-invoked), while docs — which crashed once — shows a call count of 2 (genuinely re-executed, this time to success).
The falsification probe
L4 VERIFY additionally ran an independent check this build's own test suite doesn't perform: after the simulated crash, delete the on-disk checkpoint file before calling resume. If resume "succeeded" regardless of whether real persisted state existed, that would mean the mechanism was not actually reading from disk — the test would be structurally incapable of catching a fake. With the checkpoint file deleted, resuming a thread_id that LangGraph has no persisted state for behaves as a fresh run rather than a false-positive resume, confirming the resume path genuinely depends on the on-disk state it claims to read, not merely a code path that always reports success.

7Why SQLite, not Redis

PLAN.md's original M4 outcome text said the graph "checkpoints state to Redis" — the natural choice, given M3 already stood up a Redis instance this project owns. Before writing any production code, this build installed langgraph-checkpoint-redis (LangGraph's official Redis checkpointer) and smoke-tested it directly against this project's own docker-compose.yml Redis.

What was tried

langgraph-checkpoint-redis's .setup() issues FT.INFO / FT.CREATE — RediSearch module commands — to build a search index for checkpoint lookups. Plain redis:7-alpine (M3's image) does not implement RediSearch. The concrete, reproduced failure: redis.exceptions.ResponseError: unknown command 'FT.INFO'.

What this build uses instead

langgraph-checkpoint-sqlite's SqliteSaver, a real, first-party LangGraph checkpointer — not a mock — backed by a file (not :memory:) so state survives the writing process exiting, which is the entire property "resume after a crash" depends on being true.

Switching M3's Redis image to Redis Stack (which does bundle RediSearch) would fix the original checkpointer, but that is a change to docker-compose.yml outside M4's freeze boundary — not a decision this milestone should make unilaterally on a shared piece of infrastructure. This is a documented, justified tradeoff, not a silent substitution: PLAN.md's M4 outcome now states plainly that the build uses a durable file-backed SQLite checkpointer, with a parenthetical noting Redis-backed checkpointing needs RediSearch/Redis Stack and was deferred. L4 VERIFY reviewed this deviation directly and ruled it non-blocking, since DONE.html's own gate asks only that the graph be "compiled with a checkpointer, not without" — it does not name Redis specifically.

8Failure isolation: contained vs. propagated

M4 deliberately proves two different failure modes, because conflating them would hide a real design decision. nodes.py defines two distinct exception types for this reason alone:

ExceptionRepresentsWhat happens to it
AgentExecutionError A specialist's own logic failing — a malformed diff, a future LLM provider error, a response that fails schema validation. Caught inside that node's wrapper function and recorded in GraphState.node_errors. The run continues; the other three specialists' findings still reach the final state.
SimulatedNodeCrashError The worker process itself dying mid-node — what a real OOM kill or crash looks like from the checkpointer's point of view. Left to propagate uncaught, out of the node, out of the graph, out of WorkflowEngine.run. The run fails, and only resume against the persisted checkpoint can continue it — see the checkpointing sections above.

This split is by design, not an oversight: a single specialist's own bug must never cost the other three their work (that would make the whole review as fragile as its flakiest agent), but an actual process death is a fundamentally different event that a graph should not — and structurally cannot — quietly paper over. It has to surface as a failed run so that resume's checkpoint-driven recovery path is what handles it, not a caught-and-ignored exception pretending nothing happened.

Verified, not just claimed
test_fanout_isolates_single_node_failure arms an AgentExecutionError in the quality node and asserts the run still completes with exactly 3 findings (security, tests, docs) plus a non-empty node_errors["quality"] message — proving isolation, not just claiming it. The crash-propagation half of this design is exercised by test_checkpoint_resume_skips_completed_nodes itself, which relies on SimulatedNodeCrashError actually failing the run (via pytest.raises) before it can test resume at all.

9Known limits, stated honestly

L4 VERIFY approved M4 — the demo command passes, all four gates are green, and the crash-resume gate is satisfied by a real cross-process test plus an independent falsification probe. It also flagged real, non-blocking limitations:

  1. LangGraph logs a deserialization warning on resume: "Deserializing unregistered type backend.models.enums.AgentType / Severity / backend.models.findings.Finding from checkpoint. This will be blocked in a future version." This project's custom Pydantic models and enums aren't registered with LangGraph's (de)serializer, so a future LangGraph major could hard-block resume for these exact types unless a mitigation (LangGraph's allowed_msgpack_modules, or an equivalent registration mechanism) is configured first. Resume works correctly today; this is a forward-looking upgrade risk, not a present bug — recorded in checkpoints/CURRENT.md and as a comment in langgraph_engine.py next to the checkpointer setup.
  2. The default checkpoint path is untested outside the test suite. LangGraphWorkflowEngine's default, var/orchestrator_checkpoints.sqlite3, is never exercised by any test — every test uses a fresh tmp_path-scoped file instead. The underlying mechanism (a real file-backed SqliteSaver, resume across a new engine instance) is verified; whether the specific default path works end-to-end in a real local run is not evidenced one way or the other.
  3. The orchestrator is not wired into the webhook/queue path. Nothing in backend.webhook_receiver or backend.job_queue calls LangGraphWorkflowEngine yet. A validated, queued webhook and a working orchestrator both exist today as separately-tested capabilities — connecting them (webhook → queue → orchestrator run) is explicitly out of M4's freeze boundary and expected in a later milestone.
Why these aren't blockers
None of the three contradicts what M4's plan entry or DONE.html's DoD gate asked for: four stub nodes fan out in parallel, their outputs land in the final state, and a simulated crash resumes from checkpoint rather than re-running completed work. The demo command and all 5 new integration tests prove exactly that. Recording the gaps keeps them visible for whichever later milestone needs to close them, instead of quietly forgetting them or scope-creeping M4 to cover work — real agents, aggregation, wiring into the request path — that was never this milestone's job.

10Quiz

Three questions. Click each one to reveal the answer.

1. Why does GraphState.findings need Annotated[list[Finding], operator.add] instead of just list[Finding], given that LangGraph refuses to silently pick a default for concurrent writes anyway?

Because without a declared reducer, LangGraph doesn't pick a safe default at all — it raises InvalidUpdateError and fails the whole run the moment more than one node in the same super-step writes to that key. operator.add is what tells LangGraph the correct way to combine four branches' contributions (list concatenation), turning a hard failure into defined, correct merge behavior.

All four specialist nodes run in the same super-step and each returns its own one-element findings list. A bare, un-reduced field can't accept more than one writer per super-step at all — the reducer isn't an optimization on top of working default behavior, it's what makes concurrent writes to that key legal in the first place. test_fanout_state_merges_across_parallel_branches proves the actual merge: four distinct, independently valid findings survive, not a silently collapsed one.

2. test_checkpoint_resume_skips_completed_nodes builds a brand-new LangGraphWorkflowEngine instance to call resume(), rather than reusing the engine instance that hit the simulated crash. Why does that distinction matter?

Because reusing the same in-memory engine/process would only prove "this Python object can retry its own work," not "a genuinely new worker process can pick up a dead one's work from disk" — which is the actual failure mode checkpointing exists to survive (a process crashing, not a function raising and being caught).

A fresh engine instance means a fresh SQLite connection with no in-memory state carried over from the crashed run — the only thing connecting the two engine instances is the same on-disk checkpoint file and the same thread_id. If resume worked only because some in-process cache survived the crash, testing against a brand-new instance would expose that immediately; testing it this way is what makes the three untouched call counts (still 1) and the re-executed docs node (count 2) a real result rather than an artifact of test setup.

3. This build uses langgraph-checkpoint-sqlite instead of the Redis checkpointer PLAN.md originally named. Why wasn't the fix simply "add Redis Stack to docker-compose.yml" during this same milestone?

Because docker-compose.yml is not listed in M4's freeze boundary — the set of files this milestone is scoped to touch — so swapping M3's shared Redis image is a decision this milestone should not make unilaterally, even though it would technically unblock the original Redis checkpointer.

The actual blocker was concrete and reproduced, not assumed: langgraph-checkpoint-redis's .setup() issues RediSearch commands (FT.INFO) that plain redis:7-alpine doesn't implement, confirmed by an actual ResponseError. Given a real, working, first-party LangGraph checkpointer (SqliteSaver) was available and satisfies every behavior the milestone's gate actually asks for — "compiled with a checkpointer, not without," durable across a process restart — using it and documenting the tradeoff was the option that didn't require an out-of-scope infrastructure change to a shared service other milestones also depend on.
