1Background: one table, three jobs

Every milestone through M6 built a piece of the review pipeline — webhook ingress, a queue, an orchestrator, an aggregator, a reliability layer — but none of them left a record of what actually happened while a review ran. If a reviewer asks "why did PR #42 get auto-posted?", or "how much did the security agent's LLM calls cost last week?", or "prove nobody edited this audit record after the fact" — M6's codebase has no answer. M7's job is a single new table, agent_events, and a small emission API in front of it (backend/observability/events.py), wired into the webhook route and the four orchestrator specialist nodes.

The interesting design decision is not "add a table" — it's that one table, append-only and ordered by timestamp, is enough to serve three purposes that might otherwise look like they need three separate systems:

trace viewer

backend.observability.audit.reconstruct_review_trace reads every row for one review_id, ORDER BY ts ASC, id ASC — a complete, time-ordered story of one review from the webhook decision through every specialist's span.start/span.end to the aggregator's final decision, reconstructed from nothing but the id.

audit trail

The same rows, but the property that matters here isn't order — it's that they can never be altered or deleted after being written (Section 2). An audit record you can edit after the fact isn't an audit record; it's a note.

cost ledger

AgentEvent's tokens_in, tokens_out, and cost_usd columns (see backend/database/models.py) exist on every llm.call row. Summing cost_usd across a review_id, or across a day, is the same SELECT shape as the trace query, just aggregated differently.

Nothing about the schema privileges any one of these three readings over the others — they are three different WHERE/ aggregation shapes over the same append-only stream, not three separate stores that need to agree with each other. That is the actual argument for "one events spine" instead of a trace-only log plus a separate cost table plus a separate audit table: there is nothing to keep in sync, because there is only one place the facts live.

Where this lives
Schema and enforcement: backend/database/migrations/0001_agent_events.sql. Typed row + the fixed EventType vocabulary: backend/database/models.py. Read/write access (the only file in the codebase allowed to run SQL against this table): backend/database/repository.py. The emission API every call site actually imports, plus this milestone's failure policy: backend/observability/events.py. Wired into backend/webhook_receiver/router.py (one decision event per verified webhook outcome) and backend/orchestrator/nodes.py (a span per specialist, one decision from the aggregator).

2Enforcing append-only in the database, not by convention

"Append-only" is easy to promise in a docstring and easy to break by accident — one future UPDATE agent_events SET outcome = ... slipped into a bugfix, and the audit trail's core property is gone, silently. Migration 0001 makes the promise true two different ways, and the reason there are two is that each one closes a gap the other leaves open.

1. a BEFORE trigger

agent_events_no_update and agent_events_no_delete fire on any UPDATE or DELETE, for any role, and raise unconditionally. This is the primary mechanism, not a backstop — see below for why.

2. a restricted writer role

agent_events_writer is granted only SELECT, INSERT; UPDATE, DELETE, TRUNCATE are explicitly REVOKEd. The application connects as this role, never as an admin.

The trigger has to be the primary mechanism, because a PostgreSQL superuser bypasses ordinary privilege checks entirely — a REVOKE on its own means nothing against a connection using the postgres role (exactly the role migration 0001 itself runs as, and the role a human operator would use for a manual fix at 2am). A BEFORE trigger, by contrast, fires unconditionally regardless of who issues the statement — it is what actually makes "nobody can mutate this table" true, rather than merely documented policy that a superuser connection can walk straight through. The REVOKE on the restricted role is still worth keeping — it makes the file's intent unambiguous to a future reader, and it means the ordinary application connection gets a clean permissions error instead of ever reaching the trigger at all — but it is defense in depth, not the thing doing the actual work.

3The TRUNCATE gap a row-level trigger leaves open

The first L1 BUILD shipped exactly the two row-level triggers above and a comment claiming they made append-only true "regardless of which role issues it." That comment was wrong, and the same L4 VERIFY session that caught this milestone's centerpiece bug (Section 5) caught this one too: TRUNCATE agent_events;, run as the postgres superuser, silently wiped every row — 94 of them at the time — with no exception and no trigger firing at all.

The reason is a genuine PostgreSQL quirk worth understanding on its own terms, not just patching around: TRUNCATE is not "a big DELETE." A DELETE is row-level DML — Postgres walks the table and removes matching rows one at a time, which is exactly the hook a FOR EACH ROW trigger sits on. TRUNCATE, instead, deallocates the table's storage pages wholesale without ever visiting individual rows — it behaves more like a DDL operation than a per-row delete. Because no row is ever individually touched, PostgreSQL has nothing to invoke a FOR EACH ROW trigger on — the row-level trigger machinery is architecturally absent from the TRUNCATE code path, not merely unlucky to miss it. PostgreSQL does support a separate trigger granularity, FOR EACH STATEMENT, that fires once per statement regardless of how many rows it touches (or doesn't touch) — and critically, a table's FOR EACH ROW triggers and its FOR EACH STATEMENT triggers are registered, and fired, completely independently of each other.

Before the fix

Only agent_events_no_update/ agent_events_no_delete (both FOR EACH ROW) exist. TRUNCATE agent_events; matches neither trigger's registration — it succeeds silently, every row gone.

After the fix

A third trigger, agent_events_no_truncate (BEFORE TRUNCATE ... FOR EACH STATEMENT), registered separately. It uses its own trigger function (agent_events_forbid_truncate) rather than reusing the row-level one, because a statement-level trigger has no per-row OLD/NEW context to read. TRUNCATE agent_events; now raises agent_events is append-only: TRUNCATE is not permitted before anything is removed.

The transferable lesson is the specific one, not "add more triggers": when a table has more than one way to be mutated, each PostgreSQL trigger granularity (row-level vs. statement-level) has to be checked against every mutating statement type independently — "I added a BEFORE trigger" is not automatically the same claim as "no mutation gets through," because a granularity mismatch, not a missing trigger, is exactly the gap that opened here.

4Why the app connects as a restricted role

Two separate connection strings exist in Settings: database_url (the agent_events_writer role — SELECT, INSERT only) and database_admin_url (the postgres superuser). EventRepository, the only application code that touches this table, is constructed from database_url exclusively. The admin DSN is used in exactly one place: backend.database.postgres.apply_migrations, which runs migration 0001 itself — creating the table, the triggers, and the restricted role all require privileges that restricted role is deliberately never granted, so the restricted role could not apply its own migration even if application code tried to.

This is the same "least privilege for the request path, elevated privilege only for setup" split you'd want for any production database user, made concrete here by the fact that the two DSNs literally differ in which role they authenticate as. If application code were ever compromised or simply buggy enough to attempt an UPDATE, connecting as the restricted role means that attempt fails on a permissions check before it would even reach the trigger that (independently) also forbids it.

5The centerpiece: blocking the event loop

This is the part of M7's history worth understanding in full, not smoothing into a footnote — a first, independent L4 VERIFY session rejected M7's original build for a real bug, not a nitpick.

What "blocking the event loop" means, for a reader who hasn't thought about it

FastAPI (via uvicorn) can serve many concurrent requests using a single OS thread, because each request handler is a coroutine — Python code that periodically hands control back to an event loop at every await. The event loop's job is to look at every in-flight coroutine and run whichever one is ready to make progress, switching between them whenever one hits an await and is waiting on something (a network read, a timer). This is how ten requests can be "in progress" at once on one thread: none of them ever occupies the thread for long — they take turns.

That entire arrangement depends on every coroutine actually handing control back promptly. If one coroutine calls a plain, ordinary Python function that blocks — no await, just a synchronous call that doesn't return for a while — the event loop has no opportunity to switch to anything else. It isn't "this request waits a while"; it's "the one thread the entire process depends on to run any coroutine is now occupied," which means every other concurrent request, no matter how unrelated, is frozen too. A single stalled call inside one handler can make the whole server look dead, not just the one request that made the call.

what actually happened

backend.webhook_receiver.router.receive_webhook is async def. The original build called EventRepository.insert_event — a plain, synchronous psycopg.connect(...) — directly, with no await and no offload. Every other concurrent webhook request shares the same event loop thread.

The proof, not just the theory

L4 VERIFY did not stop at reasoning about this abstractly — it reproduced the failure against a live server. An admin session held LOCK TABLE agent_events IN ACCESS EXCLUSIVE MODE (the strongest lock Postgres has — it blocks every other statement against the table, including the plain INSERT the events write performs) for several seconds. While that lock was held, three concurrent, otherwise-unrelated webhook POSTs were sent to a live uvicorn process: 

three concurrent webhook POSTs, events table locked ACCESS EXCLUSIVE:
each request: ~4.4s (normal, unlocked case: sub-10ms)
→ SERIALIZED, not concurrent: one blocked write held the event
  loop thread every other in-flight request also needed.

Every request's own events write blocked on the same table lock — that part is expected, one connection waiting for one lock. What is not expected, and what makes this a real bug rather than "the slow request was slow," is that the other two requests, which never touched the locked table themselves, took just as long — because the one request's blocking call froze the event loop thread they all depended on to run at all. This also violates .genesis/DONE.html's own section 2 gate — "every outbound call has a timeout / circuit-breaker" — since connect_timeout was the only bound in place, and it does not cover this failure mode at all (Section 6).

6The fix: a real timeout, an offload, a reused breaker

The L2 DEBUG loop that followed the REJECT applied three changes, each closing a distinct part of the failure — none of them a hand-rolled one-off, all three reusing existing primitives.

1. statement_timeout, because connect_timeout never covered this

EventRepository already passed connect_timeout to psycopg.connect before the fix. It did nothing to prevent the bug above, and understanding why is the key distinction: connect_timeout bounds only the initial TCP handshake — the time it takes to establish the connection itself. It has nothing to say about how long a query takes to execute once the connection exists, and nothing to say about time spent waiting to acquire a lock the query needs before it can run at all — which is exactly the situation the ACCESS EXCLUSIVE lock created: the connection opened fine, and then the INSERT sat waiting for a lock that wouldn't release for seconds. A timeout on the handshake is silent about everything that happens after the handshake succeeds.

The fix sets Postgres's own statement_timeout GUC (via libpq's options connection parameter, -c statement_timeout=<ms>, applied from the moment the connection is established) — a bound enforced by the database itself on query execution, including lock-wait time. Default 2000ms (Settings.events_statement_timeout_ms). Once this bound is in place, a query stuck behind a lock for longer than the timeout is cancelled by Postgres, not left to hang indefinitely.

2. asyncio.to_thread, to get the call off the loop

A real query-level bound alone still leaves the original problem half-solved: even a 2-second bounded block is still 2 seconds of the entire event loop being unavailable to every other request. The actual fix for "blocking the event loop" is not a shorter block — it's not blocking the loop thread at all. backend.observability.events gained emit_decision_async, and the router now awaits it instead of calling the synchronous emit_decision directly:

Before

emit_decision(event_repository, review_id, agent=None, outcome=outcome)
# a plain synchronous call, unawaited, on the event loop thread

After

await emit_decision_async(event_repository, review_id, agent=None, outcome=outcome)
# runs emit_decision on asyncio's default thread-pool executor via
# asyncio.to_thread; only THIS request's own coroutine awaits it

asyncio.to_thread submits the blocking call to asyncio's own default executor — a bounded worker thread pool the event loop already manages, not a new thread spun up per call — and hands back an awaitable. The calling coroutine suspends at the await exactly like any other I/O wait, which is precisely the point: the event loop is free again the instant the write is handed off, and every other concurrent request's coroutine keeps making progress on it while this one write happens on a separate thread. The response still waits for the write to finish (or fail-and-be-swallowed, per Section 8) before answering — this is not "fire and forget," only "don't make everyone else wait too."

Note what did not need this change: backend/orchestrator/nodes.py's span/decision emissions call the plain synchronous emit_span_start/ emit_span_end/emit_decision functions directly, with no asyncio.to_thread wrapper — correctly, because LangGraph already runs a synchronous graph's nodes on its own worker-thread pool, never on an asyncio event loop. There is no event loop at that call site for a blocking call to starve, so offloading again there would be solving a problem that doesn't exist in that lane.

3. A dedicated CircuitBreaker, reused from M6, not hand-rolled

insert_event now runs through a CircuitBreaker — M6's own class (backend.reliability.circuit_breaker), instantiated fresh for the events path with independent knobs (events_circuit_breaker_failure_threshold, default 5; events_circuit_breaker_reset_timeout_seconds, default 30.0) rather than sharing state with RedisJobQueue's breaker. Once the events database has failed 5 consecutive times, the 6th call fails immediately with CircuitOpenError — no connection attempt, no waiting out another statement_timeout window — until the reset window elapses. This is the same "fail fast instead of retrying at full cost on every request" logic M6 built for Redis, composed the same way rather than re-implemented for Postgres.

7Independent re-verification, not trust

A second, independent L4 VERIFY session did not take the L2 DEBUG session's word that the fix worked — it re-ran the same concurrency experiment against the fixed code and measured the numbers itself, then went further and stress-tested the specific mechanism (asyncio.to_thread offloading) under saturation.

Reported by the second independent verifier (see .genesis/checkpoints/CURRENT.md)

The same three-concurrent-webhook-POSTs-under-a-locked-table experiment, re-run against the fixed code: ~2.03s per request, ~2.09s total wall time for all three — concurrent, not stacked to something close to 3×2.03s. The near-equality of "total wall time" and "per-request time" is itself the signal: if the three requests were still serialized behind one blocked event loop, the total would scale with the count of requests; here it doesn't, because all three genuinely overlap.

A separate saturation check went after the offloading mechanism directly rather than only the end-to-end timing: 40 event emissions were driven against a deliberately small, 14-thread executor, while a concurrent heartbeat coroutine ticked every 0.1 seconds on the same event loop. Result: the 40 emissions completed in 3 clean FIFO batches (the small pool queuing work in submission order once its 14 threads filled up — exactly the behavior a bounded thread pool should show under more work than it has threads), while the heartbeat ticked 61 times out of 61, with no gaps. A stalled or gap-riddled heartbeat would have meant the event loop was still getting starved somewhere even after the fix; 61/61 with clean timing is the loop staying fully responsive while 40 blocking writes were in flight on background threads.

These specific figures come from the verification sessions' own reports, as recorded in .genesis/checkpoints/CURRENT.md and .genesis/PLAN.md's M7 progress entry — the concurrency and saturation experiments are ad hoc, one-time repros against a live server and a custom executor, not scripts preserved as permanent, re-runnable tests in this repository (unlike tests/integration/test_events_spine.py's own TestConcurrentWebhookWritesAreNotSerializedByALockedEventsTable, which asserts the same underlying property — no individual request approaches the full lock-hold duration, and the batch completes in close to one statement_timeout window rather than scaling with the request count — using its own lock-hold and timeout parameters).

  • L4 VERIFY — Reject
    Independent session locks agent_events ACCESS EXCLUSIVE, measures three concurrent webhook POSTs at ~4.4s each (sub-10ms normally), and rejects M7's L1 BUILD for a real reliability defect.
  • L2 DEBUG
    Adds statement_timeout, offloads the webhook's events write via emit_decision_async/asyncio.to_thread, wraps the write in a dedicated CircuitBreaker; also closes the TRUNCATE gap and narrows an exception swallow (Sections 3 and 8), and fixes the demo command's clean-shell/tiebreak bugs.
  • L4 VERIFY — Approve
    A second, independent session reproduces ~2.03s/request and ~2.09s total wall time for three genuinely concurrent requests, proves the loop stays responsive under executor saturation (40 emissions, 3 FIFO batches, heartbeat 61/61), and approves M7.

8Failure policy: log-and-continue, except for our own bugs

Writing an audit/trace event must never take down the request it is observing — a webhook POST must still verify, dedupe, and enqueue correctly even if the events Postgres is completely unreachable. backend.observability.events._emit implements this by catching psycopg.Error, OSError, and CircuitOpenError around the actual write, logging a warning, and returning normally — the caller never sees the failure.

The same L4 VERIFY session that caught the event-loop bug also caught a second problem with this policy, narrower but real: the original except (psycopg.Error, OSError) is broad enough to also catch psycopg.errors.IntegrityError — a CHECK-constraint violation, for example, is a subclass of psycopg.Error. Concretely: agent_events's event_type column has a CHECK constraint limiting it to the five known event kinds (backend/database/migrations/0001_agent_events.sql). If a future bug ever managed to construct an AgentEvent with a value outside that set (or violated a future NOT NULL/UNIQUE constraint the same way), that is a bug in this codebase's own logic, not evidence the database is unavailable — and the original broad except would have silently swallowed it into the exact same log line as a genuine outage, hiding a real defect behind the same message used for "Postgres is down right now, which is expected and fine."

The fix
_emit now catches IntegrityError first and re-raises it immediately, before the broad (psycopg.Error, OSError, CircuitOpenError) clause runs — a genuine schema-rejects-this-row bug propagates loudly, while a real connectivity failure is still swallowed exactly as before. Every emit_* function also constructs its AgentEvent outside the try/except entirely, so a pydantic ValidationError from bad caller input (e.g. a string where tokens_in expects an int) was never at risk of being caught by this policy in the first place — it was always a programmer error, not a database outage, and always propagated.

9Known limits, stated honestly

  1. The breaker can drop events for up to reset_timeout_seconds (30s default) under a sustained outage. Once EventRepository's breaker opens, every write attempt fails fast and is logged-and-swallowed by backend.observability.events's policy (Section 8) for as long as the breaker stays OPEN. Every drop is logged, and this is a judged, deliberate trade-off — a bounded gap in the audit trail is preferable to an unbounded request stall — but it is worth stating plainly rather than glossing over: an audit log that can silently (from the request path's point of view) drop entries for up to 30 seconds has an integrity concern distinct from ordinary availability. There is no /health surface yet that would make an open events breaker visible operationally, rather than discoverable only by grepping logs after the fact.
  2. The exact same defect class this milestone just fixed still exists in M6-scope code that already passed its own L4 VERIFY. backend/webhook_receiver/router.py's queue.enqueue(event) call (line 239, inside async def receive_webhook) is a plain, synchronous, unawaited call — no await, no asyncio.to_thread. RedisJobQueue.enqueue (backend/job_queue/redis_arq.py) itself blocks the calling thread: its _enqueue_arq_job hands work across a sync/async bridge via asyncio.run_coroutine_threadsafe(...) and then waits on that future with future.result(timeout=...) (backend.reliability.timeout.await_future) — a real, bounded wait, but one made synchronously from inside a coroutine, on the event loop thread. A slow-but-not-fully-down Redis (elevated latency rather than a hard outage) would serialise every concurrent webhook request behind that wait the same way the pre-fix events write did. This was found during M7's own L4 VERIFY passes, not fixed as part of them — backend/job_queue/redis_arq.py and this router call site sit outside M7's freeze boundary. It is recorded in .genesis/checkpoints/CURRENT.md's Deferred list as a high-priority item for its own dedicated fix loop, most likely mirroring this milestone's own emit_decision_async pattern.
  3. events_statement_timeout_ms's 2000ms default is judged reasonable for the single-row inserts this milestone performs, but is a best-guess default worth revisiting once real load/latency data exists.

10Quiz

Three questions. Click each one to reveal the answer.

1. EventRepository already passed connect_timeout to psycopg.connect before the fix, yet three concurrent webhook requests still took ~4.4s each under a locked events table. Why didn't connect_timeout catch this?

connect_timeout only bounds the initial TCP handshake -- how long it takes to establish the connection. It says nothing about how long a query takes to execute afterward, or how long it waits to acquire a lock it needs before running. The lock-wait was the entire problem here: the connection opened fine, and the INSERT then sat blocked waiting on the ACCESS EXCLUSIVE lock, a phase connect_timeout has no visibility into at all.

The fix that actually covers this is Postgres's own statement_timeout GUC, which bounds query execution including lock-wait time, because it's enforced by the database itself on the statement, not by the client on the connection attempt. That's why the fix sets both: the pre-existing connect_timeout stays (it still guards against an unreachable host), and a new statement_timeout is added for everything connect_timeout was never designed to cover.

2. The row-level agent_events_no_update and agent_events_no_delete triggers fire for any role, including a superuser, on UPDATE or DELETE. Why did TRUNCATE agent_events; still silently wipe every row before the fix?

TRUNCATE never fires a row-level (FOR EACH ROW) trigger at all, for any role -- it isn't a row-by-row operation the way DELETE is, so there's no per-row hook for that trigger granularity to attach to. PostgreSQL requires a separate, statement-level (FOR EACH STATEMENT) trigger to intercept TRUNCATE, registered independently of the row-level pair.

This is why the fix adds a third trigger, agent_events_no_truncate (BEFORE TRUNCATE ... FOR EACH STATEMENT), with its own trigger function rather than reusing the row-level one -- a statement-level trigger has no per-row OLD value to reference. The lesson generalizes: a table's row-level and statement-level trigger sets are independent, so "I added a BEFORE trigger" only covers whichever mutation types actually use that trigger's granularity.

3. The webhook router now does "await emit_decision_async(...)" instead of calling emit_decision(...) directly, but backend/orchestrator/nodes.py still calls emit_span_start/emit_span_end/emit_decision directly, with no asyncio.to_thread wrapper. Why is that difference correct rather than an inconsistency?

The router's handler is an async def coroutine running on uvicorn's single event loop, where a blocking call directly freezes every other concurrent request -- that's the bug this milestone fixed. The orchestrator's nodes run as plain synchronous functions on LangGraph's own worker-thread pool for a sync graph, never on an asyncio event loop at all.

Since there's no event loop at the orchestrator's call site to starve in the first place, wrapping those calls in asyncio.to_thread would add an unnecessary layer of indirection without fixing anything -- there's nothing broken there to fix. The rule isn't "always offload blocking calls"; it's "offload a blocking call only when it would otherwise run on a shared event loop thread other concurrent work depends on," which is true for exactly one of these two call sites.
