Tiger Cloud Migration

Every table this project has written to since M7 has lived on a single local Postgres box with no time-partitioning at all. M12 moves agent_events and code_chunks onto a real, paid Tiger Cloud (managed TimescaleDB) instance — a real hypertable, real continuous aggregates, a real DiskANN index. The centerpiece is a gap that almost slipped through unnoticed: the append-only invariant this project has enforced with database triggers since M7 turned out to have a hole a hypertable's chunking opens up, one the parent table's own correct behavior was actively hiding. This page covers what a hypertable actually is, why chunking forces a schema change to the primary key, the row-trigger-vs- statement-trigger gap and how it was closed, why a continuous aggregate's exclusion filter has to live inside the view, the arithmetic trap in combining pre-aggregated buckets, and a glob bug that briefly leaked Tiger-only SQL into local development. 1Background: what a hypertable is

agent_events has been an ordinary Postgres table since M7 — one INSERT per span, LLM call, or routing decision, growing forever because the table is deliberately append-only (a database trigger rejects UPDATE/DELETE for every role, superuser included). An ordinary table with no partitioning has one physical structure holding every row ever written; a query scoped to "the last hour" still has to consult an index built over the entire table's history, and an index that spans years of rows gets larger, slower to update, and slower to vacuum every single day the table stays in production.

A hypertable (TimescaleDB's core abstraction, layered on top of ordinary Postgres) looks like one table to every query (SELECT, INSERT, an index, a trigger — all of it addressed by the hypertable's own name, agent_events), but is physically implemented as many smaller tables called chunks, each holding one time range. This migration chunks on ts at a 1-day interval:

agent_events (hypertable — the name every query still uses)
↓ physically implemented as ↓
chunk: 2026-08-29 (its own physical table)
chunk: 2026-08-30 (its own physical table)
chunk: 2026-08-31 (its own physical table)

A query scoped to today only ever touches today's chunk — its index is small, no matter how many years of history the hypertable holds in total. An INSERT is routed to the right chunk automatically (creating a new one the first time a row lands in a day that doesn't have one yet); nothing about EventRepository's own INSERT/ SELECT SQL had to change, because it still only ever names agent_events. This is exactly why an append-only audit table that grows without bound — this project's own description of agent_events since M7 — is close to the textbook case a hypertable exists for.

2Why the primary key had to change

Local's agent_events (migration 0001_agent_events.sql) has a plain id BIGSERIAL PRIMARY KEY. The Tiger migration's schema is byte-for-byte identical in every other column, but its primary key is PRIMARY KEY (id, ts) — ts, the partitioning column, added into the constraint.

This isn't a style choice. TimescaleDB's create_hypertable() rejects a unique or primary-key constraint outright if it does not include the column being partitioned on. The reason is structural, not arbitrary: a unique constraint has to be enforceable, and Postgres enforces uniqueness by checking an index — but each chunk only holds an index over its own rows. If id alone were the key, guaranteeing no two chunks ever produced the same id would require checking every chunk on every insert, defeating the entire point of splitting the table up. Requiring the partitioning column in the key means each chunk can enforce uniqueness of (id, ts) purely locally, using only its own index — the constraint stays cheap precisely because it never has to look outside the chunk it's inserting into.

What this says about partitioned tables generally
A uniqueness guarantee that isn't allowed to touch every partition has to be re-derived to depend only on the field that determines which partition a row lives in. This shows up under different names across partitioning schemes: TimescaleDB's chunking, a sharded SQL database's shard key, or a NoSQL store's partition key — the common thread is that a global uniqueness invariant becomes local (and cheap) exactly when the constraint includes the partition key. id (a BIGSERIAL) still remains effectively unique in practice, because one sequence generates it regardless of which chunk a row ends up in — but what Postgres/TimescaleDB actually enforce is the composite (id, ts), not id alone.

3The centerpiece: the trigger that didn't follow

Since M7, agent_events has enforced append-only with three triggers: a BEFORE UPDATE and a BEFORE DELETE, both row-level (FOR EACH ROW), and a BEFORE TRUNCATE, statement-level (FOR EACH STATEMENT) — added at M7 specifically because PostgreSQL never fires a row-level trigger for a TRUNCATE at all; TRUNCATE only supports statement-level triggers. That distinction — which PostgreSQL requires for TRUNCATE specifically — is what turned out to matter again here, in a completely different way.

TimescaleDB re-creates a hypertable's row-level triggers on every chunk automatically: an UPDATE or DELETE issued directly against a chunk's own internal table name (something like _timescaledb_internal._hyper_3_14_chunk, not the agent_events name any application code uses) still fires the same rejection. A statement-level trigger created on the hypertable does not get this treatment — it exists only on the hypertable itself, never propagated to any chunk, past or future.

What was tested (looked safe)

TRUNCATE agent_events;
-- ERROR: agent_events is
-- append-only: TRUNCATE is
-- not permitted

The hypertable name itself correctly rejects — the statement trigger fires here, because this is the relation it was created on.

What was never tried before this milestone

TRUNCATE
  _timescaledb_internal._hyper_3_14_chunk;
-- (silently succeeds; rows gone,
--  no exception)

The chunk's own physical table has no statement-level trigger at all — nothing intercepts this.

This is exactly why the gap was invisible from the obvious test: the one behavior everyone naturally checks — does TRUNCATE agent_events get rejected? — passes, because that statement genuinely does hit the trigger. The parent table's own correct rejection actively hides the fact that a chunk, addressed by its internal name, has no such protection. Proving the gap required deliberately bypassing the name every application uses and typing an internal _timescaledb_internal relation name instead.

The fix: privileges propagate where statement triggers don't
agent_events_writer — the restricted role every real write path connects as (SELECT + INSERT only, UPDATE/DELETE/TRUNCATE explicitly REVOKEd) — closes the gap, because PostgreSQL GRANT/REVOKE on a hypertable is propagated by TimescaleDB to every chunk, existing and future, unlike a statement-level trigger. Proven live: a brand-new chunk, created by an insert with a ts days in the future after the role already existed, carried the identical restricted ACL with no manual step — and TRUNCATE/UPDATE/DELETE issued directly against a real chunk's own name, as agent_events_writer, each failed with "permission denied for table ...", rejected by the privilege system itself before any trigger could even run.

The honest residual

This closes the gap for agent_events_writer — the role every production code path actually uses — but not for the owning admin role (tsdbadmin) itself. A REVOKE cannot restrict a table's own owner, and no statement-level trigger reaches a chunk directly, so an operator connected as tsdbadmin who deliberately types a specific chunk's internal name and runs TRUNCATE against it still bypasses both mechanisms. This is judged acceptable, not silently ignored: no production code path ever connects as tsdbadmin (grep-confirmed — every real write goes through agent_events_writer), and it requires deliberately discovering and typing an internal relation name, not something an ordinary mistake could stumble into. It is the same class of "an admin connection with DDL rights can always find a way around a restriction built for everyone else" limitation this project's local design already accepts for its own Postgres superuser.

Independently reproduced by L4 VERIFY
A second, independent verification session did not take the build session's account on faith: it seeded 34 rows into a target chunk inside a transaction, issued TRUNCATE against that chunk's internal name, watched the row count go from 34 to 0 with no exception, root-caused the absence by querying pg_trigger directly (the statement-level trigger's tgrelid pointed only at the hypertable, never at the chunk's own relation), confirmed the same absence on a chunk created fresh after the trigger already existed — ruling out "the chunk just predates the trigger" as an alternate explanation — and then rolled the whole transaction back, leaving no destructive trace in the real database.

4Continuous aggregates and the filter's address

A continuous aggregate is a materialized view TimescaleDB keeps incrementally up to date on a schedule (a refresh policy), rather than recomputing from scratch on every read. This migration adds two: agent_health_1m (1-minute buckets — call count, cost sum, latency sum, and a p95-latency sketch via timescaledb_toolkit's percentile_agg, grouped by agent/model) and pr_cost_hourly (hourly, per-review). What materializing a rollup buys is the same thing a hypertable's chunking buys for raw rows: a query against "the last hour of agent health" touches pre-summed buckets instead of re-scanning and re-aggregating every individual llm.call event since the table was created.

Both views' WHERE clause excludes known test-and-fixture review_id prefixes — the exact same list backend.database.repository._TEST_FIXTURE_REVIEW_ID_ PREFIXES already used to filter M13's plain-SQL cost query, duplicated by hand as literal NOT LIKE clauses inside each CREATE MATERIALIZED VIEW statement.

Why "baked into the view" and not "applied when reading it"
A continuous aggregate pre-computes its buckets once, on the refresh schedule — a synthetic row admitted into a bucket at refresh time is permanently summed into that bucket's cost_usd_sum. Filtering it back out later, at read time, cannot undo a sum that already happened; the only way to exclude a row from a rollup is to keep it out of the aggregation in the first place. This is precisely M13's own $97,468.71 defect in miniature, one layer earlier: M13's bug was a query that forgot to filter before summing; a continuous aggregate that pre-summed before any filter ran would bake that same contamination permanently into the materialized bucket, immune to any filter a later reader remembered to add. Putting the exclusion inside the view definition is what makes "forgetting to filter at read time" structurally impossible instead of merely unlikely.

One asymmetry is deliberate, not an oversight: the future-dated half of the filter (M13's other exclusion mechanism, alongside the prefix list) is not repeated inside the view. It doesn't need to be — a row with a ts in the future lands in a future time bucket regardless, and any reader (EventRepository.aggregate_llm_calls_by_agent's Tiger path) applies its own bucket <= now() bound at query time, structurally excluding that bucket the same way the pre-swap local query's ts <= now() clause did. A prefix a view never admits has to be excluded inside the view; a bucket that simply hasn't arrived yet can still be excluded correctly by a reader, because "not yet" is a property of when you look, not what you summed.

5The weighting trap

EventRepository.aggregate_llm_calls_by_agent gained a Tiger-backend branch that reads agent_health_1m instead of raw agent_events. M13's own comment anticipated this swap as "a narrow change to that one method's FROM/GROUP BY" — and the honest correction this milestone makes is that the swap needed one more change: the SELECT list itself.

A per-minute bucket already stores sum(latency_ms) and count(*) separately — not a pre-computed average. Combine several buckets into one overall average two different ways, and they do not agree unless every bucket happens to contain exactly the same number of calls:

Bucketcallslatency sum (ms)bucket mean (ms)
12:0012,0002,000
12:01999,900100

A naive "average of the bucket means" gives (2000 + 100) / 2 = 1050ms — dominated by the one-call bucket, as if it mattered exactly as much as the ninety-nine-call bucket next to it. The true overall mean is (2000 + 9900) / (1 + 99) = 119ms — barely above the hundred-call bucket's own mean, because that's where nearly every call actually happened. Averaging bucket-level averages silently re-weights every bucket equally, no matter how many calls produced it.

How SUM(sum)/SUM(count) avoids it
agent_health_1m stores raw sums (latency_ms_sum, call_count), never a pre-divided average, specifically so a reader combining buckets can compute SUM(latency_ms_sum) / SUM(call_count) — which is algebraically identical to summing every individual call's latency and dividing by the true total call count, regardless of how unevenly calls are spread across buckets. aggregate_llm_calls_by_agent's Tiger branch does exactly this in Python (total_latency_ms / call_count), not a second AVG() in SQL over already-averaged rows.

L4 VERIFY re-verified this directly against real seeded buckets: the swapped query returned a 182ms average latency, against a true weighted average of 181.8ms computed independently from the underlying rows — where naively averaging the per-minute bucket means themselves would have returned 550ms for the same data. The gap between 182ms and 550ms is the entire weighting trap made concrete.

6DiskANN vs. HNSW

code_chunks exists on both backends with the same VECTOR(256) column and the same generated-column FTS index, so HybridRetriever's SQL is unchanged either way — only the ANN (approximate nearest neighbor) index type differs. Local's dev-pgvector-init.sql uses HNSW (Hierarchical Navigable Small World), pgvector's built-in graph index. Tiger's migration uses DiskANN (pgvectorscale's index, built specifically for TimescaleDB/Tiger), chosen for exactly the property its name promises: it's designed to serve approximate nearest-neighbor queries efficiently against an index too large to fit entirely in memory, which matters once a deployment's embedded corpus grows past what a single local Postgres box comfortably holds in RAM. Local's HNSW stays HNSW deliberately — pgvectorscale/DiskANN is a Tiger-side extension, and local's whole point (a keyless checkout, no paid account required) would be defeated by depending on it there.

This milestone's own build-time test seeded 2,000 rows and confirmed EXPLAIN shows the planner choosing an Index Scan using idx_code_chunks_embedding_diskann, not a sequential scan, for an ORDER BY embedding <=> ... LIMIT query. L4 VERIFY ran its own independent version of the same check at a different scale — 2,500 rows — and confirmed the same planner choice.

7Keeping local development alive

Nothing about this milestone was allowed to require a Tiger Cloud account just to run the existing free test suite — a keyless checkout has been this project's standing bar since M1. Both new Settings fields, events_backend and memory_backend, default to "local"; the free suite (396 tests) was proven green with .env entirely absent, meaning nothing in that path even imports anything Tiger-specific, let alone connects to it.

The regression this discipline nearly missed
backend.memory.tiger_client.apply_migrations's LOCAL-only migration runner applies every .sql file in migrations/scripts/ by globbing the directory. Adding 2026-06-tiger-init.sql alongside the pre-existing dev-pgvector-init.sql in that same directory meant the glob started picking up the Tiger file too — silently applying DiskANN/hypertable DDL that does not exist on local pgvector, against local pgvector.

The two files are genuinely incompatible on purpose, not just by accident of where they happen to live: local's HNSW index must never also exist on Tiger (Stage C's entire point is DiskANN replacing HNSW, not sitting alongside it), and Tiger's schema needs vectorscale/hypertable machinery local's plain pgvector image doesn't have. The fix was to stop treating "every .sql file in this directory" as one applyable set: the Tiger migration is now applied only by backend.database.postgres.init_tiger_schema, called explicitly by name, never picked up by the local glob. L4 VERIFY confirmed the fix by inspecting both local databases' schemas directly (Postgres 5433, pgvector 5434) and finding no Tiger-only DDL in either.

8Quiz

Three questions. Click each one to reveal the answer.

1. `TRUNCATE agent_events;` correctly raised the append-only exception both before and after this migration. Why wasn't that enough to prove the append-only invariant survived the move to a hypertable?

Because that statement only ever tests the hypertable's own relation — TimescaleDB does not propagate a statement-level trigger to chunks, so a `TRUNCATE` issued directly against a chunk's own internal table name (`_timescaledb_internal._hyper_N_M_chunk`) bypasses the trigger entirely and silently succeeds.

The row-level `UPDATE`/`DELETE` triggers do get automatically re-created on every chunk, so testing those against the hypertable name genuinely does prove the same protection holds at the chunk level. `TRUNCATE`'s trigger is statement-level (the only kind PostgreSQL allows for `TRUNCATE`), and statement-level triggers stay put on whatever relation created them — the hypertable's own correct rejection says nothing about a chunk addressed directly, which is exactly why the obvious test looked sufficient and wasn't.

2. The chunk-level TRUNCATE gap is closed by REVOKEing UPDATE/DELETE/TRUNCATE from the `agent_events_writer` role, not by adding another trigger. Why does a privilege REVOKE succeed here where a statement-level trigger fails?

PostgreSQL GRANT/REVOKE on a hypertable is automatically propagated by TimescaleDB to every chunk, existing and future — the same propagation row-level triggers get, but which statement-level triggers never get.

A new trigger created on the hypertable would face the identical problem the original TRUNCATE trigger had: statement-level triggers simply don't reach chunks. Privileges are a different mechanism entirely, checked by the relation's own ACL rather than fired as a database object — and TimescaleDB keeps that ACL in sync across chunks automatically, proven directly by a brand-new chunk (created after the role already existed) carrying the identical restricted grants with no manual step.

3. `agent_health_1m`'s WHERE clause excludes known test-fixture `review_id` prefixes inside the CREATE MATERIALIZED VIEW statement itself. Why not just keep the existing local-path filter and apply it when reading the aggregate, the way M13's plain-SQL query already did?

A continuous aggregate pre-sums its buckets on a refresh schedule — once a synthetic row is summed into a bucket's `cost_usd_sum`, no filter applied afterward, at read time, can undo that sum. The only way to keep a row out of the rollup is to keep it out of the aggregation in the first place.

This is M13's own $97,468.71 defect one layer earlier: that bug was a query that forgot to filter before summing raw rows. A continuous aggregate that pre-summed before any filter ran would bake the same contamination permanently into a materialized bucket, immune to whatever filter a later reader remembered to add. Baking the exclusion into the view definition makes "forgetting to filter" structurally impossible rather than merely unlikely — exactly the fix M13's own history argued for.
